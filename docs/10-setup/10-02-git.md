# 10-02 Git と GitHub の準備

!!! abstract "到達目標"
    - Git をインストールし、`user.name` と `user.email` を設定できる
    - GitHub への認証方法（HTTPS と SSH）の違いを説明できる
    - `dev-environment` リポジトリを clone できる
    - Windows で改行コード（CRLF / LF）が問題になる理由を説明できる

## 何か

Git は、ソースの変更履歴を記録・共有するための道具（バージョン管理システム）です。
GitHub は、Git のリポジトリ（履歴付きのフォルダ）をインターネット上で共有するサービスです。
Pull Request（PR、変更をレビューしてもらう仕組み）や GitHub Copilot も GitHub の機能です。

Windows では Git for Windows を使います。
一緒に入る **Git Bash** は、Linux と同じコマンド（`ls`、`cp`、`./gradlew` など）が使えるターミナルです。
この教材のシェルスクリプト（`.sh`）は Git Bash で実行します。

## なぜ必要か

- チームのソースはすべて GitHub のリポジトリで管理されています。clone できないと作業を始められません
- コミットには「誰が変更したか」が記録されます。名前とメールアドレスの設定が正しくないと、履歴を追えなくなります
- Windows と Linux では改行コードが違います（Windows は CRLF、Linux は LF）。
  設定を誤ると、シェルスクリプトが動かなくなったり、全行が変更扱いになったりします

## どうやるか

### 1. Git for Windows をインストールする

1. [Git for Windows](https://git-scm.com/download/win) のインストーラーを実行する
2. 改行コードの選択肢は、既定の「Checkout Windows-style, commit Unix-style line endings」のままでよい
3. ほかの選択肢も、迷ったら既定のままで進める

**確認**（PowerShell または Git Bash）:

```bash
git --version
```

`git version 2.xx.x.windows.x` のように版が表示されれば OK です。

### 2. 名前とメールアドレスを設定する

Git Bash で次を実行します。`< >` の部分は自分の値に置き換えます。

```bash
git config --global user.name "<あなたの名前>"
git config --global user.email "<あなたのメールアドレス>"
```

メールアドレスは、GitHub のアカウントに登録したもの（または組織が指定したもの）を使います。

**確認**:

```bash
git config --global --list
```

!!! failure "悪い例"
    リポジトリごとに名前やメールアドレスがばらばらで、個人のメールアドレスと業務のメールアドレスが混ざっている。
    コミットの作者が誰か分からず、GitHub 上でもアカウントと紐づきません。

!!! success "良い例"
    業務用の名前とメールアドレスを `--global` で 1 回設定し、`git config --global --list` で確認しておく。

### 3. 改行コードの設定を確認する

```bash
git config --global core.autocrlf
```

インストーラーの既定を選んだ場合は `true` と表示されます。
`true` は「取り出すときは CRLF、記録するときは LF に変換する」という意味です。

`dev-environment` リポジトリには `.gitattributes` があり、ファイルの種類ごとに改行コードを固定しています。
そのため、`autocrlf` が `true` でも、シェルスクリプトや `gradlew` は LF のまま取り出されます。

```text
* text=auto eol=lf
*.bat text eol=crlf
*.cmd text eol=crlf
*.ps1 text eol=crlf
*.jar binary
gradlew text eol=lf
```

!!! warning "`.gitattributes` が無いリポジトリでは"
    `autocrlf=true` のままだと、`.sh` ファイルが CRLF で取り出され、
    実行時に `bad interpreter` や `$'\r': command not found` が出ることがあります。
    その場合は [つまずき集](../appendix/troubleshooting.md) を見てください。

### 4. GitHub に認証する（HTTPS か SSH）

GitHub からリポジトリを取得したり、変更を送ったりするには認証が必要です。
方法は 2 つあります。チームの決まりがあればそれに従います。

| 方法 | 仕組み | 向いている場面 |
|---|---|---|
| HTTPS | Git Credential Manager がブラウザでログインさせ、資格情報を Windows に保存する | 初めての人、プロキシ環境（443 番ポートしか通らない） |
| SSH | 自分の PC で鍵のペアを作り、公開鍵を GitHub に登録する | 鍵の管理に慣れている人 |

#### HTTPS の場合（おすすめ）

Git for Windows には Git Credential Manager が同梱されています。
初めて `git clone` や `git push` をすると、ブラウザが開いて GitHub へのログインを求められます。
ログインすると資格情報が保存され、次回からは聞かれません。

#### SSH の場合

```bash
ssh-keygen -t ed25519 -C "<あなたのメールアドレス>"
cat ~/.ssh/id_ed25519.pub
```

表示された公開鍵（`.pub` の中身）を、GitHub の Settings → SSH and GPG keys に登録します。
秘密鍵（`.pub` が付かないファイル）は、だれにも渡さず、チャットにも貼りません。

**確認**:

```bash
ssh -T git@github.com
```

`Hi <ユーザー名>! You've successfully authenticated` と表示されれば OK です。

!!! danger "パスワードやトークンをファイルに書かない"
    GitHub のパスワードや個人アクセストークンを、ソースや設定ファイル、URL に書かないでください。
    一度コミットすると履歴に残り、消すのが非常に大変です。

### 5. dev-environment を clone する

作業用のフォルダ（例: `C:\work`）を作り、Git Bash で次を実行します。
URL はチームから案内されたものを使います。

```bash
mkdir -p /c/work && cd /c/work
git clone https://github.com/<組織名>/dev-environment.git
cd dev-environment
```

**確認**:

```bash
git status
ls
```

`On branch main` と表示され、`local`・`sample-app`・`cloud` などのフォルダが見えれば OK です。

!!! tip "フォルダの場所"
    OneDrive の同期フォルダや、日本語・空白を含むパスの下は避けてください。
    ビルドが遅くなったり、ツールがパスを正しく扱えなかったりすることがあります。

## サンプルアプリでは

`dev-environment` リポジトリの次のファイルが、Git の扱いに関係しています。

- `.gitattributes`: 改行コードをファイルの種類ごとに固定します。`gradlew` は LF、`gradlew.bat` と `.ps1` は CRLF です
- `.gitignore`: コミットしないファイルを指定します。先頭に秘密情報の行があります

```text
# secrets
.env
.env.*
!.env.example
*.tfvars
!*.tfvars.example
backend.hcl
```

`.env`（パスワードなどを書くファイル）はコミットされず、見本の `.env.example` だけがコミットされます。
この仕組みは [10-04 コンテナとローカル環境](10-04-docker-local.md) で使います。

- `.editorconfig`: エディタに文字コード（UTF-8）と改行コード（LF）を伝えます。VS Code は拡張機能なしでも一部を読み取ります

## もし Git がなかったら？

ソースを共有フォルダやメールでやり取りすることになり、「どれが最新か」「だれが何を変えたか」が分からなくなります。
不具合が見つかっても、どの変更で入り込んだかを調べられません。

また、改行コードの決まりが無いと、Windows で編集しただけで全行が差分になり、
レビューで本当の変更が埋もれてしまいます。
ブランチと PR を使った日々の流れは [Git の流れとレビュー](../20-basics/20-18-git-flow-review.md) で学びます。

## 理解度チェック

1. `git config --global user.email` を設定しないと、どんな困りごとが起きますか。
2. `core.autocrlf=true` の意味を説明してください。
3. `.gitattributes` で `gradlew text eol=lf` と指定しているのはなぜですか。
4. HTTPS と SSH の認証で、GitHub に登録・保存するものはそれぞれ何ですか。
5. `.env` がコミットされないのは、どのファイルのどの指定によるものですか。

??? note "答え"
    1. コミットの作者が正しく記録されず、GitHub のアカウントとも紐づかないため、履歴を追えなくなります。
    2. 取り出すとき（checkout）は LF を CRLF に、記録するとき（commit）は CRLF を LF に変換する設定です。
    3. `gradlew` はシェルスクリプトで、CRLF だと Git Bash や Linux（CI）で実行できなくなるためです。
    4. HTTPS は Git Credential Manager がログイン後の資格情報を Windows に保存します。SSH は自分で作った公開鍵を GitHub に登録します。
    5. `.gitignore` の `.env` と `.env.*` の行です。`!.env.example` で見本だけは除外の対象外にしています。

## コードを読むときの確認観点

- [ ] リポジトリに `.gitattributes` があり、スクリプトの改行コードが固定されているか
- [ ] `.gitignore` に `.env` などの秘密情報のファイルが入っているか
- [ ] 見本のファイル（`.env.example` など）に本物のパスワードが書かれていないか
- [ ] コミットの作者名とメールアドレスが業務用のものになっているか
