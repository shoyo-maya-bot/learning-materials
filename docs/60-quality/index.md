# 60 設計品質

この章群では、設計書を書く・レビューする・品質を測るための考え方を学びます。
コードを書く力に加えて、「伝わる設計書」と「役に立つレビュー」を作る力を身に付けます。
目安の期間は **3 日** です。

!!! abstract "この章群の到達目標"
    - 読み手を意識し、あいまいな言葉や例外ケースの漏れが無い設計書を書ける
    - 根拠と重要度（MUST / WANT / NITS / Q）を付けて、レビューの指摘を書ける
    - AI のレビュー結果を下書きとして扱い、採否を自分で判断できる
    - 指摘の分類・密度・カバレッジ・トレーサビリティを、プロセスの改善に使える

## チームの道具との関係

この章群は、チームで使っている次の道具の考え方に沿っています。
道具の使い方そのものは、それぞれのリポジトリの README を参照してください。

| 道具 | この章群で扱う考え方 |
| --- | --- |
| ai-coding の `guidelines/` | 設計書に書くこと、レビュー観点（RP1〜RP5）、品質ゲート、対応表 |
| office-review | 設計書レビューの観点（`config/checks.yaml`）と指摘の書き方 |
| design-diff | 設計書の新旧差分、設計書と OpenAPI の整合チェック |
| quality-analytics | 指摘の分類（A / B / C）と真因（R1〜R6）、傾向の分析 |

!!! warning "数字は人の評価に使わない"
    60-03 で扱う指摘数やカバレッジは、プロセスを良くするための数字です。
    個人の評価に使うと、指摘が出にくくなり、かえって品質が下がります。
