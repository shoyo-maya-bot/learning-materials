# 60-01 設計書の書き方

!!! note "読むコードは `exercise-base` ブランチ"
    この章の引用と行番号は、dev-environment の **`exercise-base` ブランチ**（弱いところを直す前の sample-app）に合わせています。
    `main` は修正済みです。切り替え方と修正後との比べ方は [30 実ソース読解](../30-reading/index.md#exercise-base) を参照してください。

!!! abstract "到達目標"
    - 設計書の読み手（実装者・テスト担当・運用担当・AI）が何を必要とするかを説明できる
    - 「適宜」「など」「必要に応じて」のようなあいまいな言葉を、確定した記述に直せる
    - 例外ケース（0 件・上限・重複・再実行・同時実行・タイムアウト）の漏れを見つけられる
    - 設計書と他の成果物（OpenAPI・メッセージ表・DB 定義・コード）の整合を確かめられる

## 何か

**設計書** は、「何を、どう作るか」を、作る人と確かめる人が同じ理解を持てるように書いた文書です。
この教材では、API 設計書とバッチ設計書を主に扱います。

設計書には、複数の読み手がいます。

| 読み手 | 知りたいこと |
| --- | --- |
| 実装者 | 入力・処理手順・出力・エラー時の扱い |
| テスト担当 | 結果ごとの期待値（ステータス・メッセージ ID・件数） |
| 運用担当 | 起動のタイミング、終了コード、再実行の手順 |
| AI（コード生成） | 上のすべて。書いていないことは推測で埋める |
| レビュアー | 上位文書（要件・基本設計）と合っているか |

最後の AI の行が、近年とくに大切になりました。
ai-coding のガイドライン（`design-doc-requirements.md`）は、冒頭で次のように述べています。

> AI は書いていないことを推測で埋めます。推測させないために、設計書に次を明記します。

人も同じです。
書いていないことは、読み手ごとに違う推測で埋められます。

## なぜ必要か

設計書のあいまいさは、そのまま実装のばらつきになります。
「エラーの行は適宜処理する」と書けば、ある人は行を飛ばし、ある人は全体を止めます。
どちらも設計書には違反していないので、レビューでも見逃されます。

例外ケースの漏れは、テストでも見つかりにくい欠陥です。
テスト担当は設計書から期待値を決めるので、設計書に無いケースはテストもされません。
本番で初めて「0 件のときに異常終了した」と分かります。

他の成果物とのずれは、作業の途中で手戻りを生みます。
設計書では桁 50、DB では 60、OpenAPI では 40、という状態では、どれが正しいか決めるところからやり直しです。

## どうやるか

### あいまいな言葉を確定させる

次の言葉が出てきたら、具体的に書き直します。
office-review の観点 `ALL-003`「『など』『適宜』『必要に応じて』で範囲がぼかされていない」に当たります。

| あいまいな言葉 | 何が決まっていないか | 書き直しの例 |
| --- | --- | --- |
| 適宜 | 誰が・いつ・どうするか | 「形式エラーの行は飛ばし、行番号と理由を警告ログに出す」 |
| など | 対象の範囲 | 「対象: 会員・注文・商品の 3 つ」（全部を列挙する） |
| 必要に応じて | 条件 | 「入力ファイルが 0 件のとき」 |
| 大量の | 件数 | 「1 日最大 10 万件」 |
| 速やかに | 時間 | 「受付から 5 分以内」 |
| 正しく | 基準 | 「quantity が 1〜999 の整数」 |

!!! failure "悪い例"
    ```text
    STEP2 注文を登録する。
    形式に誤りがある行は適宜エラーとする。
    既に登録済みの注文などは必要に応じてスキップする。
    ```

!!! success "良い例"
    ```text
    STEP2 注文を登録する。
    - 形式エラーの行は登録せずに飛ばし、「行番号: 理由」を警告ログ（APPW0001）に出して続行する
      形式エラーは次の 6 種類: 列数が 4 でない / order_no が空 / member_id が数値でない /
      product_code が空 / quantity が数値でない / quantity が 1〜999 の範囲外
    - order_no が既に登録済みの行は登録しない（件数を「重複」として数える）
    - 形式エラーが 1 行以上あれば終了コード 4、無ければ 0
    ```
    対象を列挙し、条件を確定させています。
    「など」を使うなら、確定した一覧を別に置き、例示であることを明記します。

### 例外ケースを洗い出す

正常の流れを書いたら、次の観点で「そうでないとき」を書き足します。
quality-analytics の分類では、ここの漏れは真因 R2「前提・制約の確認漏れ」に当たります。

| 観点 | 問い |
| --- | --- |
| 0 件 | 入力が空・見出しだけのときはどうするか |
| 上限・境界 | 最大件数・最大桁・最小値ちょうどのときは |
| 重複 | 同じキーが 2 回来たら |
| 再実行 | 途中で異常終了した後に再実行したら（冪等性） |
| 同時実行 | 同じ処理が 2 つ同時に動いたら |
| 外部の障害 | 相手が応答しない・遅いとき（タイムアウトと再試行） |
| 日時 | 日付の境目・タイムゾーン・月末 |
| 権限 | 他人のデータを指定されたら（[50-06](../50-api/50-06-auth.md)） |

### 他の成果物と突き合わせる

設計書の数字や名前は、他の成果物にも現れます。
提出前に、少なくとも次を突き合わせます。

| 突き合わせる相手 | 確かめること | 道具 |
| --- | --- | --- |
| 上位文書（要件定義・基本設計） | 機能・項目・条件が矛盾していない | 目視（office-review `ALL-005`） |
| OpenAPI | 項目・必須・型・桁 | design-diff `spec` |
| 前の版の設計書 | 変えたつもりの箇所だけが変わっている | design-diff `excel` |
| メッセージ表 | ID・本文・埋め込み値 | 目視（`messages.properties` と） |
| DB 定義 | 列の型・桁・制約 | 目視 |

### 書く形をそろえる

ai-coding のガイドラインでは、設計書に Front Matter（`id`・`title`・`type`・`status`）を付けます。
`status` が `approved` になったものだけを実装に使います。
これにより、どの版の設計書から作ったかを後から追えます（[60-03](60-03-measure-quality.md) のトレーサビリティ）。

## サンプルアプリでは

sample-app には設計書そのものは含まれていません。
しかし、コードのコメントに、設計書に書くべき内容が現れています。
ここから「設計書に何が書かれていたはずか」を読み取れます。

`sample-app/src/main/java/com/example/sample/order/OrderImportService.java` の Javadoc です。

```java
/**
 * 注文ファイル取込（JOB0001）の業務ロジック.
 *
 * <p>入力: CSV（1 行目は見出し {@code order_no,member_id,product_code,quantity}）。
 * 形式エラーの行は飛ばして続行し、結果に行番号と理由を残す。登録済みの注文番号は飛ばす（冪等）。
 */
```

入力の形式、エラー時の扱い（続行）、重複の扱い（冪等）が、あいまいな言葉を使わずに書かれています。

`sample-app/src/main/java/com/example/sample/order/batch/OrderImportJob.java` には、終了コードが書かれています。

```java
 * <p>終了コード: 0 正常 / 4 形式エラーの行あり（取込は続行）/ 8 異常終了。実案件では運用設計の終了コード体系に合わせる。
```

整合の例として、数量の範囲を見ます。
`OrderImportService.parse` の入力チェックは次のとおりです。

```java
if (quantity < 1 || quantity > 999) {
    throw new IllegalArgumentException("quantity は 1〜999 です（" + quantity + "）");
}
```

`dev-environment` の `local/db/init/01_schema.sql` の DB 定義は次のとおりです。

```sql
quantity     INTEGER     NOT NULL CHECK (quantity BETWEEN 1 AND 999),
```

コードと DB で「1〜999」がそろっています。
設計書の入力項目表にも同じ値が書かれ、3 か所が一致している状態が目標です。
どれか 1 か所だけ変えると、たとえば「コードは通すが DB で弾かれて異常終了する」といった不具合になります。

## もし設計書の書き方の基準がなかったら？

「エラーは適宜処理する」と書かれた設計書から、2 人の開発者が 2 つのバッチを作ったとします。
1 人は形式エラーの行を飛ばして続行し、もう 1 人は最初のエラーで全体を止めました。
運用担当は、同じ種類のエラーなのに、ジョブによって対応手順を変える必要が出ます。

AI にコードを書かせる場合、この問題はさらに大きくなります。
AI は迷わずに推測で埋め、それらしいコードを素早く出します。
レビュアーがそのコードを見ても、設計書にあいまいさがある以上、誤りと言い切れません。
設計書の質が、そのままコードの質の上限になります。

## 理解度チェック

1. 「既に登録済みの注文などは必要に応じてスキップする」の問題点を 2 つ挙げてください。

    ??? note "答え"
        「など」で対象の範囲がぼかされている点と、「必要に応じて」でスキップする条件が決まっていない点です。
        対象を列挙し、条件を確定させて書き直します。

2. 例外ケースの観点「再実行」で、注文取込バッチについて確かめるべきことは何ですか。

    ??? note "答え"
        途中で異常終了した後に再実行したとき、登録済みの注文を二重に登録しないかです。
        sample-app では、`insertIfAbsent` で登録済みの注文番号を飛ばすことで冪等にしています。

3. 設計書の入力項目の桁と OpenAPI の `maxLength` のずれは、どの道具で見つけられますか。

    ??? note "答え"
        design-diff の `spec` コマンドです。
        API 定義書（Excel）と OpenAPI を比べ、項目・必須・型・桁の差分を出します。

4. 「AI は書いていないことを推測で埋める」ことが、設計書の書き方にどう影響しますか。

    ??? note "答え"
        AI に推測させないよう、実装クラス名・メッセージ表・テーブル操作・エラー時の扱いなどを明記する必要があります。
        設計書のあいまいさが、そのまま生成されたコードのばらつきになるからです。

## コードを読むときの確認観点

- [ ] コードのエラー時の扱い（続行か停止か）が、設計書に明記されているか
- [ ] 入力チェックの範囲・桁が、設計書・DB 定義・OpenAPI と一致しているか
- [ ] メッセージ ID と本文が、設計書のメッセージ表と一致しているか
- [ ] 0 件・重複・再実行のときの動きが、設計書とコードの両方で決まっているか
- [ ] 設計書に無い動き（推測で足された処理）がコードに入っていないか
