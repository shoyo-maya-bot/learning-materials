# 60-02 レビュー

!!! abstract "到達目標"
    - レビューの観点（チェックリスト）を使って、設計書やコードを確かめられる
    - 根拠・重要度（MUST / WANT / NITS / Q）・提案を付けて、指摘を書ける
    - 観点の「無効となるケース」を確かめ、誤指摘を減らせる
    - AI のレビュー結果を下書きとして扱い、採否を自分で判断できる

## 何か

**レビュー** は、作成者以外の人が成果物を読み、誤りや改善点を見つける作業です。
対象は設計書・コード・テスト・OpenAPI などです。

レビューの結果は **指摘** として残します。
指摘には、チームで共通の **重要度** を付けます。
この区分は ai-coding・office-review・quality-analytics の 3 つのリポジトリで共通です。

| 重要度 | 意味 | 例 |
| --- | --- | --- |
| MUST | 直さないと問題が起きる（必須の修正） | 二重登録が起きる、設計書と結果のステータスが違う |
| WANT | 直すと良くなる（望ましい修正） | 処理を分けると読みやすい、性能の目安を書くとよい |
| NITS | 表記・体裁の軽微な点 | 誤字、インデント、import の書き方 |
| Q | 質問 | 「この場合はどうなる想定ですか」 |

**観点** は、レビューで確かめる項目の一覧（チェックリスト）です。
設計書は office-review の `config/checks.yaml`、コードやテストは ai-coding の `guidelines/review-checklists.md`（RP1〜RP5）にあります。

## なぜ必要か

作成者は、自分の書いたものの誤りに気付きにくいものです。
頭の中にある「書いたつもり」の内容で、足りない部分を補って読んでしまうからです。

ただし、レビューは何でも指摘すればよいわけではありません。
根拠のない指摘や、好みの押し付けは、作成者の時間を奪います。
重要度が無いと、作成者は誤字と重大な欠陥を同じ重さで扱うことになります。
指摘の書き方をそろえることで、レビューが「品質を上げる作業」になります。

## どうやるか

### 観点を決めてから読む

漫然と読むと、目に付きやすい表記の誤りばかりが見つかります。
先に観点を決め、1 つずつ確かめます。

| 対象 | 観点の例 | 出どころ |
| --- | --- | --- |
| 設計書（共通） | あいまいな表現、未決事項、上位文書との整合 | office-review `ALL-001`〜`ALL-005` |
| API 設計書 | 結果ごとのステータスとメッセージ ID、冪等性、認可 | office-review `API-003`・`API-004`・`API-006` |
| バッチ設計書 | エラーと終了コード、再実行、コミット単位 | office-review `BAT-004`〜`BAT-006` |
| コード | 層の責務、例外とメッセージ ID、SQL の `#{}`、トランザクション境界 | ai-coding RP2 |
| テスト | 期待値が設計書由来か、異常系・境界値、アサーションの強さ | ai-coding RP3 |

### 指摘の書き方

1 つの指摘には、次の 4 つを書きます。

1. **場所**: ファイルと行、または設計書の章
2. **重要度**: MUST / WANT / NITS / Q
3. **根拠**: 何を見て、何に照らして問題と判断したか
4. **提案**: どう直せばよいか（Q のときは何を知りたいか）

!!! failure "悪い例"
    ```text
    ここ、おかしくないですか？
    ```
    ```text
    この書き方は良くないです。直してください。
    ```
    場所・根拠・重要度が無く、作成者は何をどこまで直せばよいか分かりません。

!!! success "良い例"
    ```text
    [MUST] MemberService.java 27〜31 行目
    根拠: existsByEmail で重複を確かめてから insert するまでの間に、同じメールアドレスの登録が
    同時に来ると、両方とも重複なしと判断します。2 件目の insert は DB の一意制約（member.email UNIQUE）
    で失敗しますが、その例外は ApiExceptionHandler で扱われないため 500 になります。
    設計書の結果表では「メールアドレス登録済み → 409（APPE0003）」です。
    提案: 一意制約違反の例外を捕まえて BusinessException(EMAIL_ALREADY_USED) に変換してください。
    ```

GitHub のプルリクエストでは、本文の先頭に `[MUST]` のように重要度を書きます。
quality-analytics は、この先頭の表記を読んで重要度として集計します。

### 無効となるケースを確かめる

office-review の観点には、`invalid_when`（この観点を当てはめてはいけないケース）が書かれています。
指摘する前に、これに当たらないことを確かめます。

例: `API-004`「更新系 API の再送時の動きが決まっている」

```yaml
invalid_when: 参照系（GET）のみの API
```

照会しかない API に「冪等性が書かれていない」と指摘するのは誤指摘です。
同じように、`ALL-003`（あいまいな表現）は「例示であることが明記され、確定した一覧が別の箇所にある場合」は無効です。
無効となるケースの確認は、AI のレビューでも人のレビューでも必須です。

### AI のレビューは下書き

office-review や Copilot の AI レビューは、観点を漏れなく当てはめるのが得意です。
一方で、次のような誤りもします。

- 既に書いてあることを「無い」と指摘する（読み落とし）
- 無効となるケースに当たるのに指摘する
- 根拠があいまいなまま断定する

そのため、AI のレビュー結果は **下書き** として扱います。
人が指摘ごとに採択か不採択かを判断し、最終判断の責任は人が持ちます。
ai-coding の品質ゲートでも、AI の判定表（N1〜N6）は「補助であり、最終判断は人（RP4）」と定めています。

不採択にした指摘も記録します。
office-review は採否を蓄積し、誤指摘の多い観点を直すために使います。

### 指摘を受ける側の心得

- 指摘は成果物に対するもので、人に対するものではありません
- MUST は直すか、直さない理由を返信します。黙って閉じません
- Q には答えを返信し、答えから欠陥が分かれば別の指摘として起票し直します
- 納得できない指摘は、根拠を示して議論します

## サンプルアプリでは

sample-app のコードを、レビューの観点で読んでみます。
次の 3 つは、実際のコードに対する指摘の例です。

1 つ目は、上の良い例で挙げた MUST の指摘です。
`sample-app/src/main/java/com/example/sample/member/MemberService.java` の `register` です。

```java
@Transactional
public Member register(String name, String email) {
    String normalized = email.trim().toLowerCase(java.util.Locale.ROOT);
    if (mapper.existsByEmail(normalized)) {
        throw new BusinessException(MessageIds.EMAIL_ALREADY_USED, normalized);
    }
    MemberRecord rec = new MemberRecord(name.trim(), normalized);
    mapper.insert(rec);
    return rec.toMember();
}
```

確認と登録の間に、同じメールアドレスの登録が同時に来ると、DB の一意制約で insert が失敗します。
`sample-app/src/main/java/com/example/sample/common/ApiExceptionHandler.java` はこの例外を扱わないので、409 ではなく 500 になります。
同時に登録されることはまれですが、結果のステータスが設計と変わるので MUST にしています。

2 つ目は NITS の例です。
同じ行の `java.util.Locale.ROOT` は、完全修飾名で書かれています。

```text
[NITS] MemberService.java 26 行目
根拠: 他のクラスは import して使っています（ApiExceptionHandler は java.util.Locale を import）。
提案: import java.util.Locale; を足し、Locale.ROOT と書くとそろいます。
```

動きは変わらないので NITS です。
quality-analytics の分類では B1（表記・体裁）に当たります。

3 つ目は Q の例です。
`sample-app/src/main/java/com/example/sample/order/OrderImportService.java` では、見出し行が不正なら `IllegalArgumentException` を投げます。

```java
if (lines.isEmpty() || !HEADER.equals(stripBom(lines.get(0)).trim())) {
    throw new IllegalArgumentException("見出し行が不正です（期待値: " + HEADER + "）");
}
```

```text
[Q] OrderImportService.java 27〜29 行目
入力ファイルが空（0 バイト）のときも「見出し行が不正」として終了コード 8 になります。
空ファイルは「0 件の正常終了」とする運用もありえますが、設計書ではどちらの想定でしょうか。
```

答えによっては、設計書に「0 件のとき」を書き足す指摘に変わります。

## もし指摘の書き方の決まりがなかったら？

「ここおかしい」とだけ書かれた指摘が 50 件届いたとします。
作成者は 1 件ずつ、どこが、なぜおかしいかを推測することになります。
重要度が無いので、誤字の修正と二重登録の修正を同じ順番で進めてしまいます。
期限が迫ると、重大な欠陥が後回しになるかもしれません。

AI の指摘を下書きとして扱わないと、誤指摘に合わせて正しい記述を書き換えてしまうことがあります。
「AI が言ったから」は根拠になりません。
採否を判断するのは人であり、その判断の記録が次のレビューを良くします。

## 理解度チェック

1. 指摘に書く 4 つの要素を挙げてください。

    ??? note "答え"
        場所、重要度（MUST / WANT / NITS / Q）、根拠、提案です。

2. 照会（GET）だけの API 設計書に、「再送時の二重登録の対策が書かれていない」と指摘するのは適切ですか。

    ??? note "答え"
        適切ではありません。
        観点 `API-004` の無効となるケース「参照系（GET）のみの API」に当たるので、誤指摘です。

3. sample-app の `MemberService.register` に対する指摘が MUST になるのはなぜですか。

    ??? note "答え"
        同時に登録が来ると、一意制約違反の例外が `ApiExceptionHandler` で扱われず、409 ではなく 500 になるからです。
        設計どおりの結果にならないので、直さないと問題が起きる MUST に当たります。

4. AI のレビュー結果を「下書き」として扱うとは、具体的にどうすることですか。

    ??? note "答え"
        指摘ごとに、根拠が正しいか・無効となるケースに当たらないかを人が確かめ、採択か不採択かを判断することです。
        不採択にした理由も記録し、観点の改善に使います。

5. Q の指摘に答えた結果、考慮漏れが分かったらどうしますか。

    ??? note "答え"
        考慮漏れを、新しい指摘（多くは MUST）として起票し直します。
        Q のまま閉じると、欠陥として数えられず、記録にも残りません。

## コードを読むときの確認観点

- [ ] レビューの前に、使う観点（チェックリスト）を決めたか
- [ ] 指摘に場所・重要度・根拠・提案があるか
- [ ] 根拠が「自分の好み」ではなく、設計書・規約・観点に照らしたものか
- [ ] 観点の無効となるケースに当たらないことを確かめたか
- [ ] AI の指摘を、採否を判断せずにそのまま作成者に渡していないか
- [ ] 確認と登録の間の同時実行など、1 人で動かしたときには起きない問題を見たか
