# 60-03 品質を測る

!!! note "読むコードは `exercise-base` ブランチ"
    この章の引用と行番号は、dev-environment の **`exercise-base` ブランチ**（弱いところを直す前の sample-app）に合わせています。
    `main` は修正済みです。切り替え方と修正後との比べ方は [30 実ソース読解](../30-reading/index.md#exercise-base) を参照してください。

!!! abstract "到達目標"
    - レビュー指摘を、種類（A 欠陥 / B ノイズ / C 確認）と真因（R1〜R6）で分類できる
    - 指摘の密度とカバレッジの意味と、数字だけで判断してはいけない理由を説明できる
    - トレーサビリティ（設計書の要件 → 実装 → テスト）の状態を読める
    - 品質の数字を、個人の評価ではなくプロセスの改善に使う理由を説明できる

## 何か

品質を測るとは、成果物やプロセスの状態を数字や分類で表すことです。
この章では、次の 4 つを扱います。

| 測るもの | 答える問い | 道具 |
| --- | --- | --- |
| 指摘の分類と真因 | どんな欠陥が、なぜ作り込まれたか | quality-analytics |
| 指摘の密度 | どの成果物に欠陥が集中しているか | quality-analytics |
| カバレッジ | テストがコードのどこを通ったか | JaCoCo（Gradle の `jacoco` プラグイン） |
| トレーサビリティ | 設計書の要件が、実装とテストまでつながっているか | ai-coding の対応表と `spec-trace` |

## なぜ必要か

「レビューで 100 件指摘した」だけでは、品質が良いのか悪いのか分かりません。
100 件が全部誤字なら成果物の中身は良く、100 件が全部記載漏れなら作り方に問題があります。
分類して初めて、何を直せばよいかが見えます。

また、同じ種類の欠陥を繰り返さないためには、指摘を直すだけでは足りません。
「なぜその欠陥が作り込まれたか」（真因）を知り、作り方の側を直す必要があります。
たとえば例外ケースの漏れが多いなら、設計書のテンプレートに例外ケースの表を足します。

## どうやるか

### 指摘を分類する

quality-analytics の分類（`docs/CLASSIFICATION.md`）では、指摘ごとに種類を付けます。

| 種類 | 区分 | 意味 |
| --- | --- | --- |
| A 欠陥 | A1 記載漏れ / A2 誤り・矛盾 / A3 曖昧 | 品質に効く指摘 |
| B ノイズ | B1 表記・体裁 / B2 好み・代案 / B3 対象外・誤指摘 | 直しても品質が変わらない指摘 |
| C 確認 | C1 質問・確認 | 回答によって A に変わることがある |

種類は、重要度ではなく **内容** で決めます。

| 迷う例 | 分類 | 理由 |
| --- | --- | --- |
| NITS だが、桁の数字が間違っている | A2 | 重要度ではなく内容で決める |
| MUST だが「この書き方の方が好み」 | B2 | 直さなくても品質は変わらない |
| 「適宜」「など」「必要に応じて」 | A3 | 実装者によって振る舞いが変わる |
| 既に書いてあることへの指摘 | B3 | 指摘者の読み落とし |

### 真因を付ける

欠陥（A）には、真因を付けます。

| 真因 | 典型的な指摘 | 手当ての例 |
| --- | --- | --- |
| R1 業務・要件の理解不足 | 業務の流れと違う | 業務の説明会、用語集 |
| R2 前提・制約の確認漏れ | 上限・境界・同時実行・0 件 | 例外ケースのチェックリスト |
| R3 他成果物との整合確認漏れ | 上位の設計書や一覧と食い違う | 突き合わせの手順、design-diff |
| R4 標準・規約の理解不足 | 命名規則・記述ルール違反 | 規約の要点の共有、機械チェック |
| R5 セルフチェック不足 | 転記ミス、修正漏れ | 提出前のセルフチェックリスト |
| R6 記述の技術 | 内容は正しいが伝わらない | テンプレート・良い例の共有 |

!!! failure "悪い例"
    ```text
    真因: 担当者の注意不足
    対策: 今後は気を付ける
    ```
    人の注意力に頼る対策は、次も同じことが起きます。

!!! success "良い例"
    ```text
    真因: R2 前提・制約の確認漏れ（0 件のときの動きが設計書に無かった）
    対策: バッチ設計書のテンプレートに「例外ケース（0 件・重複・再実行）」の表を足す
    ```
    仕組み（テンプレート・チェックリスト）を変えています。

指摘の本文だけで真因が分からないときは、空のままにします（推測で埋めない）。
振り返りの場で作成者と話して付けると、最も正確になります。

### 密度を見る

**密度** は、成果物の大きさあたりの指摘数です（例: 件 / ページ、件 / 1,000 行）。
大きな成果物ほど指摘が多いのは当然なので、大きさで割って比べます。

密度は、単独では良し悪しを決められません。

- 密度が高い: 欠陥が多い、または丁寧にレビューされた
- 密度が低い: 品質が良い、またはレビューが浅かった

そのため、種類（A の割合）と合わせて見ます。
quality-analytics は、欠陥の密度が平均＋1σ を超える成果物を所見として挙げます。
これは「詳しく見るべき候補」であり、即座に「悪い成果物」という判定ではありません。

### カバレッジを見る

**カバレッジ** は、テストを実行したときに通ったコードの割合です。
**分岐網羅**（ブランチカバレッジ）は、`if` の真と偽のように、分岐の両側を通ったかを数えます。

ai-coding の品質ゲート `D4 分岐網羅` では、Service・Job の分岐網羅率を既定 80% 以上としています。

カバレッジは「通ったか」しか分かりません。
「正しく確かめたか」は分かりません。

!!! failure "悪い例"
    ```java
    // 例: sample-app には無いテスト
    @Test
    void importLines() {
        List<String> lines = List.of(OrderImportService.HEADER, "A001,1,P-01,2");
        service.importLines(lines);
        ImportResult second = service.importLines(lines);
        assertThat(second).isNotNull(); // 同じ行を通るが、ほとんど何も確かめていない
    }
    ```

!!! success "良い例"
    ```java
    // sample-app/src/test/java/com/example/sample/order/OrderImportServiceTest.java
    @Test
    void rerunIsIdempotent() {
        List<String> lines = List.of(OrderImportService.HEADER, "A001,1,P-01,2");
        service.importLines(lines);

        ImportResult second = service.importLines(lines);

        assertThat(second.imported()).isZero();
        assertThat(second.duplicated()).isEqualTo(1);
    }
    ```
    設計書の要件（再実行しても重複しない）を、期待値で確かめています。

2 つのテストは同じコードを通るので、カバレッジは同じです。
しかし、価値は大きく違います。
カバレッジは「テストされていない場所を見つける」ために使い、高ければ良いとは考えません。

### トレーサビリティを見る

**トレーサビリティ** は、設計書の要件から、実装・テストまでを追えることです。
ai-coding では、対応表（`traceability/specs/<機能>.yaml`）で要件ごとに状態を持ちます。

| 状態 | 条件 |
| --- | --- |
| pending | まだ実装されていない |
| implemented | 実装の箇所（ファイルと関数）が実在する |
| proven | テストが実在し、アサーションがある |

`spec-trace check --require proven` が通れば、全要件がテストまでつながっています。
設計書が承認後に変わったことも、ハッシュの比較（`D8 設計書ドリフト`）で検知できます。

## サンプルアプリでは

sample-app には、指摘の記録や対応表はありません。
測る仕組みとして実在するのは、カバレッジの計測です。
`sample-app/build.gradle` を見ます。

<!-- src: sample-app/build.gradle @exercise-base -->
```groovy
plugins {
    id 'java'
    id 'jacoco'
```

<!-- src: sample-app/build.gradle @exercise-base -->
```groovy
tasks.named('test') {
    useJUnitPlatform {
        excludeTags 'karate'
    }
    finalizedBy jacocoTestReport
}
```

<!-- src: sample-app/build.gradle @exercise-base -->
```groovy
jacocoTestReport {
    reports {
        xml.required = true
        html.required = true
    }
}
```

- `./gradlew test` の後に、カバレッジのレポートが作られます（`finalizedBy jacocoTestReport`）
- HTML は人が見るため、XML は CI などの機械が読むためです
- Karate の API テストは `test` から除外されているので、このカバレッジには含まれません

sample-app には、分岐網羅の閾値を確かめる設定（`jacocoTestCoverageVerification`）はありません。
閾値の確認は、ai-coding のテンプレートの品質ゲート（D4）で行います。

トレーサビリティの考え方は、sample-app のコメントにも表れています。
`OrderMapper.java` の Javadoc「再実行しても重複しない＝冪等」は設計書の要件です。
それを実装したのが `OrderMapper.xml` の `insertIfAbsent` です。
それを確かめるテストが `OrderImportServiceTest` の `rerunIsIdempotent` です。
対応表では、この要件に実装（`OrderImportService#importLines`）とテスト（`OrderImportServiceTest#rerunIsIdempotent`）を結び付けて、proven にします。
ai-coding の `traceability.md` の対応表の例も、同じ組み合わせになっています。

## もし「改善のために測る」という前提がなかったら？

「指摘の少ない人ほど優秀」と評価すると、作成者はレビューを避け、レビュアーは指摘を控えるようになります。
指摘数は減りますが、欠陥は減っていません。
欠陥は、後の工程や本番で見つかるようになります。

「指摘の多いレビュアーほど優秀」と評価すると、表記や好みの指摘（B）が増えます。
作成者の時間が奪われ、本当の欠陥（A）が埋もれます。
「カバレッジ 100% 必須」を目標にすると、何も確かめないテストで数字だけを満たすようになります。

数字は、測った途端に「目標」になり、意味が変わってしまいます。
quality-analytics の README にもあるとおり、分析結果はプロセスの改善に使い、個人の評価に使わないでください。

## 理解度チェック

1. 重要度が NITS の指摘で「桁の数字が 50 ではなく 60 の誤り」とあったら、種類は何に分類しますか。

    ??? note "答え"
        A2（誤り・矛盾）です。
        種類は重要度ではなく内容で決めます。桁の誤りは品質に効く欠陥です。

2. 「0 件のときの動きが設計書に無かった」欠陥の真因と、仕組みとしての対策を答えてください。

    ??? note "答え"
        真因は R2（前提・制約の確認漏れ）です。
        対策は、設計書のテンプレートやセルフチェックリストに例外ケース（0 件・重複・再実行）の表を足すことです。

3. ある設計書の指摘密度が他より高いとき、すぐに「品質が悪い」と判断してはいけないのはなぜですか。

    ??? note "答え"
        欠陥が多い場合だけでなく、丁寧にレビューされた場合や、ノイズの指摘が多い場合にも密度は高くなるからです。
        種類（A の割合）と合わせて見ます。

4. 分岐網羅率が 100% でも、テストが十分とは言えないのはなぜですか。

    ??? note "答え"
        カバレッジはコードを「通ったか」しか示さず、正しく確かめたかは示さないからです。
        `isNotNull()` だけのテストでも、通れば網羅率は上がります。

5. sample-app の `./gradlew test` で作られるカバレッジに、Karate の API テストが含まれないのはなぜですか。

    ??? note "答え"
        `build.gradle` の `test` タスクが `excludeTags 'karate'` で Karate のテストを除外しているからです。
        Karate は起動中のアプリが要るので、別のタスク `karateTest` で実行します。

## コードを読むときの確認観点

- [ ] テストのアサーションが、設計書の要件を期待値で確かめているか（`isNotNull()` だけで済ませていないか）
- [ ] カバレッジのレポートで、テストを通っていない分岐が残っていないか（残すなら理由があるか）
- [ ] 実装した要件ごとに、対応するテストが特定できるか
- [ ] 指摘の対策が「気を付ける」ではなく、テンプレートやチェックリストなどの仕組みになっているか
- [ ] 品質の数字が、個人の評価ではなく改善の材料として使われているか
