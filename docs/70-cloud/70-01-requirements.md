# 70-01 上流工程と非機能要件

!!! abstract "到達目標"
    - V 字モデルで、上流の成果物がどのテストの基準になるかを説明できる
    - 「要求」と「要件」の違いを説明し、要求を合意できる要件に書き直せる
    - 非機能要件を 6 つの大項目で漏れなく洗い出し、数字で書ける
    - 稼働率・RTO・RPO を計算し、構成とコストへの影響を説明できる

## 何か

**上流工程** は、システムを作る前に「何を作るか」を決める工程です。
企画・要求定義・要件定義・基本設計がこれに当たります。
後半の詳細設計・実装・テストは **下流工程** と呼びます。

上流工程の仕事は、お客さんの言葉を「作れる・測れる・合意できる」文章に変えることです。
ここがあいまいだと、下流でどれだけ頑張っても手戻りになります。

工程と成果物、対応するテストの関係を **V 字モデル** で表します。

| 上流（左側） | 対応するテスト（右側） | 主な成果物 |
| --- | --- | --- |
| 企画・要求定義 | 受入テスト | 企画書、要求一覧、業務フロー（現状 / あるべき姿） |
| 要件定義 | 総合テスト | 要件定義書（機能要件・非機能要件） |
| 基本設計（外部設計） | 結合テスト | 画面・帳票・外部 IF の設計、方式設計、DB の論理設計 |
| 詳細設計（内部設計） | 単体テスト | モジュールの設計、DB の物理設計 |

左側で書いたことが、右側のテストの合格基準になります。
「速いこと」と書いても、テストでは合否を決められません。
「通常時の画面応答が 3 秒以内（95 パーセンタイル）」と書けば、そのまま総合テストの基準になります。

この章で使う用語を先にまとめます。

| 用語 | 意味 |
| --- | --- |
| 機能要件 | システムが **何をするか**（注文を登録する、会員を検索する） |
| 非機能要件 | **どのように** 動くか（速さ・止まらなさ・守り方・運用のしかた） |
| 稼働率 | 動いているべき時間のうち、実際に動いていた時間の割合 |
| RTO | Recovery Time Objective。止まってから **何時間で** 復旧するかの目標 |
| RPO | Recovery Point Objective。**どの時点の** データまで戻せればよいか（失ってよいデータの量） |
| 方式設計 | 非機能要件をどう実現するかを決める設計（構成・冗長化・バックアップ・監視など） |

## なぜ必要か

機能要件は、お客さんも開発者も意識しやすい部分です。
一方、非機能要件は「言われなかったから決めていない」状態になりがちです。
しかし、構成とコストを決めるのは、ほとんどが非機能要件です。

たとえば「止まらないこと」の度合いで、サーバーの台数・DB の構成・費用が何倍も変わります。
決めないまま作ると、次のどちらかになります。

- 必要以上に高い構成を作り、費用が合わなくなる
- 安い構成で作り、本番で障害が起きてから「そんなはずでは」となる

どちらも、後から直すほど高くつきます。
上流で数字を決め、お客さんと合意しておくことが、下流の手戻りを防ぐいちばんの手段です。

## どうやるか

### 要求を要件に書き直す

**要求** は、お客さんがやりたいことです。
**要件** は、システムがやると合意したことです。
要求をそのまま要件にせず、目的・優先度・やらないことを決めてから書きます。

!!! failure "悪い例"
    ```text
    申請をスマホでもできるようにする。
    ```
    どの端末・どのブラウザか、どの画面までかが決まっていません。

!!! success "良い例"
    ```text
    要件 REQ-012（優先度: Must）
    - 目的: 外出の多い営業担当が、帰社せずに申請できるようにする
    - 対象: 申請の入力・確認・取り下げの 3 画面
    - 環境: iOS / Android の、それぞれ最新 2 つの版の標準ブラウザ
    - 対象外: 承認画面（PC のみのまま。次の段階で検討）
    ```

優先度は **MoSCoW** で付けると、範囲の調整がしやすくなります。

| 区分 | 意味 |
| --- | --- |
| Must | 無いとリリースできない |
| Should | できれば入れたい。無くても回避策がある |
| Could | 余裕があれば入れる |
| Won't | 今回はやらない（やらないと書くこと自体が大切） |

### 機能要件を洗い出す

次の順で、抜けなく洗い出します。

1. 業務フロー（あるべき姿）を描き、人とシステムの境界を決める
2. ユースケース（誰が・何を・どうする）の一覧を作る
3. 機能の一覧（画面・バッチ・帳票・外部 IF）に落とす
4. データの作成・参照・更新・削除のタイミングを表にする（CRUD 表）

### 非機能要件を 6 つの大項目で洗い出す

IPA（情報処理推進機構）の **非機能要求グレード** は、非機能要件を 6 つの大項目に分けています。
この 6 つで確認すると、漏れが減ります。

| 大項目 | 何を決めるか | 書き方の例 | 構成への影響 |
| --- | --- | --- | --- |
| 可用性 | 稼働時間、止まってよい時間、復旧 | 稼働率 99.9%、RTO 4 時間、RPO 1 時間 | 冗長化、バックアップ、DR |
| 性能・拡張性 | 応答時間、処理量、将来の伸び | 同時 100 人、応答 3 秒以内、3 年でデータ 2 倍 | 台数、自動増減、キャッシュ |
| 運用・保守性 | 監視、バックアップ、運用の時間帯 | 24 時間監視、日次バックアップを 7 世代保持 | 監視の設計、運用の自動化 |
| 移行性 | 移行の方式・期間・データ量 | 旧システムから 500 万件を週末 1 回で移行 | 一括か段階か、移行の道具 |
| セキュリティ | 認証、権限、暗号化、ログ | 多要素認証、通信と保存データの暗号化、ログ 1 年保持 | 権限の設計、鍵の管理、WAF |
| システム環境・エコロジー | 法令、設置場所、制約 | データは国内のみに置く | リージョンの選び方 |

### 稼働率・RTO・RPO を計算する

稼働率は、1 桁上げるごとに止まってよい時間が 10 分の 1 になります。

| 稼働率 | 1 年で止まってよい時間 | 1 か月で止まってよい時間 |
| --- | --- | --- |
| 99% | 約 3.65 日 | 約 7.3 時間 |
| 99.9% | 約 8.8 時間 | 約 43 分 |
| 99.99% | 約 53 分 | 約 4.3 分 |

部品を **直列** につなぐと、稼働率は掛け算で下がります。
部品を **並列**（冗長化）にすると、稼働率は上がります。

```text
直列: 全体 = A × B
並列: 全体 = 1 −（1 − A）×（1 − B）
```

例: 稼働率 99.9% の Web サーバーと DB を直列につなぐと、0.999 × 0.999 ≒ 99.8% です。
Web サーバーを 2 台の並列にすると、その部分は 1 −（0.001 × 0.001）≒ 99.9999% になります。

RTO と RPO は、DR（災害対策）の方式を決める数字です（[70-05](70-05-aws-patterns.md)）。
RPO が 1 時間なら、少なくとも 1 時間ごとにデータを別の場所へ写す必要があります。

### 方式設計にまとめる

基本設計の中で、非機能要件を「どう実現するか」を書く部分が **方式設計** です。
最低限、次を書きます。

- システム構成図（論理構成・物理構成・ネットワーク構成）
- ソフトウェアの構成（OS・ミドルウェア・言語・フレームワークと、その版）
- 非機能要件の実現方式（冗長化・バックアップ・監視・セキュリティ）
- 外部システムとの連携方式（API・ファイル連携・メッセージ）
- 採用しなかった案と、その理由（[70-02](70-02-architecture-basics.md) の ADR）

### お客さんと合意する

非機能要件は「高いほどよい」と言われがちです。
数字を **費用とセットで** 示し、選んでもらいます。

!!! failure "悪い例"
    ```text
    お客さん: システムは絶対に止まらないようにしてください。
    開発者  : 承知しました。
    ```

!!! success "良い例"
    ```text
    開発者: 業務で止まると困る時間帯はいつですか。1 時間止まると、業務にどんな影響がありますか。
            稼働率 99.9%（年 8.8 時間まで停止）なら月 A 円、99.99%（年 53 分まで）なら月 B 円です。
            計画停止（メンテナンス）を稼働率に含めるかも決めさせてください。
    ```

決まったことはその日のうちに議事録で共有し、決まっていないことは課題管理表（担当・期限）で追います。
見積もりの方法は [00-01 案件の進め方](../00-management/00-01-project-management.md) を参照してください。

## サンプルアプリでは

dev-environment の `cloud/` は、sample-app を AWS で動かす構成です。
環境ごとの違いが、非機能要件の違いとして読めます。

```hcl title="cloud/environments/prod/main.tf（2〜8 行目）"
locals {
  name               = "${var.system_name}-prod"
  enable_nat_gateway = true
  db_instance_count  = 2
  protect_data       = true
  api_desired_count  = 2
}
```

```hcl title="cloud/environments/dev1/main.tf（2〜8 行目）"
locals {
  name               = "${var.system_name}-dev1"
  enable_nat_gateway = false
  db_instance_count  = 1
  protect_data       = false
  api_desired_count  = 1
}
```

| 項目 | dev1 | prod | 非機能要件の大項目 |
| --- | --- | --- | --- |
| `api_desired_count` | 1 | 2 | 可用性（1 台が止まっても動き続ける） |
| `db_instance_count` | 1 | 2 | 可用性（DB の切り替え先を持つ） |
| `protect_data` | false | true | 運用・保守性（誤って消さない） |
| `enable_nat_gateway` | false | true | 環境の制約と費用 |

本番だけ台数を増やしているのは、「本番は止めない、開発は安く」という要件を構成に表したものです。
コードの構造は同じで、値だけを変えています。

RPO に関わる値は、DB のモジュールにあります。

```hcl title="cloud/modules/aurora-postgres/variables.tf（46〜49 行目）"
variable "backup_retention_days" {
  type    = number
  default = 7
}
```

自動バックアップを 7 日分残す設定です。
Aurora は、この期間の中の任意の時点に戻せます（ポイントインタイムリカバリ）。
ただし、同じリージョンの中のバックアップです。
「リージョン全体の障害でも RPO 1 時間」という要件なら、この設定だけでは足りません。

`sample-app/src/main/java/com/example/sample/order/batch/OrderImportJob.java` の Javadoc にある、
「0 正常 / 4 形式エラーの行あり / 8 異常終了」の終了コードも、運用・保守性の要件です。
運用担当が、監視と再実行の手順を決めるための約束です（[30-13](../30-reading/30-13-batch-exit-code.md)）。

## もし非機能要件を決めなかったら？

本番の DB が 1 台構成のまま、リリースしたとします。
ある日、DB のあるデータセンターで障害が起き、サービスが 6 時間止まりました。
お客さんは「止まらないと思っていた」と言い、開発側は「そういう要件はなかった」と言います。
どちらも間違っていませんが、信頼は失われ、急な構成変更で費用も時間もかかります。

逆に、「念のため」とすべてを最高の構成にすると、費用が予算を大きく超えます。
数字で合意していれば、99.9% で十分な業務に 99.99% の費用を払うことはありません。
非機能要件は、品質と費用のつり合いを、お客さんと一緒に決めるためのものです。

## 理解度チェック

1. 「レスポンスが速いこと」という要件の問題点と、書き直しの例を答えてください。

    ??? note "答え"
        合否の基準が無く、総合テストで判定できない点が問題です。
        例: 「通常時（同時 100 人）の画面応答が、95 パーセンタイルで 3 秒以内」と書きます。

2. 稼働率 99.9% の部品 A・B・C を直列につないだときの、全体の稼働率はおよそいくつですか。

    ??? note "答え"
        0.999 × 0.999 × 0.999 ≒ 0.997、つまり約 99.7% です。
        直列の部品が増えるほど、全体の稼働率は下がります。

3. RTO と RPO の違いを、例を使って説明してください。

    ??? note "答え"
        RTO は復旧までの時間、RPO は戻せるデータの時点です。
        例: 「4 時間以内に再開し（RTO）、障害の 1 時間前までのデータは残っていること（RPO）」。

4. sample-app の prod 環境で API を 2 台にしているのは、6 大項目のどれに当たりますか。

    ??? note "答え"
        可用性です。
        1 台が止まっても、もう 1 台で処理を続けられるようにしています。

5. 要件定義で「やらないこと（Won't）」を書く理由は何ですか。

    ??? note "答え"
        範囲の認識のずれを防ぐためです。
        書かないと、お客さんは「入っているはず」と考え、後から追加の作業や費用の争いになります。

## コードを読むときの確認観点

- [ ] 要件定義書の非機能要件 6 大項目すべてに、数字の目標があるか
- [ ] 稼働率・RTO・RPO が、構成（台数・バックアップ・DR）と合っているか
- [ ] 環境ごとの違い（台数・削除保護など）が、要件のとおりに設定されているか
- [ ] バックアップの保持期間と場所が、RPO と災害の想定を満たしているか
- [ ] 終了コードやログの出し方が、運用の要件（監視・再実行の手順）と合っているか
