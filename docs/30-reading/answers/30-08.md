# 30-08 解答

[30-08 Mapper と SQL](../30-08-mapper-sql.md) の演習の解答です。

## 演習 1

### 解答

| 対応 | Java 側 | XML 側 |
| --- | --- | --- |
| `namespace` | `MemberMapper.java` 1 行目の `package com.example.sample.member;` と 8 行目の `interface MemberMapper` | `MemberMapper.xml` 3 行目 `namespace="com.example.sample.member.MemberMapper"` |
| `id` | `MemberMapper.java` 12 行目のメソッド名 `existsByEmail` | `MemberMapper.xml` 9 行目 `id="existsByEmail"` |
| `#{...}` | 12 行目の引数 `String email` | 10 行目 `#{email}` |
| `resultType` | 12 行目の戻り値 `boolean` | 9 行目 `resultType="boolean"` |

### 理由（コードの場所）

- MyBatis は「`namespace` + `.` + `id`」で SQL を探します。
  `com.example.sample.member.MemberMapper.existsByEmail` が、インタフェースのメソッドの完全な名前と一致します。
- 引数が 1 つの単純な値のときは、`#{...}` の名前でその引数を参照します。
- `SELECT EXISTS (...)` は PostgreSQL で真偽値を 1 つ返すので、`boolean` に詰められます。

### よくある誤答

- 「`resultType` はメソッドの戻り値から自動で決まるので、XML とは関係ない」: SELECT では XML に `resultType` を書き、戻り値と一致させます。
- 「`#{email}` は `Member` の `email` 項目」: この SQL の引数は `String email` で、`Member` は関係ありません。

## 演習 2

### 解答

```text
MemberService.register 30 行目: new MemberRecord(name.trim(), normalized)   … id は null
→ 31 行目: mapper.insert(rec)
→ MemberMapper.xml 13〜14 行目: INSERT を実行し、DB が id を採番（BIGSERIAL）
   useGeneratedKeys="true" keyColumn="id" keyProperty="id" により、採番値を rec の id に書き戻す
→ MemberRecord.java 19〜21 行目: setId(Long id) が呼ばれる
→ MemberService.register 32 行目: rec.toMember()（MemberRecord.java 31〜33 行目）で Member(id, name, email) を作る
→ MemberController.register 38〜39 行目: created.id() で Location を作り、本文にする
```

### 理由（コードの場所）

- `INSERT` の列（14 行目）に `id` が無いので、`id` は DB が採番します。
- `keyProperty="id"` の書き戻し先は、引数のオブジェクト（`MemberRecord`）の `id` 項目です。
  `Member` は `record` で `setId` を持たないので、書き戻し先にできません。
- 単体テストでは、`InMemoryMapper.insert`（`MemberServiceTest.java` 31〜36 行目）の `setId(++seq)` が、この書き戻しの代わりをしています。

### よくある誤答

- 「`insert` の戻り値が ID」: 戻り値は登録した行数（1）です（`MemberMapper.java` 15 行目の `int`）。
- 「`findById` で読み直して ID を得る」: 読み直しはしていません。書き戻された `rec` から作ります。

## 演習 3

### 解答

2 回目は、2 行とも `insertIfAbsent` が 0 を返します。
`ImportResult` は `imported = 0`、`duplicated = 2`、`errors` は空です。

### 理由（コードの場所）

- `OrderMapper.xml` 9 行目: `ON CONFLICT (order_no) DO NOTHING` により、登録済みの注文番号は何もしません。登録件数は 0 です。
- `OrderImportService.java` 46〜50 行目: 戻り値が 1 なら `imported`、それ以外なら `duplicated` を数えます。
- 52 行目: `new ImportResult(imported, duplicated, List.copyOf(errors))` を返します。
- 同じ動きを、1 行で確かめているのが `OrderImportServiceTest.rerunIsIdempotent`（34〜43 行目）です。

### よくある誤答

- 「主キー違反で例外になる」: `ON CONFLICT` があるので、例外にはなりません。
- 「`errors` に 2 件入る」: 重複は形式エラーではありません。`errors` に入るのは `parse` で弾いた行だけです（40〜45 行目）。

## 演習 4

### 解答

取込全体が失敗し、1 件も登録されません。
ジョブは終了コード 8（異常終了）で終わります。
正しい行も、存在しない会員 ID の行より前に処理された行も、すべて取り消されます。

### 理由（コードの場所）

1. `OrderImportService.parse`（55〜74 行目）は、`member_id` が数値かどうかしか確かめません。
   99999 は数値なので、形式エラーにはなりません。
2. `OrderMapper.xml` 7〜9 行目の `INSERT` が、外部キー `member_id BIGINT NOT NULL REFERENCES member (id)`（`01_schema.sql`）に違反します。
   `ON CONFLICT (order_no)` が受け止めるのは `order_no` の重複だけなので、例外になります。
3. `OrderImportService.importLines` の `catch`（42 行目）は `IllegalArgumentException` だけを受け止めます。
   DB の例外は受け止められず、`importLines` の外に出ます。
4. `importLines` には `@Transactional`（25 行目）があるので、例外によりそれまでの登録がすべて取り消されます。
5. `OrderImportJob.run` の `catch (Exception e)`（56〜58 行目）が受け止め、エラーログを出して `exitCode = ERROR`（8）にします。

クラスの Javadoc（`OrderImportService.java` 12 行目）には「形式エラーの行は飛ばして続行」とあります。
存在しない会員 ID の行は、この「形式エラー」に含まれず、全体を止めます。
これが仕様として正しいかは、設計書で確かめる必要があります。
飛ばして続行したいなら、取込前に会員の存在を確かめる、などの変更が必要です。

`order_no` や `product_code` が 21 文字以上のときも、`VARCHAR(20)` に違反して同じ結果になります。

単体テストが気づけない理由: `OrderImportServiceTest` と `OrderImportJobTest` は、Mapper をラムダ式に差し替えています。
ラムダ式には外部キーも長さの制約も無いので、DB の制約違反が起きません。

### よくある誤答

- 「その行だけ `errors` に入り、他の行は登録される（終了コード 4）」: `errors` に入るのは `parse` が投げた `IllegalArgumentException` だけです。
- 「`ON CONFLICT DO NOTHING` で無視される」: `ON CONFLICT` の対象は `order_no` の一意性の違反だけで、外部キーの違反は含みません。
- 「その行より前の行は登録済みのまま残る」: `@Transactional` により全体が取り消されます。

## 演習 5

### 解答

値が SQL の文字列にそのまま埋め込まれるので、次の問題が起きます。

| 入力の例 | 起きること |
| --- | --- |
| `a'b@example.com`（`'` を含む正当な形のアドレス） | SQL の文法エラーになり、利用者には 500 が返る |
| `'` と `OR` を組み合わせた入力 | `WHERE` の条件を書き換えられ、常に「登録済み」と判定させるなど、SQL の意味を変えられる（SQL インジェクション） |

### 理由（コードの場所）

- `MemberMapper.xml` 10 行目の `#{email}` は、値をパラメータとして渡すので、`'` を含んでも SQL の意味は変わりません。
- `'${email}'` にすると、MyBatis は SQL を組み立てる段階で値を文字列として埋め込みます。
  `'` が SQL の文字列の終わりとして解釈されます。
- メールアドレスの規格では、`@` より前に `'` を使えます。
  入力チェックの `@Email`（`MemberController.java` 29 行目）だけでは防げません。

### よくある誤答

- 「入力チェックの `@Email` があるので安全」: `@Email` は SQL の安全のためのチェックではありません。
  また、Mapper はコントローラ以外からも呼ばれます。
- 「`'` で囲んでいるので文字列として扱われ、安全」: 値の中の `'` で、囲みを途中で閉じられます。
- 「`existsByEmail` は SELECT だけなので被害は無い」: 判定を書き換えられるだけでも業務の不具合です。
  また、DB 製品や設定によっては、他の SQL を実行される危険もあります。
