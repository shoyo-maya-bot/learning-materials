### 理由（コードの場所）

- `MemberService.java` 26 行目: `email.trim()` で前後の空白を除き、`toLowerCase(java.util.Locale.ROOT)` で小文字にします。

- 30〜31 行目: 正規化した値で `MemberRecord` を作り、`insert` します。
- 同じ動きは `MemberServiceTest.register_normalizesEmailAndAssignsId`（42〜49 行目）で確かめられています。

  サービスは、コントローラ以外（バッチなど）から呼ばれることもあります。

## 演習 2

### 解答

起こりうる結果は 2 通りです。

| 結果 | 起きる条件 |
| --- | --- |
| 1 つ目は 201、2 つ目は 409（`APPE0003`） | 2 つ目のチェック（27 行目）が、1 つ目の確定後に行われた |
| 1 つ目は 201、2 つ目は 500 | 両方のチェックが、どちらの登録も確定する前に行われた |

2 つ目の結果が 500 になるのは、DB の一意制約違反の例外が `ApiExceptionHandler` で扱われないからです。
どちらの場合も、重複した会員が 2 件できることはありません。DB の一意制約が最後の砦になっています。

### 理由（コードの場所）

- 27〜31 行目は「確かめてから書く」処理です。
  `@Transactional`（24 行目）があっても、他のトランザクションの未確定の登録は見えないので、両方がチェックを通り抜けられます。
- DB の定義（`local/db/init/01_schema.sql`）で、`email` に `UNIQUE` が付いています。
  2 つ目の `insert`（31 行目）はこの制約に違反し、例外になります。
- `ApiExceptionHandler` が扱うのは `NotFoundException`、`BusinessException`、`MethodArgumentNotValidException` だけです（26・31・37 行目）。

修正案（例）: 一意制約違反の例外を、業務例外に変換します。

```java
        MemberRecord rec = new MemberRecord(name.trim(), normalized);
        try {
            mapper.insert(rec);
        } catch (org.springframework.dao.DuplicateKeyException e) {
            throw new BusinessException(MessageIds.EMAIL_ALREADY_USED, normalized);
        }
        return rec.toMember();
```

- MyBatis と Spring の組み合わせでは、DB の一意制約違反は `DuplicateKeyException` に変換されます。
- 27 行目の事前チェックは残します。普段の重複は、例外に頼らず分かりやすく弾けるからです。
- テストは、`insert` で `DuplicateKeyException` を投げる差し替えの Mapper を作り、`APPE0003` の `BusinessException` になることを確かめます。

### よくある誤答

- 「`@Transactional` があるので同時に来ても安全」: トランザクションは「途中で失敗したら全部取り消す」仕組みです。
  他のトランザクションとのチェックの競合までは防ぎません。
- 「重複した会員が 2 件登録される」: DB の一意制約があるので、2 件目は登録されません。
- 「`existsByEmail` を消して、例外の変換だけにすればよい」: 動きはしますが、普段の重複も例外の経路になり、読みにくくなります。

## 演習 3

### 解答

落ちるテストは `MemberServiceTest.register_normalizesEmailAndAssignsId` です。
47 行目の、氏名が前後の空白を除いた値になっていることの確認で失敗します。

### 理由（コードの場所）

- このテストは、前後に空白のある氏名で登録しています（44 行目）。
- `trim` を消すと、空白が付いたまま `MemberRecord` に入り、返る `Member` の `name` も空白付きになります。
- `MemberControllerTest.registerThenGet` は、空白の無い氏名で登録し、`name` を確かめていないので落ちません。

### よくある誤答

- 「`registerThenGet` も落ちる」: 氏名に空白が無く、`name` も確かめていません。
- 「`register_rejectsDuplicateEmailIgnoringCase` が落ちる」: このテストはメールアドレスの重複だけを確かめます。

## 演習 4

### 解答

`./gradlew test` が通るのは、単体テストが Spring を使わずに `MemberService` を直接作っているからです。
`@Transactional` は Spring が作った Bean を通したときだけ効くので、付けても消しても単体テストの結果は変わりません。

それでも付けておく理由は次のとおりです。

- 「このメソッドは読むだけ」という意図を、読み手に伝える
- 将来、読み取りを複数回するようになったとき、1 つのトランザクションにまとまる
- DB やドライバに読み取り専用だと伝わり、誤って書き込んだときに気づける場合がある

### 理由（コードの場所）

- `MemberServiceTest.java` 40 行目: `new MemberService(mapper)` で直接作っています。
- `MemberControllerTest.java` 30 行目も同じく `new MemberService(...)` です。
- 注釈は `MemberService.java` 19 行目にあります。

### よくある誤答

- 「`get_throwsNotFoundForUnknownId` が落ちる」: このテストは例外の型だけを確かめ、トランザクションとは関係ありません。
- 「`readOnly` が無いと書き込みになる」: `readOnly` の有無で、SELECT が書き込みに変わることはありません。
- 「テストが通るので、消しても問題ない」: テストで守られていないことと、意味が無いことは別です。
