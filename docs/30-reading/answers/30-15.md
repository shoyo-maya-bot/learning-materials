## 演習 1: メールアドレスを固定にしたら

**答え**: **1 回目から失敗します。**

| 回 | シナリオ 1（登録と照会） | シナリオ 2（重複は 409） | シナリオ 3（404） |
|---|---|---|---|
| 1 回目 | 成功 | **失敗**（24 行目: 201 を期待したが 409） | 成功 |
| 2 回目 | **失敗**（11 行目: 201 を期待したが 409） | **失敗**（24 行目） | 成功 |

**根拠**:

- シナリオ 1 が `karate@example.com` を登録します。DB の `member.email` には `UNIQUE` 制約があり（`local/db/init/01_schema.sql` 5 行目）、アプリも `MemberService.java` 27〜29 行目で重複を確かめます
- シナリオ 2 の最初の登録（21〜24 行目）は、同じアドレスなので 409 になり、`Then status 201` で失敗します
- 2 回目は、1 回目に登録したデータが DB に残っているので、シナリオ 1 の登録も 409 になります

UUID を入れているのは、シナリオどうし・実行どうしでデータがぶつからないようにするためです。

**よくある誤答**:

- 「2 回目から失敗する」。同じ実行の中でも、シナリオ 1 とシナリオ 2 がぶつかります
- 「Background で毎回作り直すので大丈夫」。作り直しても、値が固定なら毎回同じアドレスです

## 演習 2: アプリを起動せずに実行したら

**答え**:

- `./gradlew karateTest`: `localhost:8080` に接続できず（接続拒否）、3 つのシナリオがすべて失敗し、タスクも失敗します
- `./gradlew test`: Karate のテストは除外されるので、単体テストだけが動いて成功します（アプリも DB も不要）

**根拠**:

- `karate-config.js` 3 行目で、`baseUrl` の既定は `http://localhost:8080` です
- `build.gradle` 40 行目の `excludeTags 'karate'` と、`ApiKarateTest.java` 14 行目の `@Tag("karate")` の組み合わせで、`test` からは除外されます

**よくある誤答**:

- 「`karateTest` がアプリを自動で起動する」。`build.gradle` 45 行目のコメントどおり、先に起動しておく必要があります
- 「`./gradlew test` も失敗する」。`test` は Karate を動かしません

## 演習 3: 400 のシナリオを追加する

**答え（例）**: `members.feature` の末尾に追加します。

```gherkin
  Scenario: 入力に誤りがあれば 400
    Given path '/api/v1/members'
    And request { name: '', email: 'not-an-email' }
    When method post
    Then status 400
    And match response.messageId == 'APPE0001'
    And match response.details == '#[2]'
```

`'#[2]'` は「要素が 2 つの配列」という Karate の書き方です。

**根拠**:

- 名前は `@NotBlank`、メールアドレスは `@Email` に違反します（`MemberController.java` 28〜29 行目）
- `ApiExceptionHandler.java` 37〜44 行目の `invalid` が、400 と `APPE0001`、項目ごとのエラー 2 件を返します
- 同じ内容は、単体テスト `MemberControllerTest.invalidInputReturns400`（59〜67 行目）でも確かめています。Karate では、本物の `messages.properties` を使った応答で確かめられる点が違います

**よくある誤答・注意点**:

- 件数を確かめずに `match response.details == '#array'` とする。配列であることしか確かめず、件数の誤りを見逃します。件数まで見るなら `'#[2]'` や `* assert response.details.length == 2` を使います
- `details` の文の中身まで完全一致で確かめる。メッセージは検証ライブラリの版で変わることがあるので、件数や項目名に絞るのが無難です
- 新しいシナリオでも `email` を使う場合、Background で作った値が使えます。この例では、わざと誤った値を直接書いています

## 演習 4: baseUrl はテストに届くか

**答え**: **届きません。** `karate.env` だけが引き継がれ、`baseUrl` は引き継がれないからです。
その結果 `config.baseUrl` は値が無くなり、`* url baseUrl` で失敗します。sample-app の不具合と考えられます。

**根拠**:

- `./gradlew ... -DbaseUrl=...` の `-D` は、Gradle の JVM のシステムプロパティになります
- テストは別の JVM で動きます。そこに渡すのは、`build.gradle` 54 行目の `systemProperty 'karate.env', ...` だけです
- `karate-config.js` 6 行目の `karate.properties['baseUrl']` は、テストの JVM のシステムプロパティを読むので、値がありません

**直し方（例）**: `build.gradle` の `karateTest` の中、54 行目の後ろに追加します。

```groovy
    if (System.getProperty('baseUrl')) {
        systemProperty 'baseUrl', System.getProperty('baseUrl')
    }
```

あわせて、`karate-config.js` で `baseUrl` が無いときに分かりやすいエラーを出すようにすると、原因を探しやすくなります。
直したら、`-Dkarate.env=dev` 付きで実行し、レポートに出る要求の URL が開発環境になっていることを確かめます。

**よくある誤答**:

- 「`-D` で渡したので届く」。Gradle とテストの JVM は別です。54 行目のように、引き継ぐ値を明示する必要があります
- `karate-config.js` だけを直す。テストの JVM に値が無い以上、JavaScript 側では受け取れません

## 演習 5: 応答に createdAt を足したら

**答え**:

- `members.feature` 12 行目の `match response == { id: '#number', name: '結合 テスト', email: '#(email)' }` が失敗します。完全一致なので、余分な `createdAt` があると一致しません
- シナリオ 2・3 は、`messageId` しか確かめていないので通ります
- 単体テストは、`MemberControllerTest` が `jsonPath` で個別の項目だけを見ているので、確かめ方の面では影響を受けません。ただし `Member` のコンストラクタの引数が増えるので、`new Member(...)` を呼んでいる箇所（`MemberRecord.java` 32 行目など）を直すまでコンパイルが通りません

**根拠**: `Member` はレコード（`Member.java` 10 行目）なので、項目を足すと JSON にもそのまま出ます。
DB から値を取るには、`MemberMapper.xml` 6 行目の `SELECT` にも `created_at` を足す必要があります。

**直し方**: API の仕様として `createdAt` を足すと決めたなら、12 行目の期待値に `createdAt: '#string'` を足します。
完全一致の確認は、「仕様に無い項目が勝手に増えていないか」を見張る役目も持っています。

**よくある誤答**:

- 「18 行目も失敗する」。18 行目は `email` だけを確かめるので、項目が増えても通ります。ただし 12 行目で失敗した時点で、そのシナリオの残りは実行されません
- 「Karate は余分な項目を無視する」。無視するのは、`contains` を使った場合です。`==` は完全一致です
