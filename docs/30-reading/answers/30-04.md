# 30-04 解答

[30-04 共通の例外とエラー応答](../30-04-error-response.md) の演習の解答です。

## 演習 1

### 解答

- 呼ばれるハンドラ: `ApiExceptionHandler.notFound`
- HTTP ステータス: 404
- ログ: 出ない

### 理由（コードの場所）

- 例外を投げる場所は `MemberService.java` 21 行目（`new NotFoundException(...)`）です。
- `NotFoundException` は `BusinessException` の子クラスです（`NotFoundException.java` 4 行目（`extends BusinessException`））。
  `@ExceptionHandler` は最も近い型を選ぶので、`notFound`（`ApiExceptionHandler.java` 26〜29 行目（`notFound`））が呼ばれます。
- `notFound` には `log.warn` がありません。ログを出すのは `business`（33 行目）だけです。

### よくある誤答

- 「`BusinessException` の子なので `business` が呼ばれ、409 になる」: 子クラス専用のハンドラがあれば、そちらが優先されます。
- 「WARN ログが出る」: `notFound` はログを出しません。存在しない会員の照会は、利用者の操作で普通に起きるからです。

## 演習 2

### 解答

- ステータス: 400
- `messageId`: `APPE0001`
- `details`: 2 件。並び順は `email: ...` が先、`name: ...` が後

### 理由（コードの場所）

- `RegisterRequest`（`MemberController.java` 28〜29 行目（`RegisterRequest`））の入力チェックで、2 つの違反が出ます。
    - `name` が空 → `@NotBlank` 違反
    - `email` がメールアドレスの形でない → `@Email` 違反
- `@Valid`（37 行目）により、違反があると `MethodArgumentNotValidException` が投げられます。
- `ApiExceptionHandler.invalid`（37〜44 行目）が、`"項目名: 理由"` の形に変換し、`.sorted()` で並べ替えます。
  文字列の並べ替えなので、`e` で始まる `email` が `n` で始まる `name` より先になります。
- 件数は `MemberControllerTest.invalidInputReturns400`（66 行目）の `$.details.length()` が 2 であることで確かめられます。

### よくある誤答

- 「`name` が先」: 入力 JSON の順番や、`RegisterRequest` の項目の順番ではなく、文字列として並べ替えた順番です。
- 「`message` に項目ごとの理由が入る」: 項目ごとの理由は `details` に入ります。`message` は `APPE0001` の本文です。
- 「409」: 409 は `BusinessException` のときです。入力チェックは 400 です。

## 演習 3

### 解答

`NotFoundException` は親クラスのハンドラ `business` で処理されるようになります。
応答は 409 になり、WARN ログが出るようになります。
`messageId`（`APPE0002`）と `message` は変わりません。

落ちるテストは `MemberControllerTest.notFoundReturns404WithMessageId` です。
`./gradlew test` では実行されませんが、`members.feature` の「存在しない会員は 404」も `karateTest` で落ちます。

### 理由（コードの場所）

- 専用のハンドラが無くなると、次に近い型 `BusinessException` のハンドラ（31〜35 行目）が選ばれます。
- `business` は `HttpStatus.CONFLICT`（409）を返します（34 行目）。
- `MemberControllerTest.java` 54 行目の `status().isNotFound()` が失敗します。
  55〜56 行目の `messageId` と `message` の確認は、ステータスの確認より後なので、そもそも実行されません。

### よくある誤答

- 「ハンドラが無いので 500 になる」: 親クラスのハンドラがあるので、そちらで処理されます。
- 「`MemberServiceTest` も落ちる」: `MemberServiceTest` は例外の型を確かめるだけで、ハンドラを使いません。

## 演習 4

### 解答

`ErrorResponse` の形にはなりません。
パスの `abc` を `long` に変換できず、`MethodArgumentTypeMismatchException` が投げられます。
`ApiExceptionHandler` にはこの例外のハンドラが無いので、Spring の既定の処理で 400 になります。
本文は Spring Boot の既定のエラー応答で、`messageId` を含みません。

### 理由（コードの場所）

- `MemberController.java` 32 行目の引数は `long id` です。`abc` は `long` に変換できません。
- `ApiExceptionHandler` の `@ExceptionHandler` は 26・31・37 行目の 3 つだけで、型変換の例外は含まれていません。

修正案（例）:

```java
    // import org.springframework.web.method.annotation.MethodArgumentTypeMismatchException;
    @ExceptionHandler(MethodArgumentTypeMismatchException.class)
    public ResponseEntity<ErrorResponse> typeMismatch(MethodArgumentTypeMismatchException e) {
        return body(HttpStatus.BAD_REQUEST, MessageIds.INVALID_INPUT, new Object[0],
                List.of(e.getName() + ": 形式が正しくありません"));
    }
```

追加するテスト（例。`MemberControllerTest` に追加）:

```java
    @Test
    void nonNumericIdReturns400WithMessageId() throws Exception {
        mvc.perform(get("/api/v1/members/abc"))
                .andExpect(status().isBadRequest())
                .andExpect(jsonPath("$.messageId").value("APPE0001"));
    }
```

修正前にこのテストを書いて実行すると、`$.messageId` が無いため失敗します。
修正後に通ることを確かめれば、修正の効果がテストで守られます。

### よくある誤答

- 「`MethodArgumentNotValidException` になるので `invalid` で処理される」: それは `@Valid` の入力チェックの例外です。
  型の変換の失敗は別の例外です。
- 「404 になる」: URL の形（`/api/v1/members/{id}`）には合っているので、メソッドは見つかっています。
  失敗するのは引数の変換です。
- 「500 になる」: 型の変換の失敗は、Spring が既定で 400 として扱います。問題はステータスではなく、本文の形です。
