## 演習 1: 終了ログの出力場所

**答え**: `sample-app/src/main/java/com/example/sample/order/batch/OrderImportJob.java` の 53〜54 行目です。

<!-- src: sample-app/src/main/java/com/example/sample/order/batch/OrderImportJob.java @exercise-base -->
```java
log.info("{} JOB0001 終了 imported={} duplicated={} errors={}",
        MessageIds.IMPORT_FINISHED, r.imported(), r.duplicated(), r.errors().size());
```

**根拠**:

- ログの先頭 `APPI0002` は、`MessageIds.IMPORT_FINISHED`（`MessageIds.java` 14 行目）の値です
- `imported=` という文字列でソースを検索すると、この 1 か所だけが見つかります
- 件数は `ImportResult`（`ImportResult.java` 12 行目）から取り出しています

**よくある誤答**:

- `messages.properties` 5 行目（`APPI0002=処理を終了します。`）。これは API のエラー応答などで使う本文の定義です。このログは本文を使わず、ID だけを埋め込んでいます
- `OrderImportService.java`。サービスは件数を数えて返すだけで、ログは出していません

## 演習 2: Web サーバーが立ち上がらない理由

**答え**: `sample-app/src/main/resources/application-batch.yml` の 2〜4 行目、`spring.main.web-application-type: none` です。

**根拠**: プロファイル `batch` を有効にすると `application-batch.yml` が読まれます。
`web-application-type: none` は、Web サーバーを作らずにアプリを起動する指定です。

**よくある誤答**:

- `SampleApplication.java` 18〜20 行目の `System.exit`。これは「終わらせる」処理で、「立ち上げない」処理ではありません。もし `none` が無ければ、Web サーバーが一度起動してから `System.exit` で終わります
- `application.yml` 17 行目の `server.port`。ポート番号を決めるだけで、起動の有無は決めません

## 演習 3: JOB0002 を指定した場合

**答え**: ジョブは何も動かず、エラーも出ないまま **終了コード 0** で終わります。

**根拠**:

1. `OrderImportJob.java` 23 行目の条件 `havingValue = "JOB0001"` を満たさないので、`OrderImportJob` は Bean になりません
2. `ApplicationRunner` を実装した Bean が無いので、`run` は誰からも呼ばれません
3. `SampleApplication.java` 19 行目の `SpringApplication.exit(ctx)` は、`ExitCodeGenerator` の Bean が無いため 0 を返します

スケジューラから見ると「正常終了」なので、ジョブ ID の打ち間違いに気づけません。
実案件では、「どのジョブにも当たらなければ 8 で終わる」といった仕組みを入れることが多いです（sample-app には入っていません）。

**よくある誤答**:

- 「`OrderImportJob` が動いて JOB0001 が実行される」。条件付きの Bean なので作られません
- 「起動時に例外が出て終了コード 1 になる」。条件に合う Bean が無いことは、Spring にとってエラーではありません

## 演習 4: 設計書と実装クラスの違い

**答え**: パッケージ名が違います。

| | 設計書 | sample-app |
|---|---|---|
| ジョブ | `com.example.app.order.batch.OrderImportJob` | `com.example.sample.order.batch.OrderImportJob` |
| サービス | `com.example.app.order.OrderImportService` | `com.example.sample.order.OrderImportService` |

**根拠**: 設計書 1. 概要の表「実装クラス」欄と、`OrderImportJob.java` 1 行目・`OrderImportService.java` 1 行目の `package` 文を比べます。

設計書がサンプルの雛形から作られたなどの理由で、パッケージ名だけ古いまま残っていると考えられます。
実案件なら、どちらに合わせるかを設計書の担当者に確認します。

**よくある誤答**:

- 「同じ」と答える。クラス名だけを見て、パッケージ名まで比べていないと見落とします
- 入力の S3 キー（設計書は `inbound/orders.csv`、ローカルは `orders.csv`）を挙げる。これは起動引数で渡す値で、実装クラスの違いではありません（ただし気づけたこと自体は良い観点です）

## 演習 5: ローカルファイルを直接読ませる

**答え**:

```bash
./gradlew bootRun --args='--spring.profiles.active=local,batch --app.batch.job=JOB0001 --input=../local/data/orders.csv'
```

**根拠**: `sample-app/src/main/java/com/example/sample/order/batch/DefaultFileFetcher.java` の 28〜30 行目です。

<!-- src: sample-app/src/main/java/com/example/sample/order/batch/DefaultFileFetcher.java @exercise-base -->
```java
if (!location.startsWith("s3://")) {
    return Files.readAllLines(Path.of(location), StandardCharsets.UTF_8);
}
```

`s3://` で始まらない値は、ローカルのファイルパスとして読みます。
`OrderImportJob.java` 45 行目のエラーメッセージにも「s3://バケット/キー またはファイル」と書かれています。

`bootRun` の作業ディレクトリは `sample-app` なので、相対パスは `../local/data/orders.csv` になります。
DB は必要なので、`docker compose up -d --wait` は済ませておきます。

**よくある誤答**:

- `--input=file://../local/data/orders.csv`。`file://` 形式には対応していません。`Path.of("file://...")` は存在しないパスとして扱われ、`IOException` から終了コード 8 になります
- `local` プロファイルを外す。DB の接続先パスワード（`application-local.yml` 4 行目）が入らなくなり、登録時に失敗します
