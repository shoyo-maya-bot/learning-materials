## 演習 1

### 解答

コンパイルエラーになり、`./gradlew build` は失敗します。
手元の JDK が 21 でも、Java {{ versions.java }} の API だけでコンパイルするからです。

### 理由（コードの場所）

<!-- src: sample-app/build.gradle#L14-L15 @exercise-base -->
```groovy title="sample-app/build.gradle" linenums="14"
tasks.withType(JavaCompile).configureEach {
    options.release = 17
```

- `release = {{ versions.java }}` は「Java {{ versions.java }} の API 一覧に対してコンパイルする」という指定です。
- `List.getFirst()` は Java 21 で追加されたメソッドなので、17 の API 一覧にはありません。
- 13 行目のコメントのとおり、これは「21 固有の API を使わせない」ための設定です。
- 修正するなら `list.get(0)` を使います。

### よくある誤答

- 「手元が 21 なので通り、CI で初めて落ちる」: `release` が無ければそうなります。
  この設定があるので、手元でも同じように落ちます。そこがこの設定の価値です。
- 「実行時に `NoSuchMethodError` になる」: 実行の前に、コンパイルの段階で止まります。

## 演習 2

### 解答

コンパイルエラーになり、`./gradlew build` は失敗します。
PostgreSQL のドライバは `runtimeOnly` なので、コンパイル時のクラスパスに入っていないからです。

### 理由（コードの場所）

<!-- src: sample-app/build.gradle#L30-L30 @exercise-base -->
```groovy title="sample-app/build.gradle" linenums="30"
    runtimeOnly 'org.postgresql:postgresql'
```

- `runtimeOnly` の依存は、実行時には使えますが、コンパイル時には見えません。
- 望ましい理由: ドライバ固有のクラスに依存すると、DB 製品を変えにくくなります。
  コードは JDBC と MyBatis の標準の仕組みだけで DB を使うべきだ、という方針を、ビルドが守ってくれます。

### よくある誤答

- 「`implementation` に変えれば解決なので、変えればよい」: 動きはしますが、上の方針を崩します。
  変える前に、本当にドライバ固有の機能が必要かをチームに相談します。
- 「実行時に `ClassNotFoundException` になる」: `runtimeOnly` なので実行時にはクラスがあります。
  止まるのはコンパイル時です。

## 演習 3

### 解答

接続できません。
`-DbaseUrl` は Gradle 自体の JVM には届きますが、テストを実行する JVM には引き渡されないからです。
`karate-config.js` は `baseUrl` を読めず、接続先が決まらないままテストが失敗します。

### 理由（コードの場所）

<!-- src: sample-app/build.gradle#L54-L54 @exercise-base -->
```groovy title="sample-app/build.gradle" linenums="54"
    systemProperty 'karate.env', System.getProperty('karate.env', 'local')
```

<!-- src: sample-app/src/test/resources/karate-config.js#L4-L7 @exercise-base -->
```javascript title="sample-app/src/test/resources/karate-config.js" linenums="4"
  if (env === 'dev') {
    // クラウドの開発環境に向けるとき: -Dkarate.env=dev -DbaseUrl=https://<your-dev-host>
    config.baseUrl = karate.properties['baseUrl'];
  }
```

- Gradle はテストを別の JVM で実行します。
  コマンドラインの `-D` は、明示的に `systemProperty` で渡したものだけがテストの JVM に届きます。
- 54 行目は `karate.env` だけを渡しています。そのため `env === 'dev'` の分岐には入ります。
- しかし 6 行目の `karate.properties['baseUrl']` は、テストの JVM のシステムプロパティを読むので値がありません。

修正案（例）:

```groovy
    systemProperty 'karate.env', System.getProperty('karate.env', 'local')
    if (System.getProperty('baseUrl')) {
        systemProperty 'baseUrl', System.getProperty('baseUrl')
    }
```

`-DbaseUrl` を指定しないとき（ローカル）は何も渡さず、`karate-config.js` 3 行目（`baseUrl: 'http://localhost:8080'`）の既定値が使われます。

### よくある誤答

- 「`karate-config.js` のコメントどおりのコマンドなので動く」: コメントは使い方の意図を示すだけです。
  実際に値が届くかは、`build.gradle` の受け渡しまで読んで確かめます。
- 「`karate.env` も届かない」: `karate.env` は 54 行目で明示的に渡しているので届きます。
- 修正案で、`baseUrl` を常に `systemProperty` に渡す: 未指定のとき `null` を渡すことになり、別の失敗の元になります。

## 演習 4

### 解答

- `karate-junit5`（33 行目）はテストコードが `import` して使うので、コンパイル時から必要です。だから `testImplementation` です。
- `junit-platform-launcher`（34 行目）はテストコードが直接使わず、Gradle がテストを起動するときだけ必要です。だから `testRuntimeOnly` です。

### 理由（コードの場所）

- `ApiKarateTest.java` 3 行目に `import com.intuit.karate.junit5.Karate;` があります。
- `junit-platform-launcher` のクラスを `import` しているテストはありません。
  これは Gradle が JUnit のテストを見つけて実行するための部品です。

### よくある誤答

- 「どちらもテスト用なので違いは無い」: コンパイル時に見えるかどうかが違います。
- 「`testRuntimeOnly` は本番の jar に入る」: `test` で始まる構成は、本体の jar には入りません。

## 演習 5

### 解答

`test` タスクの後に `jacocoTestReport` が必ず実行され、そのレポート設定で HTML が有効だからです。
関係する行は次の 3 か所です。

| 行 | 内容 |
| --- | --- |
| 5 行目 | `id 'jacoco'`（カバレッジ計測と `jacocoTestReport` タスクを使えるようにする） |
| 42 行目 | `finalizedBy jacocoTestReport`（`test` の後に実行する） |
| 58〜63 行目 | `xml.required = true` と `html.required = true`（XML と HTML を出力する） |

### 理由（コードの場所）

- `finalizedBy` は「このタスクの後に必ず実行する」という指定です。
- レポートは `build/reports/jacoco/test/html/index.html` に作られます。
  CI もこのフォルダを成果物として保存しています（`dev-environment/.github/workflows/ci.yml`）。

### よくある誤答

- 5 行目だけを答える: プラグインを入れただけでは、`test` の後に自動でレポートは作られません。
- 「`dependsOn` で実行される」: `dependsOn` は「前に実行する」です。ここは `finalizedBy`（後に実行する）です。
