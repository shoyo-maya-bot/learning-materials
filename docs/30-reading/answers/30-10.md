## 演習 1: 見出しに空白が入っている

**答え**: ファイル全体が中止され、1 件も登録されません。**終了コードは 8** です。

**根拠**:

1. `OrderImportService.java` 27 行目の `trim()` は、文字列の **前後** の空白しか取りません
2. `"order_no, member_id,product_code,quantity"` は `HEADER` と一致しないので、28 行目で `IllegalArgumentException` が投げられます
3. この例外は `OrderImportJob.java` 56〜58 行目の `catch (Exception e)` で受け止められ、`exitCode = ERROR`（8）になります
4. ログには `JOB0001 異常終了` と、例外のメッセージ「見出し行が不正です（期待値: ...）」が出ます

設計書 STEP1 の「1 行目が見出しであること。違えば異常終了（終了コード 8）」のとおりです。

**よくある誤答**:

- 「`trim()` で空白が取れるので正常に取り込まれる」。`trim()` は項目の間の空白を取りません
- 「終了コード 4」。4 はデータ行の形式エラーのときです。見出しの誤りはファイル全体の誤りとして 8 になります

## 演習 2: 数量が数値でない行

**答え**: `3: quantity が数値ではありません`

**根拠**:

- 列数は 4、`order_no`・`member_id`・`product_code` は正しいので、69 行目の `parseLong(cols[3], "quantity")` まで進みます
- `Long.parseLong("abc")` が `NumberFormatException` を投げ、80 行目で `"quantity" + " が数値ではありません"` に包み直されます
- `importLines` 43 行目で、行番号 3 と `": "` が前に付きます

**よくある誤答**:

- `3: quantity は 1〜999 です（abc）`。範囲の確認（70 行目）は、数値に変換できた後でしか行いません
- 行番号を `2` と答える。リストの添字（`i = 2`）に `+ 1` した値が行番号です（38 行目）

## 演習 3: `split(",", -1)` を `split(",")` に変えたら

**答え**: **どのテストも失敗しません。**

**根拠**: `-1` の有無で結果が変わるのは、**末尾に空の項目がある行**（例: `A001,1,P-01,`）だけです。
`OrderImportServiceTest.java` には、そのような行が 1 つもありません。

- 62〜67 行目の `parseRejects` の 4 ケースは、どれも末尾が空ではありません
- `' ,1,P-01,1'` は **先頭** が空白ですが、`split` が捨てるのは末尾の空文字だけです

動きの違いは次のとおりです。

| 行 | `split(",", -1)`（現状） | `split(",")` |
|---|---|---|
| `A001,1,P-01,` | `quantity が数値ではありません` | `列数が 4 ではありません（3 列）` |

どちらでも形式エラーとして飛ばされるので、取込件数は変わりません。変わるのはメッセージだけです。
「テストが通る ＝ 変更が安全」とは限らない、という例です。
気になる場合は、`parseRejects` に `"A001,1,P-01,   | quantity が数値ではありません"` のようなケースを足すと、この違いを検出できます。

**よくある誤答**:

- `parseRejects` の `' ,1,P-01,1'` が落ちる。先頭の空の項目は捨てられません
- `importsValidLinesAndSkipsDuplicates` が落ちる。空行 `""` は `isBlank()` で `parse` より前に飛ばされます

## 演習 4: `stripBom` を外したら

**答え**: `importsValidLinesAndSkipsDuplicates`（18〜32 行目）が失敗します。

**根拠**: このテストだけが、見出しの先頭に BOM を付けています（21 行目。エディタでは `""` に見えますが、BOM の文字が入っています）。
BOM を取らないと 27 行目の比較が一致せず、`IllegalArgumentException` が投げられて、テストはエラーになります。

ほかのテストは `OrderImportService.HEADER` をそのまま使っているので、影響を受けません。

**よくある誤答**:

- 「どのテストも落ちない」。21 行目の BOM はエディタで見えないので、気づかないとこう答えてしまいます。`od -c` や 16 進表示のできるエディタで確かめると見つかります
- `wrongHeaderIsRejected` が落ちる。このテストはもともと「不正な見出しで例外」を期待しているので、通ったままです

## 演習 5: 商品コードの桁数チェックを追加する

**答え（例）**: `parse` の 65〜68 行目の直後に追加します。

```java
        String product = cols[2].trim();
        if (product.isEmpty()) {
            throw new IllegalArgumentException("product_code が空です");
        }
        if (product.length() > 20) {
            throw new IllegalArgumentException("product_code は 20 文字以内です（" + product.length() + " 文字）");
        }
```

テストは `OrderImportServiceTest.java` 62〜67 行目の `@CsvSource` に 1 行足します（21 文字の商品コード）。

```java
        "A001,1,P-01,1000   | quantity は 1〜999 です（1000）",
        "A001,1,P-0123456789012345678,1 | product_code は 20 文字以内です（21 文字）"
```

**根拠**: `local/db/init/01_schema.sql` 12 行目が `product_code VARCHAR(20) NOT NULL` です。
このチェックが無いと、21 文字以上の行は DB の登録時に例外になります。
その例外は `IllegalArgumentException` ではないので、行単位では飛ばされず、ファイル全体が取り消されて終了コード 8 になります。

**よくある誤答・注意点**:

- 境界値を試さない。20 文字（通る）と 21 文字（落ちる）の両方を確かめるのが基本です
- 検証を `importLines` 側に書く。`parse` に書けば、`parseRejects` のような単体テストで直接確かめられます
- 同じ理由で `order_no`（`VARCHAR(20)`）にも桁数チェックが無いことに気づけると、なお良いです。設計書 STEP1 にも桁数の記述が無いので、追加するなら設計書の担当者と相談します
