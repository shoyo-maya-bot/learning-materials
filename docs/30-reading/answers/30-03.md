## 演習 1

### 解答

| 問い | 答え | 根拠 |
| --- | --- | --- |
| Web サーバーは起動するか | 起動する | `batch` が無いので `application-batch.yml` が読まれず、`web-application-type: none` が効かない |
| `System.exit` は呼ばれるか | 呼ばれない | `SampleApplication.java` 18 行目の `matchesProfiles("batch")` が偽 |
| ポート | 8080（環境変数 `SERVER_PORT` があればその値） | `application.yml` 17 行目の `${SERVER_PORT:8080}` |

### 理由（コードの場所）

- `spring-boot-starter-web`（`build.gradle` 25 行目）があるので、既定では Web アプリとして起動します。
- `application-local.yml` にはポートの指定が無いので、`application.yml` の値がそのまま使われます。
- `main` は 18 行目の `if` を抜けて終わりますが、Web サーバーのスレッドが動き続けるので、プロセスは終わりません。

### よくある誤答

- 「`main` が終わるのでプロセスも終わる」: Web サーバーのスレッドが残るので終わりません。
- 「ポートは `application-local.yml` で決まる」: `local` にはポートの指定がありません。ファイルに無い値は共通の値が使われます。

## 演習 2

### 解答

ジョブは何も実行されず、終了コード 0 で終わります。
`OrderImportJob` が Bean として作られないため、取込も、開始・終了のログも出ません。

問題点: ジョブ管理の仕組みからは「正常終了」に見えます。
設定の誤りで 1 件も取り込まれていないのに、誰も気づけません。

### 理由（コードの場所）

<!-- src: sample-app/src/main/java/com/example/sample/order/batch/OrderImportJob.java#L23-L23 @exercise-base -->
```java title="sample-app/src/main/java/com/example/sample/order/batch/OrderImportJob.java" linenums="23"
@ConditionalOnProperty(name = "app.batch.job", havingValue = "JOB0001")
```

- `app.batch.job` が無いので、この条件が偽になり、`OrderImportJob` は Bean になりません。
- `batch` プロファイルは有効なので、`application-batch.yml` により Web サーバーは起動しません。
- `SampleApplication.java` 19 行目の `SpringApplication.exit(ctx)` は、`ExitCodeGenerator` が 1 つも無いので 0 を返します。

改善案の例: `batch` プロファイルなのにジョブが 1 つも無いときは、エラーのログを出して 8 で終える。
どこで確かめるか（起動クラスか、専用の Bean か）は、チームで決めます。

### よくある誤答

- 「`--input` があるのでジョブは動く」: `--input` を読むのは `OrderImportJob` です。
  そのクラス自体が作られないので、`--input` は使われません。
- 「起動エラーで終了コード 1 になる」: 必須の Bean が欠けているわけではないので、起動は成功します。
- 「Web サーバーが起動して待ち続ける」: `batch` プロファイルは有効なので、Web サーバーは起動しません。

## 演習 3

### 解答

`DEBUG` です。

### 理由（コードの場所）

<!-- src: sample-app/src/main/resources/application-local.yml#L8-L10 @exercise-base -->
```yaml title="sample-app/src/main/resources/application-local.yml" linenums="8"
logging:
  level:
    com.example.sample: DEBUG
```

- `application-batch.yml` はログレベルを指定していません。
- 複数のプロファイルを有効にすると、それぞれのファイルが重ねて読まれます。
  同じキーが無ければ、片方の値がそのまま残ります。

### よくある誤答

- 「`batch` のほうが後なので、`batch` の設定に置き換わり既定の `INFO` になる」: 置き換わるのは同じキーだけです。
  ファイル全体が入れ替わるわけではありません。

## 演習 4

### 解答

API として起動すると、Web サーバーが起動した直後に、コンテナが閉じられてプロセスが終わります。
終了コードは 0 です（`ExitCodeGenerator` の Bean が無いため）。
`./gradlew test` で落ちるテストはありません。

### 理由（コードの場所）

- `SpringApplication.run`（17 行目）は、Web サーバーの起動が終わると戻ってきます。
- その直後に `SpringApplication.exit(ctx)` がコンテナを閉じるので、Web サーバーも止まります。
- 単体テストはどれも `main` を呼びません。
  `MemberControllerTest` は Spring を起動せずに組み立てています（`MemberControllerTest.java` 19〜35 行目）。
- Karate のテストなら、起動中のアプリが無いので失敗しますが、`./gradlew test` では実行されません。

この変更は、テストでは守られていません。
起動クラスを変えたら、API とバッチの両方を手で起動して確かめる必要があります。

### よくある誤答

- 「起動に失敗して例外になる」: 起動は成功し、その後で正常に閉じられます。
- 「`MemberControllerTest` が落ちる」: このテストは `SampleApplication` を使いません。
- 「`OrderImportJobTest` が落ちる」: このテストも `OrderImportJob` を直接 `new` しており、`main` を通りません。
