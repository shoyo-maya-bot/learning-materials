## 演習 1: 入力ごとの終了コード

**答え**:

| 入力 | 終了コード | 決まる場所 |
|---|---|---|
| (a) `--input` を 2 回指定 | 8 | `OrderImportJob.java` 44〜47 行目（`input.size() != 1`） |
| (b) データ行がすべて重複 | 0 | 55 行目（`errors` が空なので `OK`） |
| (c) 見出しの綴りが違う | 8 | `OrderImportService.java` 28 行目の例外 → `OrderImportJob.java` 58 行目 |
| (d) 3 行中 1 行の列数が 3 | 4 | `OrderImportService.java` 57〜59 行目で記録 → `OrderImportJob.java` 55 行目 |

**根拠**: `args.getOptionValues("input")` は、同じオプションを複数回指定すると、値をすべて並べたリストを返します。
(a) はその大きさが 2 になるので、引数の誤りとして扱われます。

**よくある誤答**:

- (a) を「最後の指定が使われて正常に動く」。44 行目で `size() != 1` を確かめています
- (b) を 4 と答える。重複は `errors` に入りません（`ImportResult.java` 14〜16 行目）
- (d) を 8 と答える。行単位の形式エラーは飛ばして続行するので 4 です

## 演習 2: 55 行目を `exitCode = OK;` に変えたら

**答え**: `exitCodeFourWhenSomeLinesSkipped`（`OrderImportJobTest.java` 22〜27 行目）が失敗します。

**根拠**: このテストは、`"bad"` という 1 列だけの行を渡し、終了コード 4 を期待しています（26 行目）。
変更後は `errors` があっても 0 になるので、`isEqualTo(4)` が失敗します。

ほかの 2 つのテストは通ります。

- `exitCodeZeroWhenAllLinesValid` はもともと 0 を期待しています
- `exitCodeEightWhenInputMissingOrUnreadable` は 46 行目と 58 行目の経路で、55 行目を通りません

**よくある誤答**:

- 「3 つとも落ちる」。テストごとに、どの行を通るかをたどると、1 つだけだとわかります
- `OrderImportServiceTest` のテストを挙げる。終了コードを決めているのはジョブのクラスで、サービスのテストは関係しません

## 演習 3: 例外を外に出したら

**答え**: `exitCodeEightWhenInputMissingOrUnreadable`（29〜40 行目）が失敗します。
実際にバッチを動かすと、読み込みや登録で例外が起きたとき、**終了コードは 1** になります。

**根拠**:

- テストの後半（35〜39 行目）は、`IOException` を投げる `FileFetcher` を渡しています。例外が `run` の外に出るので、38 行目の `broken.run(...)` で例外になり、テストはエラーで終わります
- 前半の引数なし（31〜33 行目）は 46〜47 行目の経路なので、例外は関係なく 8 のままです
- ほかの 2 つのテストは例外が起きないので、通ります
- 実際の起動では、`SampleApplication.java` 17 行目の `SpringApplication.run` が例外で終わり、19 行目の `System.exit` に届きません。`main` から例外が出た JVM は、終了コード 1 で終わります

スケジューラによっては、1 を「異常終了」として扱ってくれることもあります。
それでも、約束（0 / 4 / 8）に無い値を返すのは、運用設計と合わないので避けます。

**よくある誤答**:

- 「Spring が `getExitCode()` を呼んで 8 になる」。`ERROR` を設定する行（58 行目）が無くなるうえ、`SpringApplication.exit` 自体が呼ばれません
- 「引数なしのテストも落ちる」。引数なしは例外を使わずに 8 を設定しています

## 演習 4: 0 件のときも 4 にする

**答え（例）**: `OrderImportJob.java` 55 行目を次のように変えます。

```java
            boolean nothingToImport = r.imported() == 0 && r.duplicated() == 0;
            exitCode = r.hasErrors() || nothingToImport ? WARN : OK;
```

テストは `OrderImportJobTest.java` に追加します。

```java
    @Test
    void exitCodeFourWhenNoDataLines() {
        OrderImportJob job = new OrderImportJob(loc -> List.of(OrderImportService.HEADER), service);
        job.run(new DefaultApplicationArguments("--input=orders.csv"));
        assertThat(job.getExitCode()).isEqualTo(4);
    }

    @Test
    void exitCodeZeroWhenAllLinesDuplicated() {
        OrderImportService alreadyStored = new OrderImportService(o -> 0);
        OrderImportJob job = new OrderImportJob(loc -> List.of(OrderImportService.HEADER, "A1,1,P,1"), alreadyStored);
        job.run(new DefaultApplicationArguments("--input=orders.csv"));
        assertThat(job.getExitCode()).isZero();
    }
```

**根拠**: 2 つ目のテストは「全件重複は 0 のまま」という、変えてはいけない動きを守るためのものです。
既存の `service`（13 行目）は Mapper が常に 1 を返すので、重複の場面を作るには、0 を返す Mapper（`o -> 0`）が必要です。

**よくある誤答・注意点**:

- 条件を `r.imported() == 0` だけにする。再実行（全件重複）でも 4 になり、30-11 で確かめた「再実行しても安全」の運用と合わなくなります
- 実装だけ直して、設計書 STEP3 の表を直さない。終了コードは運用担当者との約束なので、設計書と運用設計書を先に直します

## 演習 5: 設計書とメッセージの出し方

**答え（要点）**: 次の 2 点が、設計書から読み取れる内容と一致していません。どちらも「要確認」の点です。

1. **引数不足のログに API 用のメッセージ ID を使っている**: `OrderImportJob.java` 45 行目は `MessageIds.INVALID_INPUT`（`APPE0001`「入力内容に誤りがあります。」）を出します。設計書 3. メッセージの表には `APPE0001` が無く、STEP3 では「エラーログ」とだけ書かれています
2. **異常終了のログにメッセージ ID が無い**: 57 行目の `log.error("JOB0001 異常終了", e)` には ID が付いていません。監視ツールがメッセージ ID でログを拾う運用なら、見逃されるおそれがあります

一方、次の点は一致しています。

- 開始時の `APPI0001`（49 行目）と、終了時の `APPI0002`（53〜54 行目）
- 形式エラーの行ごとの `APPW0001`（52 行目）。設計書の「APPW0001 + APPI0002」のとおり、警告の後に件数を出します

**よくある誤答**:

- 「すべて一致している」。終了コードの値だけを比べると一致していますが、メッセージ ID まで見ると差があります
- 「`APPW0001` を 1 回だけ出すべき」。設計書は回数を決めていません。行ごとに出すのは、行番号と理由を残すためで、STEP1 の記述と合っています
