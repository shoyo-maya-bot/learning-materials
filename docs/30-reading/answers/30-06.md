# 30-06 解答

[30-06 会員 API のコントローラ](../30-06-member-controller.md) の演習の解答です。

## 演習 1

### 解答

| 応答の部分 | 値 | 決めている行 |
| --- | --- | --- |
| ステータス | 201 Created | `MemberController.java` 39 行目の `ResponseEntity.created(...)` |
| `Location` ヘッダ | `/api/v1/members/{採番された ID}` | 同じく 39 行目の `URI.create("/api/v1/members/" + created.id())` |
| 本文 | 登録した会員（`id`、`name`、`email`）の JSON | 39 行目の `.body(created)`。`created` は 38 行目の `service.register(...)` の戻り値 |

### 理由（コードの場所）

- `ResponseEntity.created(URI)` は、ステータス 201 と `Location` ヘッダを同時に設定するメソッドです。
- 本文の `id` は、DB が採番した値です。採番の仕組みは [30-08](../30-08-mapper-sql.md) で読みます。
- テストでは `MemberControllerTest.registerThenGet` の 42〜44 行目で、201、`Location`、`$.id` を確かめています。

### よくある誤答

- 「ステータスは `@PostMapping` で 201 になる」: `@PostMapping` はステータスを決めません。`created(...)` が決めます。
- 「本文の `name` と `email` は送った値そのまま」: サービスで空白の除去と小文字化をした値です（[30-07](../30-07-member-service.md)）。

## 演習 2

### 解答

2 件です。

| 項目 | 違反する注釈 | 違反しない注釈 |
| --- | --- | --- |
| `email` | `@NotBlank` | `@Email`（空文字は対象外）、`@Size` |
| `name` | `@NotBlank` | `@Size` |

並び順は `email: ...`、`name: ...` です（[30-04](../30-04-error-response.md) の演習 2 と同じ理由）。

### 理由（コードの場所）

- 注釈は `MemberController.java` 29 行目（`@NotBlank`）にあります。
- `@Email` は、空文字をチェック対象外として通します。空文字を弾くのは `@NotBlank` の役割です。
- `ApiExceptionHandler.invalid`（37〜44 行目）が、項目ごとの違反を 1 件ずつ `details` にします。

### よくある誤答

- 「3 件（`name` の `@NotBlank`、`email` の `@NotBlank` と `@Email`）」: `@Email` は空文字を違反にしません。
- 「1 件（最初の違反で止まる）」: 入力チェックは、すべての項目のすべての注釈を確かめてから結果を返します。

## 演習 3

### 解答

登録は成功しません。400（`APPE0001`）になります。
`@Size(max = 50)` は、空白を除く前の 52 文字に対してチェックするからです。

### 理由（コードの場所）

- `MemberController.java` 29 行目の `@Size(max = 50)` は、送られた値そのものの長さを数えます。
- 空白を除くのは `MemberService.java` 30 行目の `name.trim()` です。
  入力チェックはサービスより前（37 行目の `@Valid`）で行われるので、サービスまで届きません。

この動きが仕様として正しいかは、設計書で確かめる必要があります。
「空白を除いた長さで 50 文字まで」が仕様なら、チェックの順番を見直すことになります。

### よくある誤答

- 「`trim` で 50 文字になるので成功する」: `trim` はサービスにあり、入力チェックの後です。
- 「DB の `VARCHAR(50)` で弾かれて 500 になる」: DB に届く前に、入力チェックで 400 になります。

## 演習 5

### 解答

入力チェックが実行されず、空の氏名と不正なメールアドレスのまま登録されます。
テストの環境では 201 が返ります。
落ちるテストは `MemberControllerTest.invalidInputReturns400` です（64 行目 `status().isBadRequest()`）。

### 理由（コードの場所）

- `RegisterRequest` の注釈（29 行目）は、`@Valid`（37 行目）が無いと実行されません。
  注釈は「チェックの内容」で、`@Valid` が「チェックを実行する指示」です。
- `MemberService.register`（24〜33 行目）には、空文字やメールアドレスの形のチェックがありません。
- 実際の DB でも、`name` は `NOT NULL` ですが空文字は入るので、エラーになりません。
  不正なデータが静かに保存されます。
- Karate のシナリオには入力エラーの確認が無いので、`karateTest` では気づけません。

### よくある誤答

- 「`RegisterRequest` に注釈があるので、`@Valid` が無くてもチェックされる」: 実行の指示が無いとチェックされません。
- 「DB の制約で弾かれて 500 になる」: 空文字は `NOT NULL` に違反しません。メールアドレスの形の制約も DB にはありません。
