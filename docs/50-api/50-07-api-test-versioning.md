# 50-07 API テストと版の管理

!!! abstract "到達目標"
    - Karate で、API の結果（ステータス・応答の形・メッセージ ID）を確かめるシナリオを書ける
    - 「契約」としての API を確かめるテストの考え方を説明できる
    - 後方互換性のある変更と、互換性を壊す変更を見分けられる
    - 互換性を壊すときに、版（`v1` → `v2`）をどう扱うかを説明できる

## 何か

**API テスト** は、起動したアプリに HTTP でリクエストを送り、応答を確かめるテストです。
単体テストと違い、Controller・例外ハンドラ・DB までをまとめて確かめます。
この教材では **Karate** を使います（基本は [20-17 Karate](../20-basics/20-17-karate.md)）。

API は、作る側と使う側の **契約** です。
「このリクエストを送れば、この形の応答が返る」という約束です。
契約を確かめるテストを、**契約テスト** と呼ぶことがあります。

**後方互換性** は、API を変更しても、今の利用者がそのまま使い続けられる性質です。
**版**（バージョン）は、互換性を壊す変更をしたときに、古い契約と新しい契約を並べて提供するための番号です。

## なぜ必要か

API の利用者は、画面や他のシステムです。
作る側が気軽に応答の形を変えると、利用者の画面が壊れます。
しかも、壊れたことに気付くのは利用者側です。

API テストがあれば、意図しない変更をリリース前に見つけられます。
後方互換性の考え方を知っていれば、利用者を壊さずに API を育てられます。

## どうやるか

### 結果ごとにシナリオを書く

設計書の結果表（ステータスとメッセージ ID）の行ごとに、シナリオを 1 つ書きます。
成功だけでなく、失敗の行も確かめます。

!!! failure "悪い例"
    ```gherkin
    Scenario: 会員を照会できる
      Given path '/api/v1/members', 1
      When method get
      Then status 200
    ```
    ステータスしか見ていません。応答の形や値が変わっても気付けません。
    また、ID 1 の会員がいることを前提にしています。

!!! success "良い例"
    ```gherkin
    Scenario: 登録した会員を照会できる
      Given path '/api/v1/members'
      And request { name: '結合 テスト', email: '#(email)' }
      When method post
      Then status 201
      * def id = response.id

      Given path '/api/v1/members', id
      When method get
      Then status 200
      And match response == { id: '#(id)', name: '結合 テスト', email: '#(email)' }
    ```
    テストの中でデータを作り、応答の形と値をまとめて確かめています。

### match で「形」を確かめる

Karate の `match` は、応答の形を確かめるのに向いています。

| 書き方 | 意味 |
| --- | --- |
| `'#number'` | 数値であること |
| `'#string'` | 文字列であること |
| `'#notnull'` | null でないこと |
| `'#[]'` | 配列であること |
| `match response == {...}` | 項目の過不足も含めて完全に一致すること |
| `match response contains {...}` | 書いた項目が含まれること（他の項目があってもよい） |

自分の API のテストでは `==` で完全一致を確かめると、意図しない項目の追加にも気付けます。
一方、他のシステムの API を使う側のテストでは `contains` を使い、相手の項目追加で壊れないようにします。

### 互換性のある変更・壊す変更

| 変更 | 互換性 | 理由 |
| --- | --- | --- |
| 応答に任意の項目を足す | ある（多くの場合） | 利用者が知らない項目を無視すれば動く |
| 任意の入力項目を足す | ある | 送らなければ今までどおり |
| 新しい API を足す | ある | 既存の API は変わらない |
| 応答の項目を消す・名前を変える | 壊す | その項目を読んでいる利用者が壊れる |
| 項目の型を変える（数値 → 文字列） | 壊す | 利用者の読み取りが失敗する |
| 必須の入力項目を足す | 壊す | 今の利用者のリクエストが 400 になる |
| 入力の桁を短くする、形式を厳しくする | 壊す | 今まで通った値が通らなくなる |
| ステータスやメッセージ ID を変える | 壊す | 利用者の分岐が変わる |

「応答に項目を足す」が互換になるのは、利用者が知らない項目を無視する作りのときだけです。
Java の利用者が Jackson を使っている場合、Spring Boot の既定では知らない項目を無視します。
利用者の作りが分からないときは、追加も事前に知らせます。

### 版を上げるとき

互換性を壊す変更は、新しい版として出します。

例:

```text
GET /api/v1/members/{id}   ← 今の利用者のために残す（廃止予定と告知）
GET /api/v2/members/{id}   ← 新しい契約
```

- 旧版をいつ止めるかを決め、利用者に告知する
- 旧版と新版の両方に API テストを持つ
- 版を上げずに済む方法（任意の項目として足す、新しい API を足す）を先に検討する

版を上げると、作る側は 2 つの契約を保守することになります。
安易に上げず、互換のある変更で済ませられないかを先に考えます。

## サンプルアプリでは

API テストは `sample-app/src/test/resources/karate/members.feature` です。

```gherkin
Feature: 会員 API（API0001 照会 / API0002 登録）

  Background:
    * url baseUrl
    * def email = 'karate-' + java.util.UUID.randomUUID() + '@example.com'
```

- `Feature` の行に API ID（API0001・API0002）を書き、設計書と対応付けています
- `Background` で、シナリオごとに一意なメールアドレスを作っています。何回実行しても重複で失敗しません

登録と照会のシナリオでは、応答の形を完全一致で確かめています。

```gherkin
Then status 201
And match response == { id: '#number', name: '結合 テスト', email: '#(email)' }
```

失敗の結果も、ステータスとメッセージ ID で確かめています。

```gherkin
Scenario: 同じメールアドレスは登録できない
  ...
  Then status 409
  And match response.messageId == 'APPE0003'

Scenario: 存在しない会員は 404
  Given path '/api/v1/members', 999999999
  When method get
  Then status 404
  And match response.messageId == 'APPE0002'
```

入力誤り（400・APPE0001）のシナリオは、この feature にはありません。
入力誤りは単体テスト `sample-app/src/test/java/com/example/sample/member/MemberControllerTest.java` の `invalidInputReturns400` で確かめています。
結果表のどの行をどのテストで確かめるかを決めておくと、漏れを防げます。

実行の仕方は `sample-app/src/test/java/karate/ApiKarateTest.java` の Javadoc にあります。

```text
./gradlew bootRun --args='--spring.profiles.active=local'   # 別のターミナルで
./gradlew karateTest
```

クラウドの開発環境に向けるときは、`sample-app/src/test/resources/karate-config.js` のとおり `-Dkarate.env=dev -DbaseUrl=<URL>` を渡します。

版は URI の `/api/v1/` で表しています（`MemberController` の `@RequestMapping("/api/v1/members")`）。
sample-app には `v2` はありません。

## もし API テストと互換性の考え方がなかったら？

ある開発者が、会員の応答の `name` を `fullName` に名前を変えたとします。
Java のコードはコンパイルが通り、単体テストも直せば通ります。
しかし、`name` を読んでいた画面は、氏名が空になります。
API テストで `match response == {...}` を確かめていれば、リリース前に気付けました。

互換性の考え方が無いと、「項目名を変えただけ」「必須にしただけ」という小さな変更で利用者を壊します。
利用者が他チームや他社のシステムだと、直してもらうまでに時間がかかり、その間ずっと障害が続きます。

## 理解度チェック

1. `members.feature` で、メールアドレスを毎回 `UUID` から作っているのはなぜですか。

    ??? note "答え"
        何回実行しても、メールアドレスの重複（409）で失敗しないようにするためです。
        テストが DB に前回のデータが残っていることに依存しなくなります。

2. 応答に任意の項目を足す変更は、どんな条件のときに後方互換と言えますか。

    ??? note "答え"
        利用者が、知らない項目を無視する作りになっているときです。
        利用者の作りが分からないときは、追加も事前に知らせます。

3. 会員登録 API に「電話番号（必須）」を足す変更は、互換性を壊しますか。

    ??? note "答え"
        壊します。今の利用者は電話番号を送っていないので、リクエストが 400 になります。
        任意の項目として足すか、新しい版として出します。

4. 自分の API のテストでは `==`、他のシステムの API を使う側のテストでは `contains` を使うのはなぜですか。

    ??? note "答え"
        自分の API では、意図しない項目の追加も検知したいので完全一致にします。
        他のシステムの API では、相手の互換性のある項目追加でテストが壊れないよう、必要な項目だけを確かめます。

5. sample-app で、入力誤り（400）の結果はどのテストで確かめていますか。

    ??? note "答え"
        Karate ではなく、単体テスト `MemberControllerTest` の `invalidInputReturns400` で確かめています。
        `messageId` が `APPE0001` で、`details` が 2 件であることを確かめています。

## コードを読むときの確認観点

- [ ] 設計書の結果表の各行（成功・失敗）に、確かめるテストがあるか
- [ ] ステータスだけでなく、応答の形とメッセージ ID を確かめているか
- [ ] テストが既存のデータに依存せず、何回実行しても同じ結果になるか
- [ ] 応答の項目の削除・名前の変更・型の変更・必須の追加が含まれていないか
- [ ] 互換性を壊す変更なら、新しい版にして旧版の扱いを決めているか
