# 50-06 認証と認可

!!! abstract "到達目標"
    - 認証と認可の違いを、401 と 403 の使い分けと合わせて説明できる
    - IDOR（ID を書き換えると他人のデータが見える誤り）がどうして起きるかを説明できる
    - リソース単位の認可を、Service でどう確かめるかを書ける

## 何か

**認証**（Authentication）は「あなたは誰か」を確かめることです。
ログインして発行されたトークンを確かめ、リクエストを送ったのが会員 1 番だと分かる、といった処理です。

**認可**（Authorization）は「あなたはそれをしてよいか」を確かめることです。
会員 1 番が、会員 2 番の注文を見てよいか、といった判断です。

| 項目 | 認証 | 認可 |
| --- | --- | --- |
| 確かめること | 誰か | してよいか |
| 失敗したときのステータス | 401 Unauthorized | 403 Forbidden（隠したいときは 404） |
| 主な仕組み | トークン（JWT など）の検証 | ロールの確認、データの持ち主の確認 |
| どこで確かめるか | 入口で一括（フィルタ） | 機能ごと・データごと（Service など） |

**IDOR**（Insecure Direct Object Reference）は、認可の確認漏れの代表例です。
URI やリクエストに含まれる ID を書き換えるだけで、他人のデータが見えたり、変えられたりする誤りです。

## なぜ必要か

認証だけでは、データは守れません。
ログインした人なら誰でも、全員のデータを見られる状態になるからです。

IDOR は、気付きにくい誤りです。
画面からは自分の会員 ID しか送られないので、画面を操作するだけのテストでは見つかりません。
しかし API は、画面を通さずに直接呼べます。
`curl` などで ID を書き換えれば、誰でも試せます。

!!! failure "悪い例"
    ```text
    GET /api/v1/orders?memberId=1     ← 会員 1 がログインして自分の注文を見る
    GET /api/v1/orders?memberId=2     ← memberId を書き換えるだけで、会員 2 の注文が見える
    ```
    サーバは「ログインしているか」しか確かめず、「その会員の注文を見てよいか」を確かめていません。

個人情報を扱う API では、IDOR は情報漏えいに直結します。
設計書レビューでも、office-review の `API-006`「認可（誰がどのデータにアクセスできるか）が書かれている」で確かめます。

## どうやるか

### 認証は入口で一括して行う

Spring では、Spring Security で認証を行います。
次は、JWT（署名付きのトークン）を確かめる設定の「例:」です。
sample-app には Spring Security が入っていないので、使うには依存関係の追加が必要です。

例:

```java
@Configuration
public class SecurityConfig {

    @Bean
    SecurityFilterChain api(HttpSecurity http) throws Exception {
        http.authorizeHttpRequests(a -> a
                        .requestMatchers("/api/v1/**").authenticated()
                        .anyRequest().denyAll())
                .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()));
        return http.build();
    }
}
```

- トークンが無い・期限切れ・署名が不正なら、Controller に届く前に 401 になります
- 認証の処理を Controller ごとに書かないので、書き忘れが起きません

### 認可はデータごとに行う

「ログインしているか」は入口で確かめられます。
しかし「この注文はこの会員のものか」は、データを読まないと分かりません。
これは Service で確かめます。

!!! failure "悪い例"
    ```java
    // 例: memberId を利用者から受け取り、そのまま検索に使う
    @GetMapping("/api/v1/orders")
    public List<Order> list(@RequestParam("memberId") long memberId) {
        return orderService.findByMember(memberId);
    }
    ```

!!! success "良い例"
    ```java
    // 例: 会員 ID は利用者の入力ではなく、認証済みのトークンから取る
    @GetMapping("/api/v1/me/orders")
    public List<Order> list(@AuthenticationPrincipal Jwt jwt) {
        long memberId = Long.parseLong(jwt.getSubject());
        return orderService.findByMember(memberId);
    }
    ```

ID を URI で受け取る必要がある場合は、読んだデータの持ち主を確かめます。

例:

```java
@Transactional(readOnly = true)
public Order get(long loginMemberId, String orderNo) {
    Order order = mapper.findByOrderNo(orderNo)
            .orElseThrow(() -> new NotFoundException(MessageIds.ORDER_NOT_FOUND, orderNo));
    if (order.memberId() != loginMemberId) {
        // 他人の注文は「無い」ことにする（存在するかどうかも漏らさない）
        throw new NotFoundException(MessageIds.ORDER_NOT_FOUND, orderNo);
    }
    return order;
}
```

`MessageIds.ORDER_NOT_FOUND` は sample-app には無い、架空の ID です。

!!! tip "403 と 404 のどちらを返すか"
    他人のデータに 403 を返すと、「その ID のデータは存在する」ことが分かってしまいます。
    存在を知られること自体が問題なら 404 を返します。
    どちらにするかはチームの規約で決め、設計書の結果表に書きます。

### 認可のテストを書く

認可は、正常系のテストだけでは確かめられません。
「他人の ID を指定したら 404（または 403）になる」テストを必ず書きます。

例（Karate）:

```gherkin
Scenario: 他人の注文は見えない
  * header Authorization = 'Bearer ' + member1Token
  Given path '/api/v1/orders', member2OrderNo
  When method get
  Then status 404
```

### その他の注意

- 連番の ID は推測しやすいので、ID を推測されにくくしても認可の確認は省かない
- トークンやパスワードをログに出さない
- 管理者向けの API は、利用者向けの API と URI やロールを分ける

## サンプルアプリでは

sample-app には、認証・認可の仕組みはありません。
`sample-app/build.gradle` に Spring Security の依存関係は無く、誰でも会員 API を呼べます。

`sample-app/src/main/java/com/example/sample/member/MemberController.java` の照会を見ます。

```java
@GetMapping("/{id}")
public Member get(@PathVariable("id") long id) {
    return service.get(id);
}
```

`sample-app/src/main/java/com/example/sample/member/MemberService.java` の `get` も、ID で検索して返すだけです。

```java
@Transactional(readOnly = true)
public Member get(long id) {
    return mapper.findById(id).orElseThrow(() -> new NotFoundException(MessageIds.MEMBER_NOT_FOUND, id));
}
```

学習用のサンプルなので、これで構いません。
しかし、このまま会員が使う API として公開すると、ID を 1, 2, 3 と変えるだけで全会員の氏名とメールアドレスが見えます。
まさに IDOR です。

実際の API にするなら、次のどちらかが必要です。

- 会員本人向けにするなら、`GET /api/v1/me` のように、ID をトークンから取る
- 管理者向けにするなら、管理者のロールを持つ人だけが呼べるようにする

どちらにするかは、設計書に「認証の要否」と「誰がどのデータにアクセスできるか」として書きます。
ai-coding のガイドライン（`design-doc-requirements.md`）でも、API の設計書に「認証の要否」を書くことになっています。

## もし認可の確認がなかったら？

注文照会 API が `memberId` をクエリで受け取り、そのまま検索していたとします。
ある会員が、好奇心で `memberId` を 1 つずらしてみます。
他人の注文の一覧、届け先の住所、購入した商品が表示されます。
同じことをプログラムで繰り返せば、全会員の注文を集められます。

この誤りは、画面を操作する通常のテストでは見つかりません。
発覚するのは、利用者からの通報や、外部の調査によってであることが多いです。
認可は「機能が動くか」ではなく「動いてはいけないときに止まるか」を確かめる必要があります。

## 理解度チェック

1. 認証と認可の違いを、失敗したときのステータスと合わせて説明してください。

    ??? note "答え"
        認証は「誰か」を確かめることで、失敗すると 401 です。
        認可は「してよいか」を確かめることで、失敗すると 403（存在を隠したいときは 404）です。

2. `GET /api/v1/orders?memberId=2` で他人の注文が見えてしまう原因は何ですか。

    ??? note "答え"
        サーバが、利用者から受け取った `memberId` をそのまま検索に使い、ログインしている会員と一致するかを確かめていないからです。
        IDOR と呼ばれる認可の確認漏れです。

3. 会員 ID を利用者の入力ではなくトークンから取ると、何が良いのですか。

    ??? note "答え"
        利用者が ID を書き換えても、検索に使われるのはトークンの持ち主の ID だけになるからです。
        他人の ID を指定する余地がなくなります。

4. sample-app の会員照会 API をそのまま利用者向けに公開すると、どんな問題がありますか。

    ??? note "答え"
        認証も認可も無いので、ID を変えるだけで誰でも全会員の氏名とメールアドレスを見られます。
        本人向けなら ID をトークンから取り、管理者向けならロールで制限する必要があります。

5. 他人のデータへのアクセスに、403 ではなく 404 を返すことがあるのはなぜですか。

    ??? note "答え"
        403 を返すと、その ID のデータが存在することが分かってしまうからです。
        存在を知られること自体が問題なら 404 を返します。

## コードを読むときの確認観点

- [ ] 利用者から受け取った ID（会員 ID など）を、持ち主の確認なしに検索や更新に使っていないか
- [ ] 本人のデータを扱う API で、ID をトークンから取っているか
- [ ] 認証を Controller ごとに書かず、入口（フィルタ）で一括して行っているか
- [ ] 「他人の ID を指定したら拒否される」テストがあるか
- [ ] 設計書に、認証の要否と、誰がどのデータにアクセスできるかが書かれているか
- [ ] トークンやパスワードがログに出ていないか
