# 80-10 一括コミットと中間コミット

!!! abstract "到達目標"
    - 一括コミットと中間コミットの違いと、選ぶときの基準（量・要件・再実行・負荷）を説明できる
    - 設計書のトランザクションの情報から、実装のパターンを選べる
    - コードの中で、コミットとロールバックが起きる場所を特定できる
    - エラーが起きたときに DB がどんな状態になっているかを、場所ごとに説明できる

## 何か

トランザクションの基本（コミット・ロールバック・`@Transactional`）は [20-13](../20-basics/20-13-transaction.md) で学びました。
この章では、バッチの **コミットの単位** を、案件担当として選び、説明するところまでを扱います。

| パターン | やり方 | エラー時の DB |
|---|---|---|
| 一括コミット | 処理の全体を 1 つのトランザクションにし、最後に 1 回コミットする | 何も残らない（全部取り消し） |
| 中間コミット | N 件ごとに区切り、区切りごとにコミットする | 最後にコミットした区切りまでが残る |

## なぜ必要か

作業担当は、指示されたパターン（「`@Transactional` をここに付ける」）で実装できれば十分です。
案件担当は、設計書のトランザクションの情報を読み、パターンを選び、その理由を説明します。

コミットの単位は、障害のときの **後始末のしかた** を決めます。
一括コミットなら「直して最初からやり直す」で済みます。
中間コミットなら「どこまで終わったか」を確かめ、続きから再開するか、冪等に最初からやり直す必要があります。
この違いを説明できないと、障害が起きたときに運用の担当者に正しい手順を伝えられません。

## どうやるか

### 1. 選ぶ基準

| 基準 | 一括コミットが向く | 中間コミットが向く |
|---|---|---|
| 量 | 少ない（数万件まで、など。DB と性能の要件による） | 多い（数十万件以上） |
| 業務の要件 | 「全部そろって初めて意味がある」（例: 1 枚の伝票の明細） | 「1 件ずつ独立している」（例: 注文 1 件ずつ） |
| 再実行 | 最初からやり直せばよい | 途中から再開したい、または冪等に最初からやり直せる |
| DB の負荷 | ロックの時間が短く済む | 1 つのトランザクションが長いと、ロックと取り消し用の記録が大きくなる |

!!! warning "中間コミットは再実行の設計とセット"
    中間コミットで途中まで登録された後に失敗すると、DB には一部だけが残ります。
    再実行したときに二重に登録しない仕組み（冪等な登録、または処理済みの位置の記録）が必ず要ります。

### 2. 設計書のトランザクションの情報を読む

設計書には、ふつう次のどれかが書かれています。書かれていなければ質問します。

| 設計書の書き方の例 | 選ぶパターン |
|---|---|
| 「ファイル単位でコミットする。エラー時は全件ロールバック」 | 一括コミット |
| 「1,000 件ごとにコミットする。再実行時は処理済みの件を飛ばす」 | 中間コミット ＋ 冪等な登録 |
| 「明細は伝票単位でコミットする」 | 伝票ごとの中間コミット（区切りが件数ではなく、業務の単位） |

### 3. コミットとロールバックの場所を特定する

Spring の `@Transactional` は、Bean の外から呼ばれたときに、呼び出しの前後でトランザクションを始め・終えます。
コミットとロールバックは、**`@Transactional` の付いたメソッドから戻るところ** で起きます。

| メソッドの終わり方 | 結果 |
|---|---|
| 正常に戻る | コミット |
| 非検査例外（`RuntimeException` など）が外に出る | ロールバック |
| 検査例外（`IOException` など）が外に出る | 既定ではコミット（`rollbackFor` で変えられる） |
| メソッドの中で例外を捕まえて、正常に戻る | コミット（捕まえる前の操作も確定する） |

規則は [Rolling Back a Declarative Transaction（Spring）](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/rolling-back.html) にあります。
同じクラスの中から `@Transactional` のメソッドを呼んだときは、トランザクションが始まりません（自己呼び出し。
[Using @Transactional（Spring）](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html)）。

!!! failure "悪い例"
    ```java
    // 例: 中で例外を捕まえて正常に戻るので、途中までの登録がコミットされる
    @Transactional
    public int importAll(List<Order> orders) {
        int count = 0;
        try {
            for (Order o : orders) {
                count += mapper.insertIfAbsent(o);
            }
        } catch (RuntimeException e) {
            log.error("取込に失敗しました", e);
        }
        return count;
    }
    ```
    設計書が「エラー時は全件ロールバック」なら、この書き方は設計書に反します。

!!! success "良い例"
    ```java
    // 例: 例外はメソッドの外に出し、ログは呼び出し側（トランザクションの外）で出す
    @Transactional
    public int importAll(List<Order> orders) {
        int count = 0;
        for (Order o : orders) {
            count += mapper.insertIfAbsent(o);
        }
        return count;
    }
    ```

```java
} catch (Exception e) {
    log.error("{} JOB0001 異常終了", MessageIds.BATCH_FAILED, e);
    exitCode = ERROR;

```

`catch` はジョブの側（トランザクションの外）にあります。
`importLines` の中で DB の例外が起きると、例外が `importLines` の外に出る時点でロールバックされ、その後で `catch` に届きます。
そのため、異常終了したときの `orders` テーブルには、このファイルの行は 1 件も残りません。

一括コミットを選んだ理由と限界は、`local/README.md` の「取込の大きさとコミットの単位」に書かれています。
大きなファイルを扱う実案件では、一定の件数ごとにコミットする設計に変えるよう述べています。
再実行で二重にならないのは、`OrderMapper.xml` の `ON CONFLICT (order_no) DO NOTHING` で登録済みの注文番号を飛ばすからです（[30-11](../30-reading/30-11-idempotent-insert.md)）。

## もしコミット単位の説明がなかったら？

夜間のバッチが異常終了し、運用の担当者から「再実行してよいか」と聞かれたとします。
コミットの単位を知らなければ、「DB に何が残っているか」を答えられません。
念のためにデータを手で消してから再実行する、といった危ない作業をすることになります。

一括コミットだと分かっていれば「何も残っていないので、原因を直して再実行してよい」と答えられます。
中間コミットなら「最後のコミットまでは残っている。登録は冪等なので、そのまま再実行してよい」と答えられます。

## 理解度チェック

1. 中間コミットを選ぶとき、必ず合わせて設計することは何ですか。
2. `@Transactional` のメソッドの中で例外を捕まえて正常に戻ると、どうなりますか。
3. JOB0001 で DB の例外が起きたとき、`orders` テーブルにはこのファイルの行が残りますか。理由も答えてください。
4. 「伝票ごとにコミットする」のは、一括と中間のどちらに近いですか。

??? note "答え"
    1. 再実行の方法です。途中までの登録が残るので、冪等な登録か、処理済みの位置の記録が要ります。
    2. コミットされます。例外が起きる前の操作も確定します。
    3. 残りません。トランザクションの境界は `importLines` で、例外がその外に出るときにロールバックされるからです。ジョブの `catch` はその後です。
    4. 中間コミットです。区切りが件数ではなく、業務の単位（伝票）になっています。

## コードを読むときの確認観点

- [ ] `@Transactional` がどのメソッドに付いていて、だれから呼ばれているか（同じクラスの中からではないか）
- [ ] トランザクションの中で例外を捕まえて、正常に戻っていないか
- [ ] 検査例外を投げるメソッドで、ロールバックが要るなら `rollbackFor` を指定しているか
- [ ] 中間コミットなら、再実行が冪等になっているか
- [ ] 設計書のコミット単位と、実装のトランザクションの境界が一致しているか
