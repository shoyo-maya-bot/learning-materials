# 80-09 ブランチ戦略とコンフリクト対応

!!! abstract "到達目標"
    - 代表的なブランチ戦略と、それぞれが何を守るための決まりかを説明できる
    - コンフリクトが起きたとき、両方の変更の意図を確かめて解消し、テストで確かめられる
    - push した後に誤りに気づいたとき、`revert` と `reset` のどちらを使うべきかを判断できる
    - 自分で対処してよい問題と、すぐ報告すべき問題を区別できる

## 何か

**ブランチ戦略** は、チームでブランチをどう作り、どこに、どの順でマージするかの決まりです。
代表的なものを並べます。

| 戦略 | 形 | 守りたいもの |
|---|---|---|
| main と作業ブランチ | `main` から作業ブランチを作り、PR でマージする | `main` がいつも動く状態であること。変更が必ずレビューを通ること |
| 開発用とリリース用を分ける | `develop` に集め、出荷のときに `release` を切って `main` へ | 開発中の変更と、出荷する版を分けること。出荷前の修正を、開発中の変更と混ぜないこと |
| 長く残す専用のブランチ | 用途の違う版を、別のブランチとして持ち続ける | 用途ごとの版を、混ぜずに保つこと |

**コンフリクト**（衝突）は、2 つのブランチが同じ箇所を別々に変えたため、Git が自動で合わせられない状態です。
Git は、衝突した箇所に印を付けて、人の判断を待ちます
（[How conflicts are presented（git-merge）](https://git-scm.com/docs/git-merge#_how_conflicts_are_presented)）。

## なぜ必要か

作業担当は、決められたブランチでコミットし、PR を作れれば十分です（[20-18](../20-basics/20-18-git-flow-review.md)）。
案件担当は、決まりの意図を理解し、決まりどおりにいかない場面で正しく判断します。

コンフリクトの解消を誤ると、どちらかの変更が黙って消えます。
コンパイルが通り、テストも（その部分のテストが無ければ）通るので、気づくのは後です。
誤って push したものの戻し方を誤ると、他の人の履歴を壊します。

## どうやるか

### 1. 作業ブランチを新しく保つ

作業ブランチが古いほど、コンフリクトは大きくなります。
長く作業するときは、こまめに `main` の変更を取り込みます。

```bash
git fetch origin
git merge origin/main      # チームの決まりが rebase なら git rebase origin/main
```

### 2. コンフリクトを解消する

衝突した箇所は、次のような印で示されます。

```text
<<<<<<< HEAD
    if (quantity < 1 || quantity > 999) {
=======
    if (quantity < 1 || quantity > MAX_QUANTITY) {
>>>>>>> origin/main
```

解消の手順です。

1. 衝突したファイルの一覧を見る（`git status`）
2. 両方の変更が **何のためか** を確かめる。相手のコミットメッセージと PR を読む（`git log origin/main -- <ファイル>`）
3. 両方の意図を満たす形に書き直す。片方を丸ごと選ぶのは、もう片方の意図が不要だと確かめたときだけ
4. 印（`<<<<<<<`・`=======`・`>>>>>>>`）を消す
5. ビルドとテストを通してから、コミットする

!!! failure "悪い例"
    衝突したので、とりあえず自分の側（HEAD）を選んで、テストをせずに push する。
    相手が上限を定数にした変更が消え、後で上限を変えたときに、ここだけ古い値のまま残ります。

!!! success "良い例"
    相手の PR を読み、「上限を定数 `MAX_QUANTITY` にまとめた」変更だと確かめる。
    自分の側の変更（別の行のチェックの追加）と合わせて、定数を使う形にする。テストを通してからコミットする。

!!! tip "意図が分からないときは聞く"
    相手の変更の意図が分からないときは、推測で解消せず、変更した本人に聞きます。
    数分の会話で、消えてはいけない変更を守れます。

### 3. 誤りに気づいたときの戻し方

| 状況 | 使うもの | 理由 |
|---|---|---|
| まだ push していないコミットを直したい | `git commit --amend`・`git reset` | 自分の手元だけの履歴なので、書き換えてよい |
| push 済み・他の人も使うブランチの変更を戻したい | `git revert <コミット>` | 打ち消すコミットを足すので、他の人の履歴を壊さない |
| PR がマージされた後に不具合が分かった | `revert` の PR を作る、または修正の PR を作る | どちらが早く安全かを判断する。迷ったら相談する |

`main` のように皆が使うブランチで `git reset` と `git push --force` を使うと、他の人の手元の履歴と食い違い、作業を失わせることがあります
（[git-revert](https://git-scm.com/docs/git-revert)）。

### 4. すぐ報告すべき問題

| 問題 | すること |
|---|---|
| パスワードや鍵をコミットして push した | 自分で消そうとせず、すぐリーダーに報告する。鍵の無効化が先 |
| `main` を壊した（ビルドやテストが通らない） | 報告し、`revert` で戻すかを相談する |
| 他の人のコミットを消してしまったかもしれない | 何をしたかを正確に伝えて相談する（`git reflog` で戻せることが多い） |

## サンプルアプリでは

dev-environment は、「長く残す専用のブランチ」を使っています。
教材の演習用の `exercise-base` ブランチと、修正済みの `main` ブランチです。
`README.md` は、2 つのブランチの関係を次のように説明しています。

<!-- src: README.md @main -->
```markdown
> 教材（learning-materials）の演習は、弱いところを直す前のコードを残した **`exercise-base` ブランチ** で解きます。`main` は修正済みです（`git diff exercise-base main -- sample-app` で直し方を比べられます）。
```

`exercise-base` に `main` の修正をマージすると、演習で見つけてもらう弱いところが消えてしまいます。
このブランチの決まりが守りたいのは、「演習の前提が崩れないこと」です。
意図を知っていれば、「`main` が新しいから `exercise-base` にもマージしよう」という誤りを防げます。

改行コードの違いによる無駄な衝突は、`.gitattributes` で防いでいます（[20-18](../20-basics/20-18-git-flow-review.md)）。

<!-- src: .gitattributes @main -->
```text
* text=auto eol=lf
*.bat text eol=crlf
```

## もし決まりの意図の理解がなかったら？

決まりを形だけ守っていると、決まりに書かれていない場面で誤ります。
たとえば「出荷前の修正は `release` ブランチで」という決まりの意図を知らないと、
緊急の修正を `develop` にだけ入れて、出荷する版に入れ忘れます。

コンフリクトでも同じです。
両方の変更の意図を確かめずに片方を選ぶと、消えた変更の持ち主が気づくまで、不具合が眠り続けます。

## 理解度チェック

1. 「main と作業ブランチ」の戦略で、PR を必ず通す決まりが守っているものは何ですか。
2. コンフリクトを解消した後、コミットする前にすることは何ですか。
3. push 済みの `main` の変更を戻すとき、`git reset` ではなく `git revert` を使う理由は何ですか。
4. パスワードを push してしまったとき、最初にすべきことは何ですか。

??? note "答え"
    1. `main` がいつも動く状態であることと、すべての変更がレビューと CI を通ることです。
    2. 印が残っていないかを確かめ、ビルドとテストを通すことです。
    3. `revert` は打ち消すコミットを足すので、他の人の履歴と食い違わないからです。`reset` で履歴を書き換えて強制的に push すると、他の人の作業を失わせることがあります。
    4. 自分で消そうとせず、すぐリーダーに報告することです。履歴から消しても、すでに取得された可能性があるため、鍵やパスワードの無効化が先です。

## コードを読むときの確認観点

- [ ] 長く残すブランチが、何のためにあるかが分かるか
- [ ] `.gitattributes` などで、改行コードの違いによる衝突を防いでいるか
- [ ] コンフリクトを解消したコミットで、両方の変更の意図が残っているか
