## 演習 1: ローカルのサービスと本番の差

**答え（例）**:

| サービス | 本番で代わりをしているもの | 差で起きうる不具合 |
|---|---|---|
| `db` | クラウドの管理された PostgreSQL（Aurora PostgreSQL） | パスワードが固定（`.env`）なので、本番の秘密情報の受け渡し（環境変数・秘密情報の管理の仕組み）の誤りに気づけない。データが数件なので、遅い SQL に気づけない |
| `s3` | S3 | エミュレータは固定のキーで何でも読めるので、本番のロールの権限の不足に気づけない。S3 にしか無い機能の違いで動きが変わることがある |

**考え方**: `local/docker-compose.yml` のコメントにある「クラウドのサービスはエミュレータで代替し、ローカルからクラウドには接続しない」を手がかりに、
何を代わりにしているかと、その代わりが「本物と違う点」を挙げていれば正解です。

## 演習 2: Dockerfile の変更

**答え**:

- (a) コンテナが root（管理者）で動きます。アプリの弱点を突かれたとき、コンテナの中で何でもできてしまい、被害が大きくなります
- (b) 実行用のイメージに JDK・Gradle・ソースコード・ビルドの途中のファイルが残ります。イメージが大きくなり、攻撃に使える道具も増えます
- (c) シェルを通して起動する形になり、Java がシェルの子のプロセスになります。停止の合図（SIGTERM）が Java に届かず、正しく終了処理ができないことがあります

**考え方**: 各命令が「何のために」そう書かれているかを説明できていれば正解です。
根拠は [Dockerfile reference（Docker）](https://docs.docker.com/reference/dockerfile/) の ENTRYPOINT の節と、
[Building best practices（Docker）](https://docs.docker.com/build/building/best-practices/) にあります。

## 演習 3: 共通部品の更新

**答え（例）**:

| 取り込み方 | 手順 | 上げる前に確かめること |
|---|---|---|
| (a) パッケージレジストリ | `build.gradle` の依存の版を 1.4.0 から 1.5.0 に変え、ビルドとテストを通して PR を出す | 1.5.0 の変更点（リリースノート）に、使っている機能の変更・廃止が無いか。自分の案件のテストがすべて通るか |
| (b) git submodule | 部品のフォルダで 1.5.0 のコミット（タグ）を取り出し、使う側のリポジトリでその変更をコミットする。他の人は `git submodule update` で取り込む | (a) と同じ。加えて、使う側のリポジトリが指すコミットが 1.5.0 のものになっているか（`git submodule status`） |

**考え方**: どちらも「新しい版が出た」だけでは、使う側は変わりません。
使う側で版（またはコミット）を上げる作業をして、初めて新しい版が使われます。
上げるときは、変更点とテストで影響を確かめ、PR のレビューを通します。
