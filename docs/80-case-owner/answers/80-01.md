## 演習 1: 1 本あたりの作業の分解

**答え（例）**:

| 作業 | 見るファイル | 目安 |
|---|---|---|
| 設計書の読み込みと質問 | 設計書 | 0.25 人日 |
| 入力の record と入力チェック（Bean Validation） | `MemberController.java` の `RegisterRequest` | 0.25 人日 |
| Controller のメソッド | `MemberController.java` | 0.25 人日 |
| Service の業務ロジック（業務エラーを含む） | `MemberService.java` | 0.5 人日 |
| Mapper のインタフェースと SQL | `MemberMapper.java`・`MemberMapper.xml` | 0.5 人日 |
| 単体テスト（Service・Controller） | `MemberServiceTest.java`・`MemberControllerTest.java` | 0.75 人日 |
| API テスト（Karate） | `members.feature` | 0.25 人日 |
| レビューと指摘の対応 | PR | 0.25 人日 |

**考え方**: 実装だけでなく、読む・テストする・レビューを受ける作業を分けて書くのが大事です。
目安の数字は例です。チームの実績があれば、その値を使います。

**よくある誤り**: 「Controller・Service・Mapper」の 3 つだけに分け、テストとレビューを入れない。

## 演習 2: 手法の選択と理由

**答え（例）**:

```text
手法: 規模ベース（API 1 本あたり 3 人日 × 4 本 = 12 人日）を主にし、共通部分だけ積み上げで足す
理由: 同じ種類の API が 4 本あり、1 本あたりの実績がチームにあるため
      共通の部分（エラー応答の追加、メッセージ ID の追加）は API の数に比例しないので、積み上げで足す
使わなかった手法:
  積み上げだけ … 演習 1 の分解で積み上げると 1 本 3 人日となり実績と合うので、確かめに使う
  三点見積 … 4 本とも既存と同じ形で、不確実な作業が少ない
  類推 … 規模ベースと同じ実績を使うことになり、別の確かめにならない
```

**考え方**: 「なぜこれを選んだか」と「なぜ他を選ばなかったか」が、実績・情報の量・不確実さの 3 つで説明できていれば正解です。
規模ベースと積み上げの両方で出し、差を確かめると、より説得力があります。

**よくある誤り**: 「慣れているので積み上げ」。慣れは理由になりません。

## 演習 3: 三点見積

**答え（例）**: 新しい API のうち、既存に無い種類のもの（例: 他システムの API を呼ぶ）の「外部との結合の確認」。
O=0.5、M=1、P=4 なら、期待値は (0.5 + 4 + 4) / 6 ≒ 1.4 人日。

**考え方**: 三点見積は、結果の幅が大きい作業に使います。
既存と同じ形の Controller の実装のように、幅の小さい作業に使っても意味が薄いです。
