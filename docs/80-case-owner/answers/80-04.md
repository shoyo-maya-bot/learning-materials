# 80-04 解答

本文: [80-04 不具合とレビューの記録から品質を見る](../80-04-defect-quality.md)

## 演習 1: 不具合票の書き直し

**答え（例）**:

```text
件名: メールアドレスが 255 文字の会員登録が 400 になる（期待結果の確認が必要）
環境: ローカル（main ブランチ）
手順: 1. API を起動する
      2. POST /api/v1/members に {"name":"山田","email":"<255 文字のメールアドレス>"} を送る
期待結果: （仕様の確認が必要）
実際の結果: 400。メッセージ ID APPE0001（入力チェックの誤り）
影響: 長いメールアドレスの利用者が登録できない（仕様どおりなら影響なし）
補足: 入力チェックは 254 文字まで（RegisterRequest の @Size(max = 254)）、
      DB の列も VARCHAR(254)。両者は一致している。
```

**考え方**: 書き直すために調べると、「長いとエラーになる」は **仕様どおり** の可能性が高いと分かります。
`MemberController.java` の `RegisterRequest` は `@Size(max = 254)`、`local/db/init/01_schema.sql` の `email` も `VARCHAR(254)` です。
不具合票を書く前に、期待結果（仕様）を確かめるのが大事です。
「何文字で」「どんなエラーか」が書かれていれば、仕様どおりか不具合かをすぐ判断できます。

**よくある誤り**: 文字数を書かずに「長いと」のまま起票する。直す人が、何文字で試せばよいか分かりません。

## 演習 2: 横展開と再発防止

**答え（例）**:

- 横展開: 同じ設計書から作った他の機能について、設計書の読み違いが無いかを、設計者と一緒に読み合わせる
- 再発防止: 実装の前に、各 STEP の処理内容と処理目的を書き出し、設計者に確かめてもらう小工程を入れる（[80-06](../80-06-read-design.md)）

**考え方**: 横展開は「今ある成果物」に、再発防止は「これからの作り方」に手を打ちます。
「設計書の読み違い」が多いなら、設計書の書き方（あいまいな言葉）が原因のこともあります。
その場合は、設計書の側の改善も提案します。

## 演習 3: 密度の比較

**答え**: 機能 A は 1,000 行あたり 1 件、機能 B は 1,000 行あたり 8 件です。機能 B を詳しく調べます。
合わせて、両機能のテストの量と観点（テストケースの数・境界値や異常系があるか）を確かめます。

**考え方**: 件数だけなら B の 4 件は A の 2 件の 2 倍ですが、大きさで割ると 8 倍です。
ただし、A の密度が低いのは、テストが浅いからかもしれません。
A のテストの観点が足りなければ、A も詳しく見る対象です。
