# 80-11 解答

本文: [80-11 データの入出力方式](../80-11-data-io.md)

## 演習 1: 方式の選択

**答え**:

- (a) List。5 件しかなく、全件をメモリに持っても問題になりません。いちばん簡単に書けます
- (b) Cursor。20 万件を List で持つと、メモリの使用量が大きくなります。最初からやり直してよいので、中間コミットや再開の仕組みは要りません
- (c) ItemReader（Spring Batch）。500 万件で量が多く、「続きから再開したい」要件があります。区切りごとのコミットと、再開の仕組みを枠組みで使えます

**考え方**: 量と、再開の要件の 2 つで説明できていれば正解です。
(b) を List にしても、メモリが十分にあれば動きます。そのときは「最大の件数 × 1 件の大きさ」でメモリを見積もり、根拠を残します。

## 演習 2: JOB0001 を 1 行ずつ読む方式に変えたら

**答え（例）**:

| 箇所 | 変わること |
|---|---|
| `FileFetcher` | 戻り値を `List<String>` から、1 行ずつ取り出せる形（`BufferedReader` や `Stream<String>` など、閉じる必要のあるもの）に変える |
| `DefaultFileFetcher` | `Files.readAllLines` や `readNBytes` で全体を読むのをやめ、ストリームを開いて返す。全体の大きさの上限（`app.batch.max-input-bytes`）は、メモリを守るためには要らなくなる（別の理由で残すかは判断する） |
| `OrderImportService.importLines` | `lines.get(0)` と `lines.size()` を使えなくなる。1 行目を読んで見出しを確かめ、残りを順に読むループに書き換える。行番号は自分で数える。読み終わったら閉じる |
| テスト | `List.of(...)` で渡していた入力を、`BufferedReader(new StringReader(...))` などに包んで渡す。閉じたことを確かめるテストを足す |

メモリは、全行分から、1 行分（と読み込みのバッファ）に減ります。
ただし、エラーの行の一覧（`errors`）は今のまま全部持つので、エラーが極端に多いとメモリを使います。

トランザクションは、`importLines` に `@Transactional` が付いたままなら、一括コミットのままです。
読み方を変えただけでは、コミットの単位は変わりません。
大きなファイルで 1 つのトランザクションが長くなる問題を解くには、[80-10](../80-10-commit-unit.md) の中間コミットに変える必要があります。

**考え方**: 「読み方（メモリ）」と「コミットの単位（トランザクション）」は、別々に決まることを分けて説明できていれば正解です。

## 演習 3: Cursor を返すメソッド

**答え**: 2 つの問題があります。

- トランザクションの中で読み終える形になっていない。`@Transactional` が無いので、Mapper の呼び出しから戻った時点で接続が閉じられ、呼び出し側で読み進められない
- `Cursor` を閉じる責任が、呼び出し側にあいまいに渡っている。閉じ忘れると、DB の資源が残る

**考え方**: `Cursor` は、開いたメソッドの中で、トランザクションの中で読み終え、`try-with-resources` で閉じる形にします。
呼び出し側に 1 件ずつの処理を渡したいなら、処理（例: `Consumer<Order>`）を引数で受け取り、メソッドの中で回します。

```java
// 例: 演習 3 の修正案
@Transactional(readOnly = true)
public int forEachOrder(String orderDate, Consumer<Order> action) throws IOException {
    int count = 0;
    try (Cursor<Order> cursor = mapper.openCursorByDate(orderDate)) {
        for (Order o : cursor) {
            action.accept(o);
            count++;
        }
    }
    return count;
}
```
