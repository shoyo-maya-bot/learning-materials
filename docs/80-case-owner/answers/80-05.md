## 演習 1: SQL の文字列連結

**答え**: 修正です。

**考え方**: `${code}` は、値をそのまま SQL の文字列に埋め込みます。
入力に `'` を含む値が来ると、SQL の意味が変わります（SQL インジェクション）。
`#{code}` に直せば、値はパラメータとして渡されます（[30-08](../../30-reading/30-08-mapper-sql.md)、
[Mapper XML ファイル（MyBatis）](https://mybatis.org/mybatis-3/ja/sqlmap-xml.html) の「文字列代入」）。
抑止してよい理由はありません。

**よくある誤り**: 「呼び出し側で値を確かめているので抑止」。呼び出し側は将来変わります。この SQL 自体を安全にするのが正しい直し方です。

## 演習 2: 例外の握りつぶし

**答え**: 修正（ログを出す）です。続行する判断そのものは正しいので、残します。

```java
// 例: 演習 2 の修正案
try {
    Files.deleteIfExists(tempFile);
} catch (IOException e) {
    // 一時ファイルの削除に失敗しても処理は続ける（次回の起動時に消す）
    log.warn("一時ファイルを削除できませんでした: {}", tempFile, e);
}
```

**考え方**: 削除の失敗を何も残さないと、ディスクが一時ファイルで埋まったときに原因を追えません。
処理を止める必要は無いので、WARN で記録して続けます。
どうしても何もしないなら、抑止して「なぜ記録も要らないか」を書きます。

## 演習 3: null の可能性

**答え**: 修正を勧めます（抑止も選べますが、根拠が弱い）。

**考え方**: 「直前の処理で全会員の名前を入れてある」は、今のコードでは正しくても、
コードの外（`names` を作る処理）が変わると崩れる前提です。
`Map.get` は、キーが無ければ `null` を返します。
見つからないときの扱いを決めて書く方が、安全で読みやすくなります。

```java
// 例: 演習 3 の修正案
String name = names.get(memberId);
if (name == null) {
    throw new IllegalStateException("会員の名前がありません: " + memberId);
}
return name.trim();
```

抑止するなら、「`names` は同じメソッドの中で全会員を入れて作り、外から変えられない」と、根拠をコードで示せる場合に限ります。

## 演習 4: 使っていない private メソッド

**答え**: 修正（テストの書き方を直す）を勧めます。

**考え方**: ツールの指摘は、本番のコードから呼ばれていない、という意味で正しいです（誤検知ではありません）。
テストのためだけに private メソッドを残し、リフレクションで呼ぶと、名前を変えたときにテストが壊れることに気づきにくくなります。
public のメソッドを通してテストするか、メソッドを別のクラスに切り出してテストします。
すぐに直せない事情があれば、理由を書いて抑止し、直す課題を起票します。
