# 80-03 解答

## 演習 1: 報告を書く

**答え（例）**:

```text
【事実】小工程 12 個中 3 個が完了（予定 5 個）。進捗率 25%（予定 42%）。
        完了した 3 個の実績は 4.5 人日（見積 3 人日の 1.5 倍）。
【原因】テスト用の DB が 2 日間使えなかった（現在は復旧済み）。
【見通し】残り 9 個。期限（12 日目）までに使えるのは 7 日（1 人で進める前提）。
          実績の比率 1.5 倍が続くと 13.5 人日かかり、約 6.5 日遅れる。
          DB の停止による分を除いた比率（1.0 倍）なら 9 人日で、約 2 日遅れる。
【対策】DB が使えない間も進められるよう、テストを DB を使わない偽物（フェイク）で先に書く。
        比率が 1.0 倍に戻るかを、明日・明後日の 2 日で確かめる。
【相談】2 日の遅れについて、期限を延ばすか、優先度の低い小工程（2 個）を次の段階に回すかの判断をお願いします。
        判断の期限: 明後日。
【リスク】DB が再び止まると遅れが広がる。DB の担当に、停止の原因と再発の可能性を確認中。
```

**考え方**: 数字（完了数・進捗率・実績の比率）と見通しを出し、相談したいことを期限付きで書いていれば正解です。
見通しを 2 通り（原因が続くとき・続かないとき）出すと、判断する人が状況をつかみやすくなります。

**よくある誤り**: 「DB が止まっていたので遅れましたが、取り戻します」。数字も見通しも相談もありません。

## 演習 2: エスカレーションすべきもの

**答え**: (b) と (d) です。

- (b) 終了コードは運用（監視の設定・再実行の手順）に関わる仕様で、自分で決めてはいけません。どちらが正しいかを、設計者と運用の担当に確かめる必要があります
- (d) 他のチームの遅れは、自分の案件の範囲を超え、結合試験の日程に響きます。早く上げるほど、取れる手が増えます
- (a) は規約を調べるか、レビューで聞けば足ります
- (c) は自分で解決できています（記録は残します）

## 演習 3: 取れる手と推奨（(d) の例）

**答え（例）**:

```text
【事実】他チームの API の公開が、予定の 10 日から 17 日にずれる見込み（相手の担当者から聞いた）。
【影響】結合試験の開始が 1 週間遅れ、マイルストーン「結合試験完了」に間に合わない。
【取れる手】
  1. 相手の API の偽物（モック）を作り、先に自分の側の試験を進める
     良い点: 遅れを数日に抑えられる  悪い点: モックを作る工数（1 人日）、本物とのずれの危険
  2. 結合試験の順番を入れ替え、相手の API を使わない試験を先にする
     良い点: 追加の工数が無い  悪い点: 相手の API の試験の期間が短くなる
【推奨】1 と 2 を組み合わせる。モックは相手の OpenAPI から作り、ずれの危険を下げる。
【相談】モックを作る 1 人日の追加を認めてほしい。
```
