# 80-09 解答

本文: [80-09 ブランチ戦略とコンフリクト対応](../80-09-branch-conflict.md)

## 演習 1: exercise-base に main をマージしてはいけない理由

**答え（例）**: 差の中には、演習で見つけてもらう弱いところの修正が入っています。
たとえば `OrderImportService.java` では、`main` は存在しない会員の行を登録の前に確かめて飛ばしますが、`exercise-base` にはその確認がありません。
マージすると、この弱いところが消え、教材の演習（「存在しない会員の行があると何が起きるか」など）の前提が崩れます。

**考え方**: 差を実際に表示して、具体的な 1 つを挙げられていれば正解です。
差の中身は、dev-environment の更新で変わることがあります。
ブランチの決まりの意図（演習の前提を守る）から、マージしてはいけないと説明できることが大事です。

## 演習 2: コンフリクトの解消

**答え**:

```java
// 例: 両方の意図（行番号を足す・文言を変える）を満たす
errors.add(lineNo + ": member_id の会員が見つかりません（" + order.memberId() + "）");
```

**考え方**: 自分の側（行番号）と相手の側（文言）は、同じ行の別々の部分を変えています。
片方を選ぶと、もう片方の意図が消えます。両方を合わせて書き直します。
文言を変えたので、メッセージを確かめているテスト（`OrderImportServiceTest` など）も直す必要があります。
解消した後に、ビルドとテストを通して確かめます。

**よくある誤り**: 自分の側（HEAD）をそのまま選ぶ。相手が変えた文言が黙って元に戻ります。

## 演習 3: 場面ごとの判断

**答え**:

- (a) `git rebase -i HEAD~2` で、直したいコミットを `reword` にしてメッセージを書き直す（まだ push していないので、履歴を書き換えてよい）
- (b) `revert` の PR を作るか、修正の PR を作るかを判断する。原因がはっきりしていて、戻しても他の変更に影響が無いなら `git revert <マージのコミット> -m 1` で戻すのが早く安全。判断に迷ったら、すぐリーダーに相談する
- (c) `main` から新しいブランチを作り直し、自分のコミットだけを `git cherry-pick` で移す（まだ push していないので、他の人への影響は無い）

**考え方**: 「push したか（他の人がその履歴を持っているか）」で、履歴を書き換えてよいかが決まります。
本番の不具合は、自分だけで判断せず、早く知らせることが大事です。
