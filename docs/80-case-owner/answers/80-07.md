## 演習 1: STEP とコードの対応

**答え**:

| STEP | コードの場所 |
|---|---|
| 1 引数を確かめる | `OrderImportJob.run` の最初（`args.getOptionValues("input")`） |
| 2 ファイルを読む | `FileFetcher.readLines`（実装は `DefaultFileFetcher.readLines`） |
| 3 見出し行を確かめる | `OrderImportService.importLines` の最初（`HEADER.equals(...)`） |
| 4 解析・確認・登録 | `OrderImportService.importLines` のループ、`parse`、`OrderMapper` の `memberExists`・`insertIfAbsent`・`existsSame` |
| 5 結果を出し終了コードを決める | `OrderImportJob.run` の `log.info(...)` と `exitCode = ...` |

## 演習 2: 値の出どころ

**答え**:

| 値 | 出どころ | 決まる場所 |
|---|---|---|
| (a) S3 の接続先 | 設定ファイル | `S3Config` が `@Value("${app.s3.endpoint:}")` で受け取る。ローカルは `application-local.yml`（環境変数 `S3_ENDPOINT` で上書き可）、本番は未指定で標準の接続先 |
| (b) 入力の場所 | 変数 | 起動引数 `--input`。`OrderImportJob.run` で受け取る |
| (c) 数量の上限 999 | 定数 | `OrderImportService.parse` の `if` に直接書かれている。DB の `CHECK (quantity BETWEEN 1 AND 999)` と対応 |
| (d) ジョブ ID | 定数 | `OrderImportJob` の `JOB_ID`。どのジョブを動かすかは設定 `app.batch.job`（`@ConditionalOnProperty`）で選ぶ |

**考え方**: (c) の 999 は、名前の付いた定数ではなく、数字が直接書かれています。
変えるときは、コード・DB の制約・設計書の 3 か所を合わせて変える必要があります。

## 演習 3: 単価の列を足すときの影響範囲

**答え（例）**:

| モジュール | 直す | 中身 |
|---|---|---|
| 入力ファイル | 直す | 見出しに `unit_price` を足す。`local/data/orders.csv` のサンプルも直す |
| Service（`OrderImportService`） | 直す | `HEADER` の定数、`parse` の列数（4 → 5）と単価の解析・範囲チェック、Javadoc の入力の説明、内容の違う重複のメッセージ（比べる項目に単価を入れるなら） |
| record（`Order`） | 直す | `unitPrice` の部品を足す。`new Order(...)` を呼んでいる箇所（`parse`・テスト）も全部直す |
| Mapper XML（`OrderMapper.xml`） | 直す | `insertIfAbsent` の列と `#{unitPrice}`。`existsSame` の条件に単価を入れるかは、仕様として決める |
| Mapper インタフェース（`OrderMapper`） | 変更なし（確認済み） | 引数が `Order` なので、メソッドの形は変わらない |
| ジョブクラス（`OrderImportJob`） | 変更なし（確認済み） | 件数と終了コードの決め方は変わらない。単価の合計をログに出す、などの要件があれば直す |
| DDL（`01_schema.sql`） | 直す | `orders` に `unit_price` の列と `CHECK` の制約。既存の環境では列を足す SQL（移行）も要る |
| テスト | 直す | `OrderImportServiceTest`・`OrderImportJobTest` の入力の行（全部 5 列にする）、単価の境界値のテスト。`FakeOrderMapper` は `Order` の `equals` で比べるので、単価も自動で比べる対象になる |
| 手順書 | 直す | `local/README.md` の入力の形式の説明 |

**考え方**: データの流れ（ファイル → 解析 → record → SQL → テーブル）に沿って、順に確かめます。
「変更なし」の行にも、確かめた理由を書きます。
`existsSame` に単価を入れるかどうかのように、仕様として決めることが見つかったら、設計者に確かめます。

**よくある誤り**:

- DDL だけ直し、`Order` と XML を直さない（単価が登録されない）
- 既存のテストの入力が 4 列のままで、全部が形式エラーになる
- 既存の環境の DB に列を足す移行を忘れる
