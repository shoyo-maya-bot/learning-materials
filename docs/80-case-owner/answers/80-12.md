# 80-12 解答

本文: [80-12 共通項目の部品とログレベルの運用](../80-12-common-columns-logging.md)

## 演習 1: sample-app の共通項目

**答え**:

| テーブル | 共通項目にあたる列 | 値を入れる仕組み |
|---|---|---|
| `member` | `created_at` | DB の既定値 `DEFAULT now()`（`MemberMapper.xml` の INSERT は列を書いていない） |
| `orders` | `imported_at` | DB の既定値 `DEFAULT now()`（`OrderMapper.xml` の INSERT は列を書いていない） |

**考え方**: どちらも「作成日時」だけで、更新日時・作成者・更新者・版番号はありません。
sample-app には更新の SQL が無いので、作成日時だけで足りています。
実案件では、チームの標準の共通項目の一覧と見比べて、足りない列を確かめます。

## 演習 2: 名前の変更で足すもの

**答え（例）**:

| 箇所 | 足すもの |
|---|---|
| テーブル（`01_schema.sql`） | `updated_at`（と、必要なら `updated_by`）の列 |
| Mapper XML | 名前の UPDATE に `updated_at = #{updatedAt}`（または `updated_at = now()`）を入れる |
| テスト | 名前を変更した後に、`updated_at` が変更の時刻になっていることを確かめる。名前以外の項目（`created_at`）が変わっていないことも確かめる |

**考え方**: `DEFAULT now()` は UPDATE では効かないので、更新日時は SQL か部品で明示的に入れる必要があります。
値をアプリから渡すか、DB の `now()` を使うかは、チームの標準に合わせます（時刻の基準をそろえるため）。

## 演習 3: ログレベル

**答え**:

| ログ | レベル | 理由 |
|---|---|---|
| (a) バッチが開始した | INFO | 正常な流れの節目。対応は要らない |
| (b) 入力ファイルが見つからず終了した | ERROR | 取込が 1 件もされていない。後続の処理にも響くので、すぐ対応が要る |
| (c) 会員が存在しない行を飛ばした | WARN | 取込は続いた。後で人が確かめればよい |
| (d) 登録済みのメールアドレスで 409 を返した | WARN（または INFO） | 利用者の入力による想定内の業務エラー。対応は要らない。ERROR にすると誤報になる |

**考え方**: 「運用の担当者は何をすべきか」で決めていれば正解です。
(d) は、sample-app の `ApiExceptionHandler` では業務エラーを WARN で出しています。
件数が多く、ふだん見る必要が無いなら INFO にするチームもあります。いずれにせよ ERROR にはしません。
