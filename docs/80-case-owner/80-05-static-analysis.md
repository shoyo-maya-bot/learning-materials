# 80-05 静的解析の指摘を判断する

!!! abstract "到達目標"
    - 静的解析の指摘の代表的な種類（null・資源の閉じ忘れ・例外の握りつぶし・SQL の組み立てなど）の意味を説明できる
    - 指摘ごとに「修正する」「理由を書いて抑止する」「誤検知として除外する」を判断できる
    - 「重大度の高い指摘 0 件」という品質基準が何を保証し、何を保証しないかを説明できる
    - 抑止と除外を、レビューで確かめられる形で残せる

## 何か

**静的解析** は、プログラムを動かさずに、ソースコードを読んで問題の候補を見つける仕組みです。
静的解析ツールは、決まった規則（ルール）に当てはまる書き方を見つけ、**指摘** として一覧に出します。

指摘には、ふつう次の情報が付きます。

| 情報 | 例 |
|---|---|
| 規則の名前（種類） | null の可能性がある値を参照している |
| 重大度 | 高・中・低 |
| 場所 | ファイルと行 |
| 説明 | なぜ問題になりうるか、どう直すか |

代表的な種類と、その意味です。

| 種類 | 何が起きうるか | 重大度の目安 |
|---|---|---|
| null の可能性がある値の参照 | 実行時の `NullPointerException` | 高 |
| 資源（ファイル・接続）の閉じ忘れ | 接続やファイルハンドルが枯渇する | 高 |
| SQL を文字列の連結で組み立てている | SQL インジェクション | 高 |
| 例外を捕まえて何もしない | 障害が起きても気づけない | 中〜高 |
| 型の変換で桁があふれうる | 値が黙って壊れる | 中 |
| 使っていない変数・import | 読みにくくなる。直し忘れの兆候のことも | 低 |

## なぜ必要か

作業担当は、一覧に出た指摘を、自分の担当のコードで直せれば十分です。
案件担当は、指摘の一つ一つが「本当に直すべきか」を判断し、その判断に責任を持ちます。

静的解析ツールは、コードの意図を知りません。
規則に当てはまれば、問題が無いコードも指摘します（誤検知）。
逆に、すべての問題を見つけられるわけでもありません。

指摘を全部機械的に直そうとすると、問題の無いコードを壊したり、読みにくくしたりします。
指摘を全部無視すれば、本当の不具合を見逃します。
判断の基準を持っていることが、案件担当に求められます。

## どうやるか

### 1. 指摘を 3 つに振り分ける

| 判断 | どんなとき | すること |
|---|---|---|
| 修正 | 指摘のとおり、問題が起きうる | コードを直す。直した理由が分かるテストを足す |
| 抑止 | 問題になりうる書き方だが、意図して書いている（安全だと示せる） | コードの該当箇所に、抑止の指定と理由を書く |
| 誤検知として除外 | ツールの読み違いで、そもそも問題が無い | ツールの除外設定に、理由と確認者を残す |

迷ったら「修正」を選びます。
抑止と除外は、「安全である根拠」を自分の言葉で書けるときだけ選びます。

### 2. 理由を書いて抑止する

!!! failure "悪い例"
    ```java
    // 例: 理由の無い抑止
    @SuppressWarnings("unchecked")
    List<String> codes = (List<String>) cache.get(key);
    ```
    なぜ安全なのかが分かりません。レビューする人も、後で読む人も確かめられません。

!!! success "良い例"
    ```java
    // 例: 理由を書いた抑止
    // 抑止の理由: cache には put(String, List<String>) でしか値を入れない（ProductCache の中だけで使う）
    @SuppressWarnings("unchecked")
    List<String> codes = (List<String>) cache.get(key);
    ```
    根拠（値を入れる場所が 1 か所に限られている）を書いています。
    抑止の範囲は、メソッドやクラス全体ではなく、必要な宣言だけに絞ります。

`@SuppressWarnings` は Java の標準の注釈で、コンパイラの警告を抑えます
（[SuppressWarnings（Oracle）](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/lang/SuppressWarnings.html)）。
静的解析ツールごとの抑止の書き方（専用の注釈・コメント・設定ファイル）は、使っているツールの説明書で確かめます。

### 3. 「重大度の高い指摘 0 件」の意味を説明する

多くの案件では、出荷の条件に「重大度の高い指摘 0 件」を置きます。

| この基準が保証すること | この基準が保証しないこと |
|---|---|
| 重大度の高い指摘が、修正されたか、理由付きで抑止・除外されたこと | 不具合が無いこと（ツールが見つけられない問題は残る） |
| 抑止・除外の判断に、根拠が残っていること | 重大度の中・低の指摘が問題ないこと |

「0 件」は、指摘を消すことが目的ではありません。
高い指摘の **すべてに、人が判断を下したこと** を示す基準です。
理由の無い抑止で 0 件にすると、基準の意味がなくなります。
そのため、抑止と除外の件数と理由も、合わせて報告します。

### 4. 傾向を見る

同じ種類の指摘が何度も出るなら、書き方の癖や、規約のあいまいさが原因かもしれません。
件数を種類ごとに数え、多いものはチームに共有します。
規約を直すのはリーダーの役割ですが、傾向に気づいて伝えるのは案件担当の役割です。

## サンプルアプリでは

`sample-app/src/main/java/com/example/sample/order/batch/DefaultFileFetcher.java` には、静的解析ツールが指摘しそうな箇所があります。
S3 から読むときに、`long` の上限を `int` に変換しています。

<!-- src: sample-app/src/main/java/com/example/sample/order/batch/DefaultFileFetcher.java @main -->
```java
byte[] bytes = in.readNBytes((int) maxBytes + 1);
```

`long` を `int` に変換すると、大きな値では桁があふれます。
しかし、コンストラクタで値の範囲を確かめています。

<!-- src: sample-app/src/main/java/com/example/sample/order/batch/DefaultFileFetcher.java @main -->
```java
/** 上限に設定できる最大値（配列 1 つに読める大きさ）. */
static final long MAX_CONFIGURABLE_BYTES = Integer.MAX_VALUE - 8;
```

<!-- src: sample-app/src/main/java/com/example/sample/order/batch/DefaultFileFetcher.java @main -->
```java
if (maxBytes < 1 || maxBytes > MAX_CONFIGURABLE_BYTES) {
    throw new IllegalArgumentException(
            "app.batch.max-input-bytes は 1〜" + MAX_CONFIGURABLE_BYTES + " で指定してください: " + maxBytes);
}
```

`maxBytes` は `Integer.MAX_VALUE - 8` 以下なので、`(int) maxBytes + 1` はあふれません。
もしこの変換が指摘されたら、「抑止（根拠: コンストラクタで範囲を確かめている）」と判断できます。
このように、指摘された 1 行だけでなく、値がどこから来るかまでたどって判断します。

資源の閉じ忘れについては、同じファイルで `try-with-resources` を使い、確実に閉じています。

<!-- src: sample-app/src/main/java/com/example/sample/order/batch/DefaultFileFetcher.java @main -->
```java
try (ResponseInputStream<GetObjectResponse> in = s3.getObject(req)) {
```

## もし判断の基準がなかったら？

すべて直す方針だと、上の `(int)` の変換を、意味のない範囲チェックで包むような変更が入ります。
コードは読みにくくなり、本当に大切な範囲チェック（コンストラクタ）の意味がぼやけます。

すべて抑止する方針だと、`0 件` の報告だけが残ります。
後で障害が起きて調べると、理由の無い抑止の中に原因があった、ということになります。
判断の根拠が残っていなければ、その判断が正しかったかを、だれも確かめられません。

## 理解度チェック

1. 「抑止」と「誤検知として除外」の違いは何ですか。
2. 迷ったときに「修正」を選ぶ理由は何ですか。
3. 「重大度の高い指摘 0 件」を、理由の無い抑止で達成すると、何が問題ですか。
4. `DefaultFileFetcher` の `(int) maxBytes + 1` が安全だと言える根拠は何ですか。

??? note "答え"
    1. 抑止は、問題になりうる書き方を意図して使い、安全な根拠をコードに書くことです。誤検知の除外は、ツールの読み違いで問題がそもそも無いものを、ツールの設定で外すことです。
    2. 安全の根拠を示せないなら、問題が起きうると考えるのが安全だからです。
    3. 高い指摘のすべてに人が判断を下した、という基準の意味が失われます。本当の問題が隠れたまま出荷されます。
    4. コンストラクタで `maxBytes` を `Integer.MAX_VALUE - 8` 以下に限っているので、`int` に変換して 1 を足してもあふれないからです。

## コードを読むときの確認観点

- [ ] 抑止の指定に、安全である理由が書かれているか
- [ ] 抑止の範囲が、必要な宣言だけに絞られているか（クラス全体を抑止していないか）
- [ ] 型の変換や配列の大きさに、範囲を確かめる処理が前にあるか
- [ ] ファイルや接続を `try-with-resources` で閉じているか
- [ ] 例外を捕まえたとき、ログに出すか、別の例外に包んで投げているか

    // 例: 演習 2 のコード
