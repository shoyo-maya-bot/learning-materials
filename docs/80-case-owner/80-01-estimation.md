# 80-01 見積の手法と選び方

!!! abstract "到達目標"
    - 類推・積み上げ（WBS）・三点見積・規模ベースの 4 つの手法の特徴を説明できる
    - 案件の状況から手法を選び、選んだ理由と他の手法を使わなかった理由を説明できる
    - 見積に前提・範囲外・幅を添えて出せる
    - 見積と実績の差を記録し、次の見積に使える

## 何か

**見積** は、作業にかかる工数（人日など）と期間を、根拠を添えて予測することです。
見積の出し方には、いくつかの **手法** があります。

| 手法 | やり方 | 得意な場面 | 弱い場面 |
|---|---|---|---|
| 類推 | 似た過去の案件の実績から推す | 早い段階でおおまかな規模を知りたい | 似た案件が無い、規模が大きく違う |
| 積み上げ（WBS） | 作業を細かく分け、1 つずつ見積もって足す | 設計書がそろい、作業が具体的に見える | 早い段階（作業が分けられない） |
| 三点見積 | 楽観・最可能・悲観の 3 つの値から期待値を出す | 不確実な作業（未経験の技術、仕様が揺れている） | 3 つの値を出す根拠が無い |
| 規模ベース | 画面数・API 数・ファンクションポイントなどの規模に、生産性を掛ける | 規模を数えられ、組織に生産性の実績がある | 生産性の実績が無い、規模に表れない作業が多い |

三点見積では、次の式で期待値を出すのが一般的です（楽観 O・最可能 M・悲観 P）。

```text
期待値 = (O + 4M + P) / 6
```

例: O=3 人日、M=5 人日、P=13 人日 なら、期待値は (3 + 20 + 13) / 6 = 6 人日です。
最可能の 5 人日より大きくなるのは、悲観の側に長く伸びた作業だからです。

## なぜ必要か

作業担当は「この方法で見積もって」と言われた手法で、自分の分を出せれば十分です。
案件担当は、手法そのものを選び、その選び方を関係者に説明する立場になります。

手法を選び間違えると、見積の数字がいくら丁寧でも外れます。

- 設計書がまだ無いのに積み上げで出すと、見えていない作業が丸ごと抜けます
- 初めて使う技術を類推で出すと、似ていない過去の実績を当てはめることになります
- 生産性の実績が無いのに規模ベースで出すと、掛ける数字そのものに根拠がありません

「なぜこの手法か」「なぜ他の手法ではないか」を説明できれば、
レビューする人は前提の誤りに気づけます。説明できない見積は、だれも検証できません。

## どうやるか

### 1. 案件の状況を確かめる

手法を選ぶ前に、次の 3 つを確かめます。

| 確かめること | 問い |
|---|---|
| 情報の量 | 設計書・画面一覧・IF 一覧はそろっているか |
| 過去の実績 | 似た案件の工数の記録はあるか。規模の単位あたりの実績はあるか |
| 不確実さ | 未経験の技術・未確定の仕様・外部の相手との調整はあるか |

### 2. 手法を選ぶ

| 状況 | 選ぶ手法の例 |
|---|---|
| 提案の段階で、設計書が無い | 類推（似た案件が無ければ規模ベースで補う） |
| 詳細設計が終わり、作業が見える | 積み上げ |
| 積み上げたが、一部の作業が不確実 | 積み上げ ＋ 不確実な作業だけ三点見積 |
| API を 30 本作る、のように同じ種類が多い | 規模ベース（1 本あたりの実績 × 本数）＋ 共通部分は積み上げ |

!!! tip "2 つの手法で確かめる"
    1 つの手法だけで出すより、2 つの手法で出して差を比べると、抜けや偏りに気づけます。
    たとえば積み上げの合計が、類推の値の半分しかなければ、見えていない作業が残っている可能性が高いです。

### 3. 選んだ理由を書く

!!! failure "悪い例"
    ```text
    見積: 20 人日（WBS で積み上げ）
    ```
    なぜ積み上げなのか、何を前提にしたのかが書かれていません。

!!! success "良い例"
    ```text
    見積: 18〜24 人日（期待値 20 人日）
    手法: 積み上げ（詳細設計が承認済みで、作業を 0.5〜2 日の単位に分けられたため）
          ただし外部ファイルの形式確認だけは三点見積（相手の回答次第で 1〜6 日と幅が大きいため）
    使わなかった手法:
      類推 … 同じ種類のバッチの実績はあるが、今回は入力が 3 種類あり規模が違う
      規模ベース … バッチ 1 本あたりの生産性の実績が、チームにまだ無い
    確かめ: 類推（過去のバッチ 1 本 8 人日 × 3 本 = 24 人日）と比べ、差は 2 割以内
    前提: 入力ファイルの形式が来週水曜までに確定する
    範囲外: 性能試験、本番環境の構築
    ```

### 4. 実績を記録して次に使う

作業が終わったら、見積と実績の差を記録します。
差が大きかった作業は、理由（見えていなかった作業、仕様の変更、手戻り）を 1 行で残します。
この記録が、次の類推と規模ベースの根拠になります。

## サンプルアプリでは

sample-app の注文取込バッチ（JOB0001）を、新しく作ると仮定して見積の材料を探します。
規模の手がかりになるのは、入力の項目と、ジョブの終了コードの種類です。

<!-- src: sample-app/src/main/java/com/example/sample/order/OrderImportService.java @main -->
```java
static final String HEADER = "order_no,member_id,product_code,quantity";
```

<!-- src: sample-app/src/main/java/com/example/sample/order/batch/OrderImportJob.java @main -->
```java
 * <p>終了コード: 0 正常 / 4 形式エラーの行あり（取込は続行）/ 6 内容の違う重複あり（その行は取り込まずに続行. 人が確かめる）/ 8 異常終了。
```

項目が 4 つ、終了コードが 4 種類あることから、作るべきテストの量も見えてきます。
`OrderImportServiceTest.java` には、正常・重複・内容の違う重複・形式エラー・存在しない会員などのテストが並んでいます。
同じ種類のバッチを作るなら、このテストの数と種類が、積み上げの作業一覧の手がかりになります。

## もし手法を選ぶ基準がなかったら？

いつも同じ手法で、同じように見積もっていると、得意な場面では当たり、苦手な場面では大きく外れます。
外れた理由も記録されないので、次の案件でも同じ外れ方をします。

さらに、レビューする人が見積の誤りに気づけません。
「20 人日」という数字だけでは、前提が崩れたときに見積をどう直すべきかも分かりません。
手法と前提が書いてあれば、「形式の確定が遅れたので、三点見積の悲観側に寄せて見直す」と、すぐに打ち手を決められます。

## 理解度チェック

1. 提案の段階で設計書がまだ無いとき、積み上げで見積もるのが向かない理由は何ですか。
2. 三点見積で O=2、M=4、P=12 のとき、期待値はいくつですか。
3. 見積に「使わなかった手法とその理由」を書くと、何がうれしいですか。
4. 規模ベースの見積に必要な、組織の側の材料は何ですか。

??? note "答え"
    1. 作業を細かく分けられないため、見えていない作業がそのまま抜けるからです。類推や規模ベースで、おおまかに出します。
    2. (2 + 16 + 12) / 6 = 5 です。
    3. レビューする人が、手法の選び方の前提（実績の有無・情報の量）が正しいかを確かめられます。前提が崩れたときに、どう見直すかも決めやすくなります。
    4. 規模の単位（API 1 本、画面 1 枚など）あたりの、過去の生産性の実績です。

## コードを読むときの確認観点

- [ ] 見積の対象（画面・API・バッチ）の数と種類を、設計書やソースから数えたか
- [ ] 入力の項目数・分岐（終了コードやエラーの種類）・外部との接点を、規模の手がかりとして拾ったか
- [ ] 既存のテストの数と種類を見て、テストの作業量を見積に入れたか
- [ ] 未経験の技術や未確定の仕様を、不確実な作業として分けたか

## 演習

1. sample-app の会員 API（照会と登録の 2 本）と同じ種類の API を、新しく 4 本作るとします。
   `MemberController.java`・`MemberService.java`・`MemberMapper.xml`・テスト・Karate のシナリオを見て、
   1 本あたりの作業を 5 つ以上に分けてください。
2. 演習 1 の案件で、手法を 1 つ選び、選んだ理由と、他の手法を使わなかった理由を書いてください。
   チームに「API 1 本あたり 3 人日」という過去の実績がある、とします。
3. 演習 1 の作業のうち、三点見積にすべきものを 1 つ挙げ、O・M・P の値と期待値を出してください。
