# 80-08 テスト観点の抽出とカバレッジ

!!! abstract "到達目標"
    - 同値分割・境界値分析・異常系の考え方で、テスト観点を自分で抽出できる
    - 命令網羅（C0）と分岐網羅（C1）の違いを説明し、カバレッジの値が妥当かを判断できる
    - 結合テストの観点（機能間のインタフェース・異常系・性能など）を挙げ、テストケースを設計できる
    - テスト観点の表から、テストケースとテストコードに落とせる

## 何か

**テスト観点** は、「何を確かめるか」の切り口です。
テストケースは、観点ごとに「この入力なら、この結果になる」を具体的に書いたものです。

単体テストの観点を出すための、代表的な考え方です。

| 考え方 | やり方 | 例（数量 1〜999） |
|---|---|---|
| 同値分割 | 入力を「同じ扱いを受けるグループ」に分け、各グループから 1 つ選ぶ | 範囲内（500）、小さすぎ（-5）、大きすぎ（2000）、数値でない（`x`） |
| 境界値分析 | グループの境目と、その両隣を選ぶ | 0・1・999・1000 |
| 異常系 | 想定外の入力や、依存先の失敗 | 空・列の不足・DB に接続できない |
| 状態 | 前の操作で変わった状態からの動き | 登録済みの注文番号をもう一度取り込む |

**カバレッジ**（網羅率）は、テストで通ったコードの割合です。

| 種類 | 数えるもの | 例 |
|---|---|---|
| 命令網羅（C0） | 実行された文（命令）の割合 | 全部の行を 1 回以上通ったか |
| 分岐網羅（C1） | 分岐の行き先（真・偽）を通った割合 | `if` の真と偽の両方を通ったか |

sample-app で使っている JaCoCo では、命令と分岐を別々に数えます
（[Coverage Counters（JaCoCo）](https://www.jacoco.org/jacoco/trunk/doc/counters.html)）。

## なぜ必要か

作業担当は、テスト仕様書のとおりに実施し、結果を記録できれば十分です。
案件担当は、テスト仕様書そのものを作ります。

観点を自分で出せないと、思いついたケースだけを試すことになります。
正常な入力ばかりで、境界や異常が抜けます。
不具合の多くは、境界と異常の側に隠れています。

カバレッジは、観点の漏れに気づく手がかりです。
ただし、C1 が 100% でも、確かめるべき値を確かめていなければ不具合は残ります（[60-03](../60-quality/60-03-measure-quality.md)）。
通っていない分岐が「なぜ通っていないか」を説明できることが、妥当性の判断です。

## どうやるか

### 1. 観点の表を作る

設計書の項目と処理ごとに、観点を表にします。

| 対象 | 観点 | 入力 | 期待結果 |
|---|---|---|---|
| 数量 | 境界（下限） | 1 | 登録される |
| 数量 | 境界（下限の外） | 0 | 形式エラー「quantity は 1〜999 です（0）」 |
| 数量 | 境界（上限） | 999 | 登録される |
| 数量 | 境界（上限の外） | 1000 | 形式エラー |
| 数量 | 型 | `x` | 形式エラー「quantity が数値ではありません」 |
| 注文番号 | 状態（再実行） | 登録済みと同じ行 | 重複として数え、登録しない |

### 2. カバレッジで漏れを探す

`./gradlew test` の後、JaCoCo のレポートを開き、通っていない分岐を探します（[20-15](../20-basics/20-15-junit.md)）。
通っていない分岐ごとに、次のどれかを判断します。

| 判断 | すること |
|---|---|
| 観点が漏れていた | 観点の表とテストを足す |
| 単体テストでは通しにくい（DB の障害など） | 結合テストで確かめる、と表に書く |
| 到達できないコード | 消せるかを検討する |

!!! warning "C1 の目標値だけを追わない"
    「80% に届かせる」ために、確かめる値の無いテスト（`assertThat(r).isNotNull()` だけ）を足しても、品質は上がりません。
    目標値は、漏れに気づくきっかけとして使います。

### 3. 結合テストの観点を出す

結合テストは、複数の機能や外部の仕組みを組み合わせて確かめます。

| 観点 | 問い | JOB0001 の例 |
|---|---|---|
| 機能間のインタフェース | 渡すデータの形・文字コード・件数が、受け取る側と合っているか | S3 に置いた CSV（BOM 付き・引用符付き）を、正しく読めるか |
| 異常系 | 相手が無い・遅い・壊れているとき | ファイルが無い、DB が止まっている、UTF-8 として正しくない |
| データの整合 | 処理の後、DB の値が期待どおりか | 取込の後の `orders` の件数と中身 |
| 再実行・順序 | 途中で止まった後や、2 回目の実行 | 異常終了の後に再実行して、二重に登録されないか |
| 性能 | 想定の最大の量で、時間とメモリに収まるか | 上限に近い大きさのファイル |
| 運用 | 監視や後続の処理が、結果を正しく受け取れるか | 終了コードとログを、スケジューラが判定できるか |

## サンプルアプリでは

数量の境界は、`OrderImportService.parse` で確かめています。

<!-- src: sample-app/src/main/java/com/example/sample/order/OrderImportService.java @main -->
```java
if (quantity < 1 || quantity > 999) {
    throw new IllegalArgumentException("quantity は 1〜999 です（" + quantity + "）");
}
```

この `if` には条件が 2 つあり、分岐の行き先は「範囲内」「1 未満」「999 超え」に分かれます。
C1 を満たすには、この両方の条件で真と偽を通す必要があります。

`OrderImportServiceTest.java` には、境界のすぐ内側を確かめるテストがあります（桁数の上限 20 文字）。

<!-- src: sample-app/src/test/java/com/example/sample/order/OrderImportServiceTest.java @main -->
```java
@Test
void parseAcceptsExactlyTwentyChars() {
```

21 文字の側は、`tooLongCodeSkipsOnlyThatLine` が確かめています。
境界の内側（20）と外側（21）の両方がそろっています。

結合テストの観点の一部は、dev-environment の CI（`.github/workflows/ci.yml`）で、DB と S3 エミュレータを起動して確かめています。
バッチの終了コードや、DB を止めたときの応答（503）などです。

## もしテスト観点の抽出がなかったら？

思いついた正常なケースだけを試すと、テストは全部通り、カバレッジもそこそこの値になります。
しかし、数量 1000 や、引用符の閉じていない行を試していなければ、そこにある不具合は本番で見つかります。

結合テストの観点が無いと、単体テストで偽物に置き換えた部分（S3・DB）の組み合わせが一度も確かめられません。
「単体テストは全部通ったのに、つないだら動かない」は、この観点の漏れから起きます。

## 理解度チェック

1. 同値分割と境界値分析の違いは何ですか。
2. C0 が 100% でも C1 が 100% にならない例を挙げてください。
3. カバレッジのレポートで通っていない分岐を見つけたとき、判断することは何ですか。
4. 単体テストでは確かめにくく、結合テストで確かめるべき観点を 2 つ挙げてください。

??? note "答え"
    1. 同値分割は、同じ扱いを受けるグループから代表を 1 つ選びます。境界値分析は、グループの境目とその両隣を選びます。不具合は境目に多いので、両方を使います。
    2. `else` の無い `if` で、条件が真のケースだけを試すと、全部の文は通りますが、偽の行き先を通っていません。
    3. 観点の漏れか、単体テストでは通しにくいものか、到達できないコードかを判断し、テストを足す・結合テストに回す・消す、のどれかにします。
    4. 機能間のインタフェース（実際のファイルの文字コードや形式）、異常系（DB の停止）、再実行、性能、などです。

## コードを読むときの確認観点

- [ ] 入力チェックの境界ごとに、内側と外側の両方のテストがあるか
- [ ] 条件が 2 つ以上ある `if` で、それぞれの条件の真と偽を通しているか
- [ ] テストが、結果の値（件数・メッセージ）まで確かめているか
- [ ] 単体テストで偽物に置き換えた部分が、結合テストで確かめられているか
