# 20-11 SQL の基本

!!! abstract "到達目標"
    - SELECT / INSERT / UPDATE の基本形を書ける
    - JOIN で 2 つのテーブルを結び付ける SQL を読める
    - インデックスが何のためにあるかを説明できる
    - PostgreSQL の `ON CONFLICT DO NOTHING` で冪等な登録ができる理由を説明できる

## 何か

SQL は、リレーショナルデータベース（表形式でデータを持つ DB）を操作する言語です。
このチームでは PostgreSQL を使います。ローカルでは PostgreSQL 16 がコンテナで動きます。

SQL の命令は、目的で 2 つに分けられます。

| 区分 | 命令 | 役割 |
|---|---|---|
| DDL（定義） | `CREATE TABLE`、`CREATE INDEX` など | テーブルや索引を作る |
| DML（操作） | `SELECT`、`INSERT`、`UPDATE`、`DELETE` | データを読む・書く |

アプリの SQL は MyBatis の Mapper XML に書きます（[20-12 MyBatis](20-12-mybatis.md)）。
この章では SQL そのものを学びます。

## なぜ必要か

業務アプリのデータは、ほぼすべて DB にあります。
SQL が読めないと、アプリが「何を読み、何を書くか」が分かりません。

また、同じ結果を返す SQL でも、書き方で速さが大きく変わります。
件数が少ない開発環境では速くても、本番の大量データで遅くなることがあります。
基本形とインデックスの考え方を押さえておくと、レビューで気付けます。

## どうやるか

### SELECT（読む）

```sql
-- 例: 会員 ID が 1 の会員を読む
SELECT id, name, email FROM member WHERE id = 1;
```

- 列は `*` ではなく、使う列を書きます。列の追加でアプリが壊れにくくなります
- `WHERE` で条件を絞ります。付け忘れると全件を読みます

!!! failure "悪い例"
    ```sql
    -- 例: 全列・全件を読んでから、アプリ側で絞り込む
    SELECT * FROM orders;
    ```

!!! success "良い例"
    ```sql
    -- 例: 必要な列だけを、DB 側で絞り込んで読む
    SELECT order_no, quantity FROM orders WHERE member_id = 1;
    ```

### INSERT（登録する）

```sql
-- 例: 会員を 1 件登録する（id は自動採番）
INSERT INTO member (name, email) VALUES ('会員 一郎', 'ichiro@example.com');
```

列名を必ず書きます。列の並び順に依存しないためです。

### UPDATE（更新する）

サンプルアプリには UPDATE がありません。基本形だけ示します。

```sql
-- 例: 会員 ID 1 の氏名を変える
UPDATE member SET name = '会員 二郎' WHERE id = 1;
```

!!! failure "悪い例"
    ```sql
    -- 例: WHERE が無いので、全会員の氏名が変わる
    UPDATE member SET name = '会員 二郎';
    ```

`UPDATE` と `DELETE` は、`WHERE` を書いてから実行します。
手で実行する前に、同じ `WHERE` で `SELECT` して件数を確かめる習慣を付けましょう。

### JOIN（結び付ける）

注文（`orders`）には会員 ID しかありません。会員の氏名も欲しいときは JOIN します。

```sql
-- 例: 注文と、その注文をした会員の氏名を読む
SELECT o.order_no, o.quantity, m.name
FROM orders o
JOIN member m ON m.id = o.member_id
WHERE o.product_code = 'P-001';
```

- `JOIN`（内部結合）は、両方に対応する行があるものだけを返します
- `LEFT JOIN` は、左の表の行を必ず残し、右に無ければ null にします
- `ON` に結び付けの条件を書きます。忘れると全組み合わせ（行数の掛け算）になります

### インデックス（索引）

インデックスは、本の索引と同じです。
条件に合う行を、全行を読まずに探せるようにします。

- 主キー（`PRIMARY KEY`）と一意制約（`UNIQUE`）には、PostgreSQL が自動でインデックスを作ります
- 外部キー（`REFERENCES`）には、自動では作りません
- `WHERE` や `JOIN` の条件によく使う列は、インデックスを検討します

```sql
-- 例: 会員ごとの注文をよく検索するなら
CREATE INDEX idx_orders_member_id ON orders (member_id);
```

インデックスは書き込みを少し遅くし、容量も使います。
付ければ付けるほどよい、というものではありません。

SQL がインデックスを使うかは、`EXPLAIN` で確かめられます。

```sql
-- 例: 実行計画を見る（Seq Scan は全件読み、Index Scan は索引を使った読み方）
EXPLAIN SELECT * FROM orders WHERE member_id = 1;
```

### ON CONFLICT DO NOTHING（重複なら何もしない）

PostgreSQL の `INSERT` には、一意制約に違反したときの動きを指定する書き方があります。

```sql
-- 例: 注文番号が既にあれば、エラーにせず何もしない
INSERT INTO orders (order_no, member_id, product_code, quantity)
VALUES ('A0001', 1, 'P-001', 2)
ON CONFLICT (order_no) DO NOTHING;
```

- 登録できたら更新件数 1、既にあれば 0 が返ります
- 同じファイルを何度取り込んでも、結果が変わりません（**冪等**、べきとう）
- `ON CONFLICT` は PostgreSQL の方言です。他の DB では書き方が違います

!!! failure "悪い例"
    ```sql
    -- 例: 先に件数を数えてから登録する（2 つの処理が同時に動くと両方が 0 件と判断し、片方が失敗する）
    SELECT count(*) FROM orders WHERE order_no = 'A0001';
    INSERT INTO orders (...) VALUES (...);
    ```

!!! success "良い例"
    ```sql
    -- 例: 1 つの SQL で「無ければ登録」を行う。判断は DB の一意制約に任せる
    INSERT INTO orders (...) VALUES (...) ON CONFLICT (order_no) DO NOTHING;
    ```

## サンプルアプリでは

### テーブル定義

`dev-environment/local/db/init/01_schema.sql` です。
DB コンテナの初回起動時だけ実行されます（`docker-compose.yml` で `/docker-entrypoint-initdb.d` に置いているため）。

```sql
CREATE TABLE member (
    id         BIGSERIAL PRIMARY KEY,
    name       VARCHAR(50)  NOT NULL,
    email      VARCHAR(254) NOT NULL UNIQUE,
    created_at TIMESTAMPTZ  NOT NULL DEFAULT now()
);

CREATE TABLE orders (
    order_no     VARCHAR(20) PRIMARY KEY,
    member_id    BIGINT      NOT NULL REFERENCES member (id),
    product_code VARCHAR(20) NOT NULL,
    quantity     INTEGER     NOT NULL CHECK (quantity BETWEEN 1 AND 999),
    imported_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

- `BIGSERIAL` は自動採番の整数です。`INSERT` で `id` を書かなければ、DB が番号を振ります
- `email` の `UNIQUE` で、同じメールアドレスの二重登録を DB でも防ぎます
- 注文のテーブル名が `orders`（複数形）なのは、`ORDER` が SQL の予約語（`ORDER BY`）だからです
- `member_id` は `member (id)` を参照する外部キーです。存在しない会員の注文は登録できません
- `orders.member_id` にはインデックスがありません。会員ごとの検索が必要になったら検討します

初期データは `dev-environment/local/db/init/02_data.sql` です。

```sql
INSERT INTO member (name, email) VALUES
    ('山田 太郎', 'taro@example.com'),
    ('佐藤 花子', 'hanako@example.com');
```

テーブルを作り直したいときは `docker compose down -v` でデータごと消し、もう一度起動します。

### アプリの SQL

`sample-app/src/main/resources/mapper/MemberMapper.xml` の SELECT と INSERT です。

```xml
  <select id="findById" resultType="com.example.sample.member.Member">
    SELECT id, name, email FROM member WHERE id = #{id}
  </select>

  <select id="existsByEmail" resultType="boolean">
    SELECT EXISTS (SELECT 1 FROM member WHERE email = #{email})
  </select>

  <insert id="insert" useGeneratedKeys="true" keyProperty="id" keyColumn="id">
    INSERT INTO member (name, email) VALUES (#{name}, #{email})
  </insert>
```

- `findById` は主キーで 1 件を読みます。主キーのインデックスが使われます
- `existsByEmail` は `EXISTS` で「1 件でもあるか」を true / false で返します。`count(*)` と違い、見つかった時点で止まります
- `email` は `UNIQUE` なので、この検索にもインデックスが使われます

`sample-app/src/main/resources/mapper/OrderMapper.xml` が、冪等な登録の実例です。

```xml
  <!-- 注文番号が既にあれば何もしない（再実行しても重複しない） -->
  <insert id="insertIfAbsent">
    INSERT INTO orders (order_no, member_id, product_code, quantity)
    VALUES (#{orderNo}, #{memberId}, #{productCode}, #{quantity})
    ON CONFLICT (order_no) DO NOTHING
  </insert>
```

`OrderImportService` は戻り値が 1 なら「登録」、0 なら「登録済み」と数えます。
詳しくは [30-11 冪等な登録](../30-reading/30-11-idempotent-insert.md) で読みます。

!!! note "ON CONFLICT が止めるもの・止めないもの"
    `ON CONFLICT (order_no)` が見逃すのは、注文番号の重複だけです。
    存在しない会員 ID（外部キー違反）や `quantity` の範囲外（CHECK 違反）は、エラーになります。

## もし SQL の基本がなかったら？

`WHERE` の無い `UPDATE` を 1 回実行するだけで、全件のデータが壊れます。
本番で起きると、バックアップからの復旧が必要になります。

また、インデックスを意識せずに書いた SQL は、データが増えたときに急に遅くなります。
開発環境の数件では気付けず、本番で初めて問題になるのが典型です。
`ON CONFLICT` を知らずに「数えてから登録」を書くと、再実行や同時実行で二重登録やエラーが起きます。

## 理解度チェック

1. `member.email` の検索にインデックスが使えるのはなぜですか。

    ??? note "答え"
        `email` に `UNIQUE` 制約があり、PostgreSQL が一意制約のインデックスを自動で作るからです。

2. 注文テーブルの名前が `order` ではなく `orders` なのはなぜですか。

    ??? note "答え"
        `ORDER` は `ORDER BY` で使う SQL の予約語だからです。
        予約語をテーブル名にすると、毎回引用符で囲む必要があり、間違いの元になります。

3. `orders.csv` を 2 回取り込むと、2 回目の `insertIfAbsent` は何を返しますか。

    ??? note "答え"
        すべての行で 0 を返します。注文番号が既にあり、`ON CONFLICT (order_no) DO NOTHING` で何もしないからです。

4. 会員が存在しない注文 `A9999,99,P-001,1` を `insertIfAbsent` するとどうなりますか。

    ??? note "答え"
        外部キー制約（`REFERENCES member (id)`）の違反でエラーになります。
        `ON CONFLICT (order_no)` は注文番号の重複しか扱いません。

5. `UPDATE` を手で実行する前に、何をするとよいですか。

    ??? note "答え"
        同じ `WHERE` で `SELECT` し、対象の件数と行を確かめます。

## コードを読むときの確認観点

- [ ] `UPDATE` / `DELETE` に `WHERE` があり、対象が意図どおりに絞られている
- [ ] `SELECT *` ではなく、使う列を書いている
- [ ] `JOIN` に `ON` の条件があり、内部結合と外部結合の使い分けが正しい
- [ ] よく使う検索条件の列にインデックスがある（または不要な理由がある）
- [ ] 再実行される登録が冪等になっている（`ON CONFLICT` など）
- [ ] テーブルの制約（`NOT NULL`・`UNIQUE`・`CHECK`・外部キー）とアプリのチェックが合っている
