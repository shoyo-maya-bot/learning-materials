# 20-16 モックとテストダブル

!!! note "読むコードは `exercise-base` ブランチ"
    この章の引用と行番号は、dev-environment の **`exercise-base` ブランチ**（弱いところを直す前の sample-app）に合わせています。
    `main` は修正済みです。切り替え方と修正後との比べ方は [30 実ソース読解](../30-reading/index.md#exercise-base) を参照してください。

!!! abstract "到達目標"
    - テストダブル（スタブ・フェイク・モック）の違いを説明できる
    - インメモリの Mapper やラムダで、DB を使わない単体テストを書ける
    - MockMvc（standalone）で Controller と例外ハンドラを確かめるテストを読める
    - Mockito で呼び出しを確かめるテストを書ける

## 何か

**テストダブル**とは、テストのときだけ本物の代わりに使う部品のことです。
映画の代役（スタントダブル）が語源です。

| 種類 | 何をするか | 例 |
|---|---|---|
| ダミー | 引数を埋めるだけで、使われない | 呼ばれない処理に渡す `null` 相当のもの |
| スタブ | 決まった値を返す | 「常に 1 を返す」Mapper |
| フェイク | 簡易だが本当に動く実装 | DB の代わりに `HashMap` で持つ Mapper |
| モック | 呼ばれ方（回数・引数）を記録し、後で確かめる | 「`insert` が呼ばれていない」ことを確かめる |
| スパイ | 本物を包んで、呼ばれ方を記録する | 本物の一部だけ差し替える |

Java では、モックを作るライブラリとして **Mockito** がよく使われます。
`spring-boot-starter-test` に含まれています。

## なぜ必要か

Service を単体テストするのに、本物の DB を用意すると次の問題が起きます。

- DB の起動が要り、テストが遅くなる
- 前のテストのデータが残り、結果が実行順で変わる
- 「DB が落ちたとき」のような状況を作りにくい

チームの規約でも、単体テストは DB・外部サービスを使わず、Mapper はインメモリ実装やラムダで差し替えます。
テストダブルを使うと、確かめたいクラスの **ロジックだけ** を、速く安定して確かめられます。

ただし、テストダブルは本物ではありません。
SQL が正しいか、部品をつないで動くかは、結合テスト（Karate など）で確かめます。

## どうやるか

### 1. インターフェースに依存させる

差し替えられるのは、Service がインターフェース（`XxxMapper`）に依存し、コンストラクタで受け取っているからです。
これは DI（[20-07 Spring Boot の仕組み（DI）](20-07-spring-di.md)）の大きな利点です。

!!! failure "悪い例"
    ```java
    // 例: Service の中で new しているので、テストで差し替えられない
    public class ProductService {
        private final ProductMapper mapper = new ProductMapperImpl();
    }
    ```

!!! success "良い例"
    ```java
    // 例: コンストラクタで受け取るので、テストではフェイクを渡せる
    public class ProductService {
        private final ProductMapper mapper;

        public ProductService(ProductMapper mapper) {
            this.mapper = mapper;
        }
    }
    ```

### 2. メソッドが 1 つならラムダで書ける

抽象メソッドが 1 つだけのインターフェースは、ラムダ式で実装できます。

例:

```java
ProductMapper alwaysOne = p -> 1;   // どんな商品でも「1 件登録した」と返すスタブ
```

### 3. 状態を確かめるか、呼び出しを確かめるか

- **状態の確認**: 処理の後の結果（戻り値・フェイクの中身）を確かめる。フェイクやスタブで行う
- **呼び出しの確認**: 「このメソッドが呼ばれた／呼ばれなかった」を確かめる。モックで行う

基本は状態の確認を優先します。
呼び出しの確認ばかりだと、実装の書き方を変えただけでテストが壊れます。

### 4. Mockito を使う

サンプルアプリは Mockito を使っていません。基本形だけ示します。

例:

```java
import static org.mockito.ArgumentMatchers.any;
import static org.mockito.Mockito.*;

@Test
void register_doesNotInsertWhenEmailExists() {
    MemberMapper mapper = mock(MemberMapper.class);
    when(mapper.existsByEmail("a@example.com")).thenReturn(true);   // スタブとして値を決める
    MemberService service = new MemberService(mapper);

    assertThatThrownBy(() -> service.register("A", "a@example.com"))
            .isInstanceOf(BusinessException.class);
    verify(mapper, never()).insert(any());                          // モックとして呼び出しを確かめる
}
```

- `mock(...)` で、何もしない偽物を作ります
- `when(...).thenReturn(...)` で、呼ばれたときの戻り値を決めます
- `verify(...)` で、呼ばれ方を確かめます。`never()` は「1 回も呼ばれていない」です

!!! failure "悪い例"
    ```java
    // 例: すべての呼び出しを verify しており、実装の手順をなぞっているだけ
    verify(mapper).existsByEmail("a@example.com");
    verify(mapper).insert(any());
    verifyNoMoreInteractions(mapper);
    ```

!!! success "良い例"
    ```java
    // 例: 結果（戻り値）を確かめ、呼び出しの確認は「登録しないこと」のような要件だけにする
    assertThat(m.email()).isEqualTo("a@example.com");
    ```

## サンプルアプリでは

### フェイク: インメモリの Mapper

`sample-app/src/test/java/com/example/sample/member/MemberServiceTest.java` の 16〜40 行目です。

<!-- src: sample-app/src/test/java/com/example/sample/member/MemberServiceTest.java @exercise-base -->
```java
/** DB を使わない差し替え用の Mapper. */
static class InMemoryMapper implements MemberMapper {
    final Map<Long, Member> rows = new HashMap<>();
    long seq = 0;

    @Override
    public Optional<Member> findById(long id) {
        return Optional.ofNullable(rows.get(id));
    }

    @Override
    public boolean existsByEmail(String email) {
        return rows.values().stream().anyMatch(m -> m.email().equals(email));
    }

    @Override
    public int insert(MemberRecord member) {
        member.setId(++seq);
        rows.put(member.getId(), member.toMember());
        return 1;
    }
}

private final InMemoryMapper mapper = new InMemoryMapper();
private final MemberService service = new MemberService(mapper);
```

- `MemberMapper` を `HashMap` で実装した **フェイク** です。本当に登録・検索ができます
- `insert` は採番（`++seq`）と `setId` まで真似しています。`useGeneratedKeys` の動きの代わりです
- テストごとに新しいインスタンスが作られるので、テスト同士でデータが混ざりません
- 「登録してから重複を確かめる」のように、状態をまたぐテストが自然に書けます

### スタブ・フェイク: ラムダの Mapper

`OrderMapper` はメソッドが 1 つなので、ラムダで差し替えています。
`sample-app/src/test/java/com/example/sample/order/OrderImportServiceTest.java` の 15〜16 行目です。

<!-- src: sample-app/src/test/java/com/example/sample/order/OrderImportServiceTest.java @exercise-base -->
```java
private final Set<String> stored = new HashSet<>();
private final OrderImportService service = new OrderImportService(o -> stored.add(o.orderNo()) ? 1 : 0);
```

`Set.add` は、初めての値なら true、既にあれば false を返します。
これで `ON CONFLICT DO NOTHING`（初回 1 件、2 回目 0 件）を 1 行で真似しています。

`sample-app/src/test/java/com/example/sample/order/OrderImportJobTest.java` の 13 行目と 17 行目では、さらに単純なスタブを使っています。

<!-- src: sample-app/src/test/java/com/example/sample/order/OrderImportJobTest.java @exercise-base -->
```java
private final OrderImportService service = new OrderImportService(o -> 1);
```

<!-- src: sample-app/src/test/java/com/example/sample/order/OrderImportJobTest.java @exercise-base -->
```java
OrderImportJob job = new OrderImportJob(loc -> List.of(OrderImportService.HEADER, "A1,1,P,1"), service);
```

- `o -> 1` は「常に登録できた」と返す Mapper のスタブです
- `loc -> List.of(...)` は、S3 やファイルを読まずに決まった行を返す `FileFetcher` のスタブです
- 同じファイルの 35〜37 行目では、`IOException` を投げるスタブで「読めなかった」状況を作っています

### MockMvc（standalone）: Controller と例外ハンドラ

`sample-app/src/test/java/com/example/sample/member/MemberControllerTest.java` の 24〜35 行目です。

<!-- src: sample-app/src/test/java/com/example/sample/member/MemberControllerTest.java @exercise-base -->
```java
@BeforeEach
void setUp() {
    StaticMessageSource messages = new StaticMessageSource();
    messages.addMessage("APPE0002", Locale.JAPANESE, "会員が見つかりません（会員ID: {0}）。");
    LocalValidatorFactoryBean validator = new LocalValidatorFactoryBean();
    validator.afterPropertiesSet();
    MemberService service = new MemberService(new MemberServiceTest.InMemoryMapper());
    mvc = MockMvcBuilders.standaloneSetup(new MemberController(service))
            .setControllerAdvice(new ApiExceptionHandler(messages))
            .setValidator(validator)
            .build();
}
```

- **MockMvc** は、サーバーを起動せずに HTTP リクエストを Controller に送る仕組みです
- `standaloneSetup` は Spring のアプリ全体を起動せず、渡した Controller だけを組み立てます。速く動きます
- その代わり、例外ハンドラ（`@RestControllerAdvice` のクラス）は `setControllerAdvice` で自分で渡します
- Bean Validation の Validator も `setValidator` で明示的に渡し、何を組み込んだテストかを読み手に見せています
- `StaticMessageSource` は、`messages.properties` の代わりにテストで本文を登録する部品です
- Service は本物、Mapper は `InMemoryMapper`（フェイク）です。Mockito は使っていません

同じファイルの 59〜67 行目では、入力エラーが 400 とメッセージ ID になることを確かめています。

<!-- src: sample-app/src/test/java/com/example/sample/member/MemberControllerTest.java @exercise-base -->
```java
@Test
void invalidInputReturns400() throws Exception {
    mvc.perform(post("/api/v1/members")
                    .contentType(MediaType.APPLICATION_JSON)
                    .content("{\"name\":\"\",\"email\":\"not-an-email\"}"))
            .andExpect(status().isBadRequest())
            .andExpect(jsonPath("$.messageId").value("APPE0001"))
            .andExpect(jsonPath("$.details.length()").value(2));
}
```

## もしテストダブルがなかったら？

すべての単体テストに DB が必要になります。
テストの前に DB を起動し、データを毎回きれいにする手間がかかり、実行時間も長くなります。
DB の状態しだいで成功したり失敗したりする、不安定なテストも増えます。

また、「ファイルが読めない」「S3 に届かない」といった異常系を作るのが難しくなります。
異常系のテストが減ると、分岐網羅率（品質ゲート D4）も満たせません。

## 理解度チェック

1. `InMemoryMapper` はテストダブルのどの種類ですか。理由も答えてください。

    ??? note "答え"
        フェイクです。`HashMap` で本当に登録・検索ができる、簡易だが動く実装だからです。

2. `OrderMapper` をラムダで差し替えられるのはなぜですか。

    ??? note "答え"
        `OrderMapper` の抽象メソッドが `insertIfAbsent` の 1 つだけで、関数型インターフェースとして扱えるからです。

3. `MemberControllerTest` で `setControllerAdvice(...)` を外すと、どのテストに影響しますか。

    ??? note "答え"
        `notFoundReturns404WithMessageId` と `invalidInputReturns400` です。
        `ApiExceptionHandler` が組み込まれないので、例外がメッセージ ID 付きの応答に変換されません。
        `standaloneSetup` は、渡した部品しか組み立てないからです。

4. Mockito の `verify` で、すべての呼び出しを確かめるテストの問題点は何ですか。

    ??? note "答え"
        実装の手順をなぞっているだけになり、結果が同じでも書き方を変えるとテストが壊れます。
        結果を確かめることを優先し、`verify` は要件に関わる呼び出しだけにします。

5. テストダブルを使った単体テストだけでは確かめられないことは何ですか。

    ??? note "答え"
        Mapper XML の SQL が正しいか、DB の制約やトランザクションが期待どおりか、部品をつないで動くかです。
        これらは DB を使う結合テスト（Karate など）で確かめます。

## コードを読むときの確認観点

- [ ] Service が依存をコンストラクタで受け取っており、テストで差し替えられる
- [ ] 単体テストが DB・S3 などの外部に接続していない
- [ ] テストダブルの振る舞いが、本物の仕様（例: 重複なら 0 件）と食い違っていない
- [ ] 呼び出しの確認（`verify`）より、結果の確認を優先している
- [ ] MockMvc の standalone で、例外ハンドラと Validator を組み込んでいる
- [ ] 異常系（読み込み失敗など）をスタブで作り、確かめている

参考: [Mockito](https://site.mockito.org/)、[Spring Framework: MockMvc](https://docs.spring.io/spring-framework/reference/testing/mockmvc.html)
