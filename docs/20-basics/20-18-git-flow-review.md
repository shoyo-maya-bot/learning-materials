# 20-18 Git の運用（ブランチ・PR・レビュー）

!!! note "読むコードは `exercise-base` ブランチ"
    この章の引用と行番号は、dev-environment の **`exercise-base` ブランチ**（弱いところを直す前の sample-app）に合わせています。
    `main` は修正済みです。切り替え方と修正後との比べ方は [30 実ソース読解](../30-reading/index.md#exercise-base) を参照してください。

!!! abstract "到達目標"
    - 作業ブランチを切って PR（プルリクエスト）を出すまでの流れを説明できる
    - 何をしたかが伝わるブランチ名とコミットメッセージを書ける
    - 小さな PR にする理由を説明できる
    - レビュー指摘の区分（MUST / WANT / NITS / Q）を使い分けられる

## 何か

Git の準備と基本操作は [10-02 Git と GitHub の準備](../10-setup/10-02-git.md) で学びました。
この章では、チームで同じリポジトリを使うときの **運用の決まり** を学びます。

チーム開発の基本の流れは次のとおりです。

1. `main` から作業用のブランチを作る
2. ブランチで変更し、小さな単位でコミットする
3. リモートに push し、PR を作る
4. CI（自動のビルド・テスト）が通り、レビューで承認される
5. `main` にマージし、作業ブランチを消す

- **ブランチ**: 他の人の作業と分けて変更するための、履歴の枝分かれ
- **PR（プルリクエスト）**: 「このブランチの変更を `main` に取り込んでください」という依頼。レビューの場にもなります
- **レビュー**: 他の人が変更を読み、問題が無いかを確かめること

## なぜ必要か

全員が `main` に直接 push すると、未完成の変更や壊れた変更がすぐに全員に届きます。
誰がいつ何のために変えたかも追いにくくなります。

ブランチと PR を使うと、次のことができます。

- `main` を常に動く状態に保つ（CI とレビューを通ったものだけが入る）
- 変更の理由と議論が PR に残り、後から「なぜこうしたか」を追える
- レビューで、書いた本人が気付かない誤りや規約違反を見つけられる

## どうやるか

### 1. ブランチ名

ブランチ名は、種類と内容が分かるようにします。
次はよくある形の例です。実際はチームの決まりに従います。

例:

| 種類 | 形 | 例 |
|---|---|---|
| 機能追加 | `feature/<課題番号>-<要約>` | `feature/123-member-search` |
| 不具合修正 | `fix/<課題番号>-<要約>` | `fix/130-import-header-bom` |
| 文書・設定のみ | `docs/<要約>`、`chore/<要約>` | `docs/readme-setup` |

- 英小文字・数字・ハイフンで書きます。空白や日本語は使いません
- 課題番号を入れると、課題管理ツールと結び付けられます

### 2. コミットメッセージ

1 行目に「何をしたか」を短く書きます。必要なら 1 行空けて「なぜ」を書きます。

!!! failure "悪い例"
    例:

    ```text
    修正
    ```
    ```text
    いろいろ対応
    ```

!!! success "良い例"
    例:

    ```text
    fix: 注文取込で見出し行の BOM を除いてから比較する

    Excel で保存した CSV は先頭に BOM が付き、見出し不一致で全件エラーになっていた。
    ```

- 1 行目の先頭に種類（`feat:` 機能、`fix:` 修正、`docs:` 文書、`test:` テスト など）を付ける書き方が広く使われています
- 1 つのコミットには、1 つの目的の変更だけを入れます。「整形」と「機能追加」は分けます

### 3. 小さな PR にする

PR は小さいほど、早く・正確にレビューできます。

| 大きな PR | 小さな PR |
|---|---|
| 読むのに時間がかかり、後回しにされる | すぐに読める |
| 見落としが増える | 1 つずつ丁寧に確かめられる |
| 衝突（コンフリクト）が起きやすい | 早くマージされ、衝突しにくい |
| 問題が出ると、どの変更が原因か分かりにくい | 原因を絞りやすい |

目安として、1 つの PR は 1 つの目的にし、変更行数は数百行以内に収めます。
大きな機能は「Mapper と SQL」「Service とテスト」「Controller と API テスト」のように分けて出します。

!!! failure "悪い例"
    例:

    ```text
    PR: 会員機能一式（Controller・Service・Mapper・テスト・画面・既存コードの整形）　+3,200 行
    ```

!!! success "良い例"
    例:

    ```text
    PR 1: 会員検索の SQL と Mapper を追加（+120 行）
    PR 2: 会員検索の Service と単体テストを追加（+180 行）
    PR 3: 会員検索 API と Karate シナリオを追加（+150 行）
    ```

### 4. PR の本文

レビューする人が、コードを読む前に全体をつかめるように書きます。

- **目的**: なぜこの変更が必要か（課題番号）
- **変更内容**: 何をどう変えたか（箇条書き）
- **確認したこと**: 実行したテスト、ゲートの結果
- **見てほしい点**: 迷った点、判断に自信がない点

### 5. レビュー指摘の区分

チームでは、レビューの指摘に区分を付けます。
区分があると、書いた人が「直さないとマージできないもの」と「任意のもの」を区別できます。

| 区分 | 意味 | 例 |
|---|---|---|
| MUST | 必須の修正。直さないとマージしない | `${}` を使っている、例外を握りつぶしている、個人情報をログに出している |
| WANT | 望ましい修正。直す方がよいが、理由があれば見送れる | メソッドが長いので分けたい、テストの観点を足したい |
| NITS | 軽微。好みや細かい表記 | 変数名の言い回し、コメントの誤字 |
| Q | 質問。修正の要求ではない | 「ここを全件取り消しにした理由は？」 |

!!! failure "悪い例"
    例:

    ```text
    これはダメです。
    ```

!!! success "良い例"
    例:

    ```text
    [MUST] OrderMapper.xml の ORDER BY ${sort} は SQL インジェクションになります。
    <choose> で候補から選ぶ形にしてください（規約: SQL は #{} のみ）。
    ```

指摘するときは、区分・場所・理由・直し方の案をそろえます。
指摘は **コード** に対するもので、書いた **人** に対するものではありません。
受ける側も、Q には答えを、WANT を見送るなら理由を返し、やり取りを PR に残します。

## サンプルアプリでは

サンプルアプリはソースコードの見本なので、Git の運用そのものはコードに現れません。
ただし、運用を支えるファイルがリポジトリ（`dev-environment`）にあります。

### PR のたびに CI が動く

`dev-environment/.github/workflows/ci.yml` の先頭です。

```yaml
on:
  pull_request:
  push:
    branches: [main]
```

PR を作ったとき（と `main` への push のとき）に CI が動きます。
サンプルアプリについては、次の手順でビルドと単体テストを実行します。

```yaml
      - run: ./gradlew build --no-daemon
```

CI が失敗している PR は、レビューの前に直します。
チームの開発（ai-coding の手順）では、品質ゲート D1〜D11 がすべて通ることがマージの条件です。

### コミットしてはいけないものを除く

`dev-environment/.gitignore` の先頭です。

```text
# secrets
.env
.env.*
!.env.example
```

パスワードなどを書く `.env` はコミットしません。見本の `.env.example` だけをコミットします。
ビルドの成果物（`build/`、`.gradle/`）や IDE の設定も除いています。

### 改行コードをそろえる

`dev-environment/.gitattributes` の先頭です。

```text
* text=auto eol=lf
*.bat text eol=crlf
```

Windows と Linux・Mac で改行コードが混ざると、変更していない行まで差分に出て、レビューの邪魔になります。
リポジトリでは原則 LF にそろえ、Windows 用のスクリプトだけ CRLF にしています。

### バージョンを上げるときの注意

`sample-app/build.gradle` の 1〜2 行目です。

```groovy
// サンプルアプリ（API とバッチを 1 つのプロジェクトに同居させた最小構成）
// 版はここで固定する。上げるときは CI が通ることを確認してから。
```

ライブラリの版上げのような変更も、PR で CI を通してから取り込みます。
他の変更と混ぜず、版上げだけの PR にすると、問題が出たときに原因を切り分けやすくなります。

## もしブランチ・PR・レビューの運用がなかったら？

誰かが `main` に壊れた変更を push すると、全員の手元でビルドが通らなくなります。
原因の特定と修正の間、チーム全体の作業が止まります。

また、レビューが無いと、`${}` の SQL や個人情報のログ出力のような問題が、そのまま本番に出ます。
コミットメッセージや PR が雑だと、半年後に「なぜこう書いたのか」を誰も説明できず、安全に直せなくなります。

## 理解度チェック

1. 会員検索の機能追加（課題番号 123）を始めます。ブランチ名の例を挙げてください。

    ??? note "答え"
        `feature/123-member-search` のように、種類・課題番号・要約が分かる名前にします（チームの決まりがあればそれに従います）。

2. 「`${}` を使っている」という指摘は、MUST / WANT / NITS / Q のどれですか。

    ??? note "答え"
        MUST です。SQL インジェクションの原因になり、チームの規約と品質ゲート D9 にも反するため、直さないとマージできません。

3. 3,000 行の PR を出すと、どんな問題が起きやすいですか。

    ??? note "答え"
        レビューに時間がかかって後回しにされ、見落としも増えます。
        コンフリクトが起きやすく、問題が出たときに原因を絞りにくくなります。

4. コミットメッセージ「修正」の問題点は何ですか。

    ??? note "答え"
        何を・なぜ直したかが分からず、履歴から変更の意図を追えません。
        「fix: 注文取込で見出し行の BOM を除いてから比較する」のように具体的に書きます。

5. `.env` を `.gitignore` に入れているのはなぜですか。

    ??? note "答え"
        パスワードなどの秘密情報を書くファイルだからです。一度コミットすると履歴に残り、消すのが困難になります。

## コードを読むときの確認観点

- [ ] PR が 1 つの目的に絞られ、関係ないファイルの変更（整形だけの差分など）が混ざっていない
- [ ] ブランチ名とコミットメッセージから、変更の種類と内容が分かる
- [ ] PR の本文に、目的・変更内容・確認したこと（テスト・ゲートの結果）が書かれている
- [ ] CI が通っている
- [ ] 秘密情報（`.env`、パスワード、キー）がコミットされていない
- [ ] レビュー指摘に MUST / WANT / NITS / Q の区分が付き、すべてに返答がある
